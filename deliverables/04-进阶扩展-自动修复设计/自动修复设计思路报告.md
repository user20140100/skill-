# 检测到 Skill 问题后自动修复 —— 设计思路报告

> 课题：AI Agent 技能（Agent Skills）全链路安全审计与效果评估系统
> 所属阶段：阶段四「进阶扩展（加分项）」
> 作者：杨宇涵 ｜ 日期：2026-11-19
> 关联文档：`docs/自动修复功能需求.md`（需求分析稿，本报告为其可提交的精编版）

---

## 一、概述

在三层评估流水线「扫描 → 去重 → 评估」的**下游**新增一个「修复」环节，把系统已检出的 skill 问题转化为**可落地、可验证、可回滚**的修复补丁，形成「检测 → 定位 → 修复 → 验证」的完整闭环（参考 Skill Evaluation Graph（SEG）的「检测→定位→修复」闭环）。

本设计的三个基本定位：

1. **问题已被上游检出**：自动修复不承担「发现问题」的职责——三层评估已经产出「问题 + 修复建议」，本功能只补「把建议变成补丁」这最后一公里；
2. **修复 ≠ 自动覆盖**：修复是高影响、难回滚的动作，落地前必须留人工确认点（继承设计原则「决策权交用户」）；
3. **不是所有问题都能 / 都该自动修**：问题分「修 skill / 修 eval / 修环境 / 需用户决策」四类，必须先做可修复性路由，只对「skill 本体、可确定性修复」的问题自动生成补丁。

---

## 二、设计原则

本设计继承三层评估实践，遵循七条原则：

| 原则 | 含义 |
|---|---|
| **P1 决策权交用户** | 自动修复只产出补丁与影响说明，应用与否由用户确认，不静默覆盖源码 |
| **P2 检测与修复分离** | 检测归三层评估、修复归本功能；修复规则与检测规则不耦合，可独立开关（对齐任务 A 的「检测归检测、放行归放行」） |
| **P3 确定性打底** | 可确定性的修复（占位符替换、字段补全、白名单追加）用确定性规则；语义修复才引入 LLM，且必须引用证据、可 diff |
| **P4 非侵入式** | 修复功能作为独立模块，通过「解析产物 + 生成补丁 + 调用外部 git 应用」完成，不改动 SkillSpector / SkillEvaluator 上游源码 |
| **P5 回归验证** | 应用补丁后必须重跑对应 tier，验证「目标 finding 消失 + 无新增高危」，验证不通过即回滚 |
| **P6 可回滚可审计** | 每次修复前留快照（git 天然支持），记录问题源、补丁内容、验证结果、回滚与否 |
| **P7 风险分级** | 按严重度排序修复队列：安全（高危凭证）> 质量（frontmatter/schema）> 效果（SKILL.md 语义指引） |

## 三、问题来源：三层各自产出什么「问题 + 修复建议」

自动修复的全部输入来自三层评估，它们产出**性质不同**的问题：

| 层 | 产出物 | 问题类型 | 是否带修复建议 |
|---|---|---|---|
| **Tier 1 安全** | SkillSpector `issues[]` | 71 规则安全 finding（明文凭证 / 外发 / 提权 / 供应链 / 越权等） | ✅ 每条带 `remediation` 字段 |
| **Tier 1 质量 / Schema** | SkillEvaluator 各 validator | schema / frontmatter / version / license / hygiene / pii / secrets / unicode | 部分带建议，多为「缺什么字段」式确定性问题 |
| **Tier 2 去重** | similarity findings | 段内重复（intra-skill）、跨 skill 冗余（inter-skill / catalog） | ❌ 只有相似度分数，无修复建议 |
| **Tier 3 效果** | `what_to_fix.json` | 每条 case 的失败原因 + 修复动作 | ✅ 带 `action` 字段，`kind` 分三档 |
| **Tier 3 运行级** | `next_steps` | 运行级改进（attempts 不足 / 负样本缺失 / agent 相关） | ✅ 确定性规则，`action + check` 双字段 |

### 3.1 `what_to_fix.json` 的 `kind` 字段是修复路由的命门

Tier 3 已经把问题按「归属」分好三档，自动修复据此路由：

| `kind` | 归属 | 是否修 skill | 说明 |
|---|---|---|---|
| `skill` | skill 本体 | ✅ 修 skill | SKILL.md 指引逻辑缺陷（如「搜索了 home/root 路径」应改为「限定 workspace」） |
| `eval case` | 用例侧 | ❌ 修 eval | 用例本身有缺陷，不是 skill 的问题 |
| `run error` | 环境侧 | ❌ 修环境 | 网关 / 沙盒 / agent 运行错误，与 skill 无关 |

> **结论**：只有 `kind == "skill"`（以及 Tier 1 的确定性安全/质量 finding、Tier 2 的段内重复）才是自动修复的合法对象；`eval case` / `run error` / 跨 skill 冗余属于「不该由本功能修」的范畴，路由到对应通道。

## 四、核心洞察：审查手段决定可修复性

通过对 SkillSpector 源码（71+ 规则 / 17+ 类威胁）逐类审查手段的分析，得出本设计的**核心规律**：可修复性由「检测手段的确定性 + 定位精度」决定——定位越精确、语义越明确，越适合自动修复。

| 审查手段 | 确定性 | 定位精度 | 代表分析器 | 对自动修复的意义 |
|---|---|---|---|---|
| 静态正则 / 模式匹配（prose + code） | 确定 | file:line | `static_patterns_*`（16 类） | 文本级、可机械替换 |
| Python AST 行为分析 | 确定 | ast 节点 | `behavioral_ast` | 结构级、可确定性改写 |
| 污点追踪 / 数据流 | 确定 | source→sink | `behavioral_taint_tracking` | 需理解数据流语义 |
| YARA 签名 | 确定 | file:line | `static_yara` | 命中即恶意，整体移除 |
| MCP manifest 解析 | 确定（TP4 走 LLM） | manifest 字段 | `mcp_least_privilege` / `mcp_tool_poisoning` | 字段级、可机械补全 |
| LLM 语义分析 | 不确定 | 无精确定位 | `semantic_security_discovery` 等 | 仅建议、不可自动修 |
| 专用完整性检查 | 确定 | file:line | `whitespace_padding` / `artifact_integrity` 等 | 专项、可机械修复 |

## 五、可修复性三分类（核心路由）

按「审查手段 → 修复方式」把全部安全漏洞划分为三类。自动修复只处理前两类，第三类转人工。

### 5.1 ① 可自动修复 · 固定规则匹配（确定性替换，无需理解语义）

| 漏洞 | 规则 ID | 修复动作 |
|---|---|---|
| 明文凭证内嵌命令行/连接串 | 规则 B（自研）/ PE3 | `-pSecret123` → `-p<password>`；凭证路径 → 占位符 `/path/to/config` |
| 隐藏指令（HTML 注释 / 零宽字符） | P2 / TP1 | 删除注释与零宽字符 |
| 空白填充隐藏指令 | P9 | 删除大块空白 / 长空格 run |
| 容器镜像校验禁用 | SC7 | 删除 `--disable-content-trust` / `DOCKER_CONTENT_TRUST=0` |
| 字节码 / 隐藏可执行 | SC8 | 删除 `__pycache__/`、`.pyc` / `.pyo` |
| 危险执行调用 | AST2 / AST4 / AST5 / AST9 | `eval`→`ast.literal_eval`；`shell=True`→`shell=False`；`os.system`→`subprocess.run`；反射 → 直接调用 |
| 不安全反序列化 | AST10 / TT6 / DS1-4 | pickle/marshal→JSON；`YAML.load`→`safe_load`；`unserialize`→`json_decode` |
| 危险工具参数 / 不安全默认 | TM1 / TM3 | `shell=True`→`False`；`verify=False`→`True` |
| 特权 K8s workload | TM4 | 移除 `privileged` / `hostPath` / host 命名空间 |
| 通配符 / 过度权限声明 | LP2 / LP4 | `*`→显式列表；删除未用声明 |
| Unicode 同形字欺骗 | TP2 | 非 ASCII 标识符 → ASCII 等价 |
| 云 metadata 端点访问 | SSRF1 | 移除 `169.254.169.254` 访问 |

### 5.2 ② 可自动修复 · 大模型修改（需理解语义，须引用证据、可 diff、人工 review）

| 漏洞 | 规则 ID | LLM 修复方向 |
|---|---|---|
| 环境变量枚举 | E2 | 改为按名读取业务所需变量 |
| 文件系统扫描 | E3 | 改为显式作用域路径 |
| 过度权限（最小化） | PE1 | 收敛为最小权限集合 |
| 依赖治理 | SC1 / SC4 / SC5 / SC6 | pin 版本 / 升级修复版 / 替换废弃依赖 / 更正包名 |
| 限制工具 / 加人审 / 加限流 | EA1 / EA2 / EA4 | 白名单工具、加确认、加 rate limit |
| 输出校验 / 输出限制 | OH1 / OH3 | 参数化查询 / 转义 / 加 max_tokens |
| 触发词收窄 | TR1 / TR2 / TR3 | 改为窄化、去 shadow、去钓鱼触发 |
| 动态 import 白名单 | AST3 | `__import__`→importlib allowlist |
| 污点流加校验 | TT1 / TT2 / TT5 | 源→汇之间加 allowlist / 校验 |
| Agent 配置访问移除 | AS1 / AS2 / AS3 | 改为显式参数 / env 传入 |
| 内网 / 动态请求加白名单 | SSRF2 / SSRF3 | 移除 loopback 或加 host allowlist |
| 参数描述注入删除 | TP3 | 删除参数元数据中的注入内容 |

### 5.3 ③ 无法自动修复（需人工判断 / 无精确定位 / 高风险）

| 漏洞 | 规则 ID | 原因 |
|---|---|---|
| 提示注入 / 越狱指令 | P1 / P3 / P4 / P5 / AR1-3 | 是否恶意需语义判断，误删有风险 |
| 语义 LLM 发现 | SSD-\* / SDI-\* / SQP-\* | 无 file:line 定位，仅建议 |
| 数据外发（判断合法性） | E1 / E4 / E5 | 合法遥测 vs 恶意外发，需人判断 |
| sudo / root | PE2 | 必要性需人判断 |
| 供应链复杂项 | SC2 / SC3 / SC9 / SC10 | 远程执行 / 混淆 / 隐藏 artifact，危险 |
| 越权 / 模型切换 | EA3 / EA5 | 意图需人判断 |
| 系统提示泄露 / 记忆污染 | P6-8 / MP1-3 | 语义，无机械修复 |
| 链式滥用 / rogue agent | TM2 / RA1 / RA2 | 复杂行为，需人审查 |
| 危险执行链 / 凭证外发流 | AST8 / TT3 / TT4 | 高风险，整体移除需人确认 |
| 恶意签名 | YR1-4 | 命中即恶意，整体移除需人确认 |
| 描述-行为不符 | TP4 | 依赖 LLM 判断，结论本身不确定 |
| 权限需运行时验证 | LP1 / LP3 | 运行时权限未知，补声明需人确认 |

### 5.4 路由的四条铁律

1. **先分类、后修复**：任何 finding 都必须先过三分类，未命中「固定规则可修 / LLM 可修」的，一律不进入自动修复队列，转人工；
2. **fail-closed**：拿不准「修 skill 还是修 eval」、或「确定性可修还是语义可修」时，按「不自动修」处理，宁可漏修不可误修；
3. **高影响强制确认**：外发白名单放行、凭证语义改写等涉及安全语义的修复，无论自动化程度多高，落地前必须人工确认；
4. **修复规则可扩展**：新增可修复漏洞类型 = 新增一条修复规则（detect / fix / verify 三要素），不改核心引擎。

## 六、可扩展性设计：修复规则注册表（参考 NVIDIA 检测扩展点）

这是本设计的**核心工程思路**：NVIDIA 在检测侧预留的可扩展性，自动修复侧**同构**复用。

### 6.1 NVIDIA 检测侧的三个扩展点

| 扩展点 | 位置 | 机制 |
|---|---|---|
| 分析器自动发现注册 | `analyzers/__init__.py` | `pkgutil.iter_modules` 动态扫描包内模块，定义 `ANALYZER_ID` + `node` 函数即自动注册 |
| 规则元数据注册表 | `pattern_defaults.py` | `DEFAULT_EXPLANATIONS` / `PATTERN_NAMES` / `DEFAULT_REMEDIATIONS` / `RULE_ID_TO_CATEGORY` 四 dict + `PatternCategory` enum，每条规则自带 `remediation` 自然语言修复建议 |
| 外部挂载 | `--yara-rules-dir` / `--baseline` | 非侵入式挂载 YARA 规则与抑制基线 |

### 6.2 关键洞察：把「修复文本」升级为「可执行补丁」

`DEFAULT_REMEDIATIONS` 给的是**自然语言修复文本**，不是**可执行补丁**。自动修复的可扩展性，就是把这条 `remediation` 升级为结构化的「修复规则」三要素（对齐 `next_steps.py` 的 problem / action / check 结构）：

```
修复规则 = {
  detect: 命中哪些 rule_id / finding 特征（复用已有检测，零新增检测逻辑）
  fix:    确定性替换模板（固定规则）或 LLM 提示（大模型修改）
  verify: 修复后重扫的断言（目标 finding 消失 + 无新增高危）
}
```

### 6.3 可扩展性带来的三条能力

1. **新增可修复漏洞类型 = 新增一条修复规则**，不改核心引擎；
2. **修复规则独立开关 / 灰度**：复用任务 A 的 `select.yaml` + `toggle.py` 模式，逐条启用 / 停用，对比修复前后差异；
3. **跟随上游升级**：SkillSpector 新增规则时，只需在修复规则库补对应 `detect` 条目，无需改检测代码（延续「非侵入式」原则）。

## 七、完整闭环：回归 → 补充 → 运行增长

自动修复策略不是一次性写死的，而是**随运行增长**的开放规则库：

```
检测 → 路由 → 修复 → 验证（重跑对应 tier 确定性比对）
                        │
                   回归发现新漏洞
                        │
            ├─ 已命中现有修复规则 → 继续修
            └─ 未命中 → 记录「未覆盖漏洞」→ 沉淀为新修复规则 → 扩充修复规则库
                                    │
                        审查更多 skill、修复更多安全漏洞
                                    │
                        修复规则库随运行增长 → 覆盖率递增 → 完整闭环
```

- **回归补充**：每次回归测试中出现的、未被现有规则覆盖的新漏洞，自动记为「待补充修复策略」，人工评审后沉淀为新修复规则，进入下一轮；
- **运行积累**：通过审查更多 skill（扩展 `skill-dataset/`）、修复更多漏洞，修复规则库持续增长，覆盖率单调递增；
- **完整闭环**：检测（三层评估）→ 定位（finding 精确定位）→ 修复（规则/LLM 补丁）→ 验证（回归比对）→ 反馈（未覆盖漏洞回流规则库），形成 SEG 式闭环，全程「确定性打底 + LLM 只做语义增量 + 决策权交用户」。

## 八、核心需求点（FR1-FR10）

| 编号 | 需求名称 | 需求描述 | 优先级 |
|---|---|---|---|
| **FR1** | 问题可修复性路由 | 解析三层产物，按路由表判定「可自动修 / 需人工 / 不可修（属 eval 或环境）」，只对可修项进入修复队列 | **P0** |
| **FR2** | 修复补丁生成 | 生成 unified diff / 逐文件改动清单，默认 dry-run 不落地；确定性修复走规则/模板，语义修复走 LLM 且可 diff | **P0** |
| **FR3** | 人工确认点 | 落地前展示补丁 + 影响说明，用户确认后才应用，不静默覆盖 | **P0** |
| **FR4** | 回归验证 | 应用后重跑对应 tier，确定性比对「目标 finding 消失 + 无新增 critical/high」 | **P1** |
| **FR5** | 失败回滚 | 验证不通过时自动回滚到修复前快照，记录失败原因 | **P1** |
| **FR6** | 风险分级排序 | 修复队列按严重度排序：安全 > 质量 > 效果 | **P1** |
| **FR7** | 可复现可审计 | 每次修复记录问题源、补丁内容、验证结果、回滚与否 | **P1** |
| **FR8** | 修复规则注册表 | 沉淀 detect / fix / verify 三要素的修复规则，支持开关与灰度，新增类型 = 新增规则 | **P2** |
| **FR9** | LLM 语义修复（可选） | 对 `kind=skill` 的 SKILL.md 指引缺陷用 LLM 生成补丁，人工 review 后才进队列 | **P2** |
| **FR10** | 修复范围白名单 | 限定自动修复只作用于声明的可修问题类型与文件路径，避免误改 | **P0** |

**最小可交付闭环**：FR1 + FR2 + FR3 + FR10 构成「检测 → 定位 → 修复补丁」前半段；FR4 + FR5 补齐「验证 + 回滚」后半段。时间紧张时先交付前半段（纯确定性、零 LLM、零风险）。

## 九、三套实现方案与选型

| 维度 | A 补丁生成器 | B 修复编排器 | C Agentic 闭环 |
|---|---|---|---|
| 自动化程度 | 半自动（只生成） | 半自动（生成 + 验证 + 回滚） | 全自动 |
| 落地写盘 | 否 | 是（备份 + 回滚） | 是 |
| 回归验证 | 无 | 确定性比对 | 迭代验证 |
| LLM 依赖 | 无 | 可选 | 强依赖 |
| 风险 | 低 | 中 | 高 |
| 演示价值 | 闭环前半段 | **完整闭环** | 完整但易翻车 |

- **方案 A（确定性补丁生成器）**：只做「读产物 → 生成补丁 → 输出」，不落地写盘；纯解析 + 确定性规则，零风险、零 LLM 成本，与 skill-recommend 同构。**推荐起步**。
- **方案 B（修复编排器）**：在 A 基础上补「应用 → 重跑 tier → 确定性比对 → 失败回滚」，新增 `fix` 子命令。**推荐目标**，是 SEG 的最小可复现版。
- **方案 C（Agentic 全自动修复）**：让 agent 自读产物、生成、应用、验证、迭代。LLM 生成不可控、验证成本高、易翻车，与「确定性打底 + LLM 只叙述」原则相悖。**仅文档化，不实现**。

## 十、风险与缓解

| 风险 / 依赖 | 影响 | 缓解 |
|---|---|---|
| 误修 eval / 环境问题 | 改了不该改的对象 | 路由铁律 + fail-closed，拿不准不自动修 |
| 补丁不精确 / 误改其他内容 | 引入新缺陷 | 范围白名单 + 统一 diff + 人工确认 |
| 修复引入新高危 | 回归验证漏检 | 重跑对应 tier 确定性比对，不通过即回滚 |
| 语义修复不可控 | 演示翻车 | LLM 仅生成、人工 review 后才进队列 |
| 验证成本高（重跑 Tier3） | 无法全量验证 | 先修确定性安全问题（验证只需重跑 Tier1），语义问题懒评估 |
| 无 LLM 网关凭据（当前环境） | 语义修复做不了 | 方案 A 全程确定性、零 LLM，不受影响 |
| 修复与检测规则耦合 | 规则失效或误改 | 检测与修复分离，独立开关 |

---

## 十一、结语

本设计把「检测到 skill 问题后自动修复」落点为：**以「审查手段决定可修复性」为路由依据、以「修复规则注册表」为可扩展内核、以「回归反馈回流」为闭环动力的确定性打底方案**。它复用 NVIDIA 在检测侧预留的三层扩展点（分析器自动发现、规则元数据注册表、外部挂载），把每条 finding 已自带的 `remediation` 自然语言建议，升级为「detect → fix → verify」三要素的可执行修复规则，从而让「可修复漏洞种类」像「可检测漏洞种类」一样可扩展、可开关、可跟随上游升级，并在持续运行中通过回归补充不断完善修复策略，形成完整闭环。
