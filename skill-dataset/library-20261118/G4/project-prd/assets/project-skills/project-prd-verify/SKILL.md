# Project PRD Verify

对 PRD 完整性和代码语义一致性给出证据化结论。

## 验证流程

1. 定位包含 `.project-prd/manifest.json` 的项目根目录。
2. 运行：

   ```bash
   python3 .project-prd/tools/project_prd_guard.py integrity --project-root <项目根目录>
   ```

   失败即输出 `FAIL` 并停止语义 Review。
3. 确定 Review 范围：优先使用用户指定的 commit/PR/diff；否则检查工作区与当前分支相对基线的生产代码和测试差异。
4. 阅读 `INDEX.md`，通过 diff 文件、调用关系、数据模型、`source_entries` 和 Behavior ID 选择全部受影响 PRD。
5. 完整阅读受影响 PRD，建立：

   | 代码变化 | 受影响 PRD/FP/Behavior | 功能章节 | 行为是否变化 | 测试证据 | 结论 |
   |---|---|---|---|---|---|

6. 检查生产代码是否改变：
   - 用户/调用方的交互步骤与系统响应。
   - 页面跳转、中间校验、数据加载或恢复。
   - 角色、数量、格式、状态、生效时机等正向限制。
   - 不支持、拒绝、置灰、幂等和重入等反向限制。
   - 空态、失败、网络、权限、边界的结果、文案和展示方式。
   - 功能之间的入口、协作、取消、恢复、清理与最终闭环。
   - Mermaid 流程图是否仍覆盖实际 FP 流转，规则矩阵是否仍与代码枚举、状态、优先级、文案和策略一致。
7. 检查 PRD 覆盖质量：diff 命中的触发、分支、状态、异步结果和清理路径必须归属明确候选、FP 和 Behavior；流程图、规则矩阵或异常证据失配时报告覆盖缺口。
8. 检查测试：新增/修改测试必须对应 PRD 章节或 Behavior ID；不得删除关键断言、放宽期望或只验证实现细节。
9. 按项目测试规范运行受影响的最小可靠测试集；共享基础能力或影响不明时扩大回归。
10. 输出唯一结论：`PASS`、`FAIL` 或 `BLOCKED`。证据不足不得使用 PASS。

## Review 输出

先给结论，再列出：

1. PRD 完整性结果。
2. 受影响的 PRD ID、Behavior ID 和章节。
3. 按严重度排序的问题及精确代码位置。
4. 已运行测试与结果。
5. 未覆盖风险。

没有问题时明确写“未发现违背已索引 PRD 的修改”，但仍需列出映射和测试证据。
