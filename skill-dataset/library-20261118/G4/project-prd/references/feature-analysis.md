# 项目全功能分析规则

本规则改编自 `project-feature-inventory` 的项目识别与业务聚合方法，用于生成逐功能 PRD，而非简单清单。

## 范围

只分析项目自身源码、资源和与行为相关的测试。排除：

- `.git/`、`.project-prd/`、`.agents/skills/`；
- `node_modules/`、`vendor/`、`third_party/`、`Pods/`、`oh_modules/`；
- `build/`、`dist/`、`target/`、`coverage/`、`.gradle/`、缓存和生成代码；
- CI/CD、打包、部署脚本，除非其本身是用户可感知产品能力。

## 项目识别

根据构建清单识别源码目录，并覆盖所有模块：

| 标识 | 常见源码目录 |
|---|---|
| `build.gradle(.kts)` | Android/Java/Kotlin 各模块 `src/main` |
| `oh-package.json5` | HarmonyOS 各模块 `src/main/ets` |
| `Package.swift` | `Sources/` |
| `pubspec.yaml` | `lib/` |
| `package.json` | `src/`、`app/`、`lib/`、服务端目录 |
| `go.mod` | 包含 `*.go` 的业务包 |
| `Cargo.toml` | `src/` 和 workspace members |
| `pyproject.toml` 等 | 根包或 `src/` |
| `*.sln` / `*.csproj` | 各项目业务目录 |

无法识别时，扫描常见源码后缀并按入口、导出和目录结构推断；不要只看根目录第一层。

如果项目提供 CodeGraph、IDE 索引或其他结构化索引，先用它追调用关系，但必须把索引文件清单与磁盘源码清单逐目录对账。索引漏掉的枚举、文案构建器、拦截器、配置和监听器仍要直接读取；不得把“索引中没有”当作“功能不存在”。

## 分析顺序

1. **入口**：Application、main、App、CLI 子命令、SDK 公共导出。
2. **路由/导航/注册**：页面、Controller、Router、Ability、Activity、插件注册。
3. **业务模块**：按目录和包识别领域边界。
4. **公开接口与状态流**：Service、UseCase、Store、ViewModel、Reducer、状态机。
5. **完整行为闭包**：从入口继续阅读实际执行路径、guard、switch/if 分支、拦截器、回调、定时器、订阅、资源清理和外部副作用。复杂功能不得停在接口级。
6. **数据模型**：Entity、Model、Schema、协议和持久化结构，尤其关注枚举值与状态字段如何影响行为。
7. **测试与用户文档**：用于确认边界、错误行为和兼容性；测试缺失不代表行为不存在。
8. **依赖关系**：区分 feature 专属组件、跨 feature 公共模块和基础设施。

## 两级聚合

最终 PRD 树只有两级：

```text
功能聚合分类/
└── 细分功能.md
```

- 一级分类使用业务名词，例如“用户与权限”“订单系统”“画布编辑”。
- 二级细分功能使用用户可感知的动宾或名词短语，例如“用户登录”“订单查询”“撤销重做”。
- 同一实体的 CRUD 通常合并为一个细分功能。
- 只服务某功能的 UI、模型和工具归入该功能。
- 跨功能复用但具有可观察契约的能力可归入“公共能力”。
- 日志、缓存、连接池等纯基础设施通常不建功能 PRD；如果它们有用户或调用方可感知的可靠性承诺，可建立“运行保障”类 PRD。

分类不设成员数量目标。一个独立业务域只有一个细分功能时，必须保留单成员分类，禁止为了凑 3 个成员与相邻技术模块合并。

### 一级分类内聚门禁

建立目录前，先在 `.project-prd/.analysis/` 输出分类契约表：

| 分类 | category_domain | category_goal | category_contract | 成员功能 | 每成员 category_fit 证据 | 排除项 |
|---|---|---|---|---|---|---|

- `category_domain` 是所有成员共同操作的核心业务对象、状态或生命周期；不是源码目录、技术栈或公共工具。
- `category_goal` 是所有成员共同服务的用户/调用方结果。
- `category_contract` 用 `dimension=value` 表达结构化共同维度，维度只能是 `actor/outcome/object/journey/lifecycle/permission`，按该顺序书写，至少两项。
- `category_fit` 用 `dimension=value @ path:Symbol` 证明当前细分功能确实契合契约；至少两项，值必须与 contract 完全相同，证据必须同时进入当前 PRD 的 `source_entries`。
- 目录内每份 PRD 必须复制完全相同的 domain、goal 和 contract；所有成员共同有证据的 fit 维度少于两个时 finalize 拒绝聚合。
- 任意两个成员至少共享以下两项并分别给出源码证据：主要角色、用户结果、核心业务对象/状态、连续用户旅程、同一生命周期与权限边界。
- 只共享源码目录、Service、UDI 通道、工具类、调用关系或维护者，不构成业务聚合依据。
- “信源切换”和“HAP 安装”、“设备诊断”等没有共同用户结果或状态域的能力必须拆开，不能建立“信源与工具”式拼盘目录。
- 禁止无业务限定的 `工具`、`其他`、`杂项`、`未分类`、`模块1` 等兜底名；`系统工具`、`辅助功能`等有明确产品含义的名称仍需通过上述分类契约，而不是仅凭名称放行。

## 覆盖检查

- 每个源码目录至少抽取并理解代表文件，核心目录必须完整阅读。
- 结构化索引文件集与磁盘业务源码文件集已经对账，所有索引缺口均已直接阅读并归类。
- 每个入口和路由都有 PRD 归属。
- 每个公开业务接口和数据模型都有归属。
- 每个多分支函数、状态机阶段、拦截器、枚举映射、异步回调和终止清理路径都进入行为清单。
- 对 source_entries 指向目录的 PRD，必须展开目录内所有项目源码，而不是把目录名当作已分析证据。
- 未归类文件单独列出并解释。
- PRD 结论至少能追溯到代码入口、测试或项目文档之一。

## 防止过度概括

一个细分功能对应一份 PRD。以下信号说明不能只写一两步主路径或空泛的限制表：

- 流程有多个编号步骤或状态阶段；
- 存在多个触发来源且准入规则不同；
- 存在拦截器链、优先级链或多个策略分支；
- 包含确认、取消、倒计时、超时、回调或异步等待；
- 正常结束、失败结束和取消结束执行不同清理；
- 最终动作有多种可观察策略或外部副作用。

发现这些信号后，转到 `prd-extraction.md` 建立行为清单，将每个独立行为分配到交互、限制、异常或闭环章节。
