# requirement_completion_skill 技能介绍

## 1. 概述与用途

本技能面向**空调室内机领域**，将自然语言或非结构化需求输入，转化为**可补全、可改写、可评审、可提取**的结构化需求结果，用于需求编写、评审与知识提取。

| 用途 | 说明 |
|------|------|
| **需求补全** | 根据用户意图补全缺失的维度（如控制入口、优先级、恢复逻辑等），并区分显式需求、推断需求与待确认项 |
| **需求改写** | 将一句话或片段改写成符合规范的结构化需求表述 |
| **需求评审** | 对已有需求文本做完整性、一致性检查，输出问题清单、缺失维度、风险与改写建议 |
| **结构化提取** | 从需求中抽取模块、条件、动作等结构化字段，便于入库或下游使用 |
| **补全说明** | 解释某功能模块在需求补全时应关注哪些维度、默认推断与必须确认项 |

**不适用**：纯技术方案、电控算法、硬件选型、成本评估、详细测试用例生成。

---

## 2. 架构

### 2.1 整体架构

```
用户输入 (task_type + user_input [+ context])
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│  任务分类 (task_classification)                          │
│  completion | rewrite | review | extraction | explanation │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│  模块匹配 (module_matching)                             │
│  module_registry + matching_rules → primary + related   │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│  插件加载 (plugin_loading)                              │
│  modules/plugins/<module_code>.json                      │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│  意图识别 + 通用框架检查 + 插件增强 + 多模块消歧         │
│  common_requirement_framework + plugin 规则 + resolution │
└─────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│  输出渲染 (output_rendering)                            │
│  task_templates + output_schema → 结构化结果             │
└─────────────────────────────────────────────────────────┘
        │
        ▼
结构化输出 (JSON / 文档，含 matched_modules 与任务相关字段)
```

### 2.2 目录与职责

| 目录/文件 | 职责 |
|-----------|------|
| **schemas/** | 输入/输出契约。`input_schema.json` 约束入参；`output_schema.json` 按任务类型约束必填字段 |
| **core/** | 通用需求框架与任务裁剪。`common_requirement_framework.json` 定义通用维度、评审检查点；`task_templates.json` 定义各任务类型的输出字段集合 |
| **modules/** | 领域模块注册与单模块知识。`module_registry.json` 为模块总表；`plugins/<module_code>.json` 为单模块的默认规则、必须确认项、缺失项、推理规则与改写模板 |
| **rules/** | 匹配与多模块规则。`matching_rules.json` 负责模块识别、主/关联判定、置信度与消歧；`multi_module_resolution_rules.json` 负责多模块时的依赖、优先级、冲突与恢复逻辑合并 |
| **runtime/** | 运行编排。`runtime_workflow.json` 定义步骤顺序与每步的输入输出、读取文件 |
| **prompts/** | 系统提示词等，供执行时引用 |
| **examples/** | 标准样例与验证集，用于 few-shot 与回归验证 |
| **output/** | 技能产出的评审结果、完善版需求等（可选落盘） |

### 2.3 数据流

- **输入**：最少需 `task_type` + `user_input`；可带 `domain`、`candidate_modules`、`context`（产品类型、交互通道、输出风格等）。
- **中间**：任务类型 → 匹配模块（primary + related）→ 加载对应插件 → 通用维度检查 + 插件规则叠加 → 多模块时做冲突/优先级/恢复合并。
- **输出**：所有任务均含 `task_type`、`matched_modules`；其余字段按 `task_templates` 与 `output_schema` 依任务类型输出（如 review 含 `review_issues`、`missing_dimensions`、`rewritten_requirement` 等）。

---

## 3. 任务类型与输出

| task_type | 主要输出字段（除 task_type、matched_modules 外） |
|-----------|---------------------------------------------------|
| **completion** | intent_type, core_intent, explicit_requirements, inferred_requirements, missing_dimensions, default_inference, must_confirm, risks, follow_up_questions, rewritten_requirement, assumptions |
| **rewrite** | intent_type, core_intent, must_confirm, rewritten_requirement, assumptions |
| **review** | intent_type, core_intent, review_issues, missing_dimensions, risks, follow_up_questions, rewritten_requirement |
| **extraction** | intent_type, structured_extraction, assumptions |
| **explanation** | core_intent, default_inference, must_confirm |

---

## 4. 模块与插件机制

- **模块注册表**（`module_registry.json`）：列出所有室内机功能模块，含 module_code、别名、关键词、关联模块、类别等，用于匹配与主/关联判定。
- **插件**（`modules/plugins/<module_code>.json`）：每个模块一份，包含：
  - **key_dimensions**：该模块需求补全时需关注的维度
  - **default_rules**：可默认采用的规则（如「静音与部分特殊模式互斥」）
  - **must_confirm_rules**：必须与用户或产品确认的边界
  - **common_missing_items**：该模块常见缺失项
  - **inference_rules**：从用户表述到补全维度的推理模式
  - **output_templates**：如改写模板（rewrite_template）

多模块命中时，以 primary 为主、related 为辅叠加规则，并按 `multi_module_resolution_rules` 处理冲突与优先级。

---

## 5. 规则体系

- **matching_rules**：模块识别置信度权重、主/关联判定规则、消歧规则、任务类型偏置、类别优先级等。
- **multi_module_resolution_rules**：多模块时的合并顺序（如安全保护优先）、冲突维度、冲突解决规则、common_linkages（如「静音/睡眠/强力/经济」聚焦模式互斥与退出恢复）。
- **common_requirement_framework**：通用维度（功能目标、控制入口、状态定义、优先级、记忆恢复、异常处理、反馈交互等）与通用评审检查点，用于补齐缺失维度与统一表达。

---

## 6. 使用方式

1. **明确任务类型**：completion / rewrite / review / extraction / explanation。
2. **提供 user_input**：原始需求段落、一句话需求或待评审文本。
3. **可选**：提供 `candidate_modules`、`context`（如产品类型、交互通道）。
4. 执行技能后，按 `output_schema` 与 `task_templates` 得到结构化结果；review 时还可直接使用输出的 `rewritten_requirement` 作为完善版需求草稿。

---

## 7. 维护与扩展

- 新增功能模块：在 `modules/plugins/` 新增插件 JSON，并在 `module_registry.json` 注册；必要时更新 `matching_rules`、`multi_module_resolution_rules` 及 `examples`。
- 调整通用维度或评审标准：改 `core/common_requirement_framework.json`。
- 调整某任务输出字段：改 `core/task_templates.json` 与 `schemas/output_schema.json`。
- 详细流程见 `core/维护规范.md`。
