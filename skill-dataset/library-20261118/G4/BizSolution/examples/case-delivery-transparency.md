# 需求方案示例：客户交付链条透明可信

> 本范例严格按 BizSolution SKILL.md v6.0 五部分结构输出，**展示方法论深度**：六色建模、规则六要素、RACI、场景差异、AI 机会审视、Given-When-Then 验收纲要。

---

## 一、问题定义

### 1.1 背景与痛点

TV 事业部当前客户交付过程依赖于人工沟通：客户下订单后需通过电话、微信、邮件向销管获取交期，交期变更时无主动通知。

**核心痛点（可量化）**：
- 销管团队每天平均花费 **2.5 小时**回复客户交期查询（访谈 5 名销管，2025Q4 数据）
- 交期变更后客户平均 **3.2 天**才获知（无主动通知机制，依赖客户下次询问）
- 2025 年客户投诉中 **78%**与「交期不透明」「变更无通知」相关（客服工单分类统计）
- 大客户海信在 Q4 业务回顾中明确提出「交付可视性」为续约条件之一

**不解决的代价**：大客户流失风险 + 销管团队随业务量增长需线性扩编 + 交付纠纷导致的商务赔偿。

### 1.2 目标与成功标准

| 维度 | 基线值 | 目标值 | 测量方式 |
|------|--------|--------|----------|
| 客户需求满足率 | 72%（2025 年均值） | ≥85% | ERP + 门户统计 |
| 交期变更通知及时率 | 0%（无此机制） | ≥95%（变更确认后 2H 内） | 通知系统日志 |
| 节点状态更新及时率 | 约 60%（依赖人工） | ≥98% | 系统自动采集 |
| 销管人工查询量 | 约 50 次/天（5 人×10 次） | 下降 ≥60% | 门户查询量 vs 人工沟通量 |
| 客户门户活跃率 | 0%（无门户） | ≥70%（下单客户月活） | 门户埋点 |
| 时间节点 | — | 6 个月内试点上线 | 里程碑追踪 |

目标满足 SMART：具体（每个指标有定义）、可衡量（有基线与目标值）、可达成（对标 H 企业已达到类似水平）、与业务相关（直连客户留存与运营成本）、有时间节点（6 个月）。

### 1.3 范围

**在范围内**：
- 组织范围：TV 事业部（销管、计划、采购、生产、物流、IT）
- 客户范围：第一阶段大客户（海信试点）+ 公板客户
- 业务范围：订单交付全链条（下单→采购→生产→发货→签收）+ 交期变更闭环
- 系统范围：客户门户、订单管理、MRP、生产执行、物流追踪（具体集成边界待 IT 确认）

**明确不在范围内**：
- 供应商侧的生产进度透明化（本期仅到采购单层面，供应商内部排产透明为二期）
- 财务结算与对账（已有独立系统，门户仅展示交付状态不涉及资金流）
- 移动端 APP（一期仅 Web 门户，移动端视试点反馈再评估）
- 海外事业部交付（组织架构与流程差异大，需独立分析）

### 1.4 干系人与诉求

| 干系人 | 角色 | 核心关切 | 潜在冲突 |
|--------|------|----------|----------|
| 客户（海信等大客户） | 受益方 | 随时知道交期、变更主动通知 | 希望看到最乐观交期 vs 计划需保守承诺 |
| 销管团队 | 执行方/受益方 | 减少重复应答、统一信息出口 | 担心门户上线后客户直接找计划绕过销管 |
| 计划部门 | 关键执行方 | MRP 能力提升后才能给出可靠交期 | 担心交期承诺公开后承受更大压力 |
| 采购/生产/物流 | 执行方 | 节点状态更新的操作成本 | 担心增加录入工作量 |
| IT 部门 | 使能方 | 系统集成复杂度与资源投入 | 多系统打通周期长，期望分阶段交付 |
| 事业部总经理 | 决策者 | 客户留存率、运营效率 | 关注投入产出，需看到阶段性价值 |

### 1.5 约束与假设

**约束**：
- 预算：一期预算上限 300 万（含 IT 建设与业务流程改造）
- 时间：大客户海信续约时间窗口为 2026 年 Q4，须在此之前完成试点
- 技术：现有 ERP 为 SAP ECC，MRP 模块尚未启用，需评估启用代价
- 组织：计划部门当前编制紧张，MRP 能力建设需同步考虑人员补充或培训

**关键假设**（及不成立时的预案）：
| 假设 | 不成立时的预案 |
|------|---------------|
| SAP ECC MRP 模块可在 3 个月内启用 | 降级为 Excel 半自动排程 + 手工同步，门户展示有所延迟 |
| 海信愿意配合试点并提供反馈 | 切换至另一大客户创维，时间线后延 1 个月 |
| 各部门可投入兼职人员参与项目 | 申请专项编制或外部顾问支援 |

## 二、诊断分析

### 2.1 差距分析

对标 H 企业（同行业交付透明度领先者）及理论最优：

| 维度 | 标杆（H 企业） | 我方现状 | 差距量化 | 证据类型 |
|------|---------------|----------|----------|----------|
| 订单可见性 | 客户随时查看节点与状态，平均查询响应 < 10 秒 | 依赖人工问询，平均响应 4 小时 | 系统性差距（无自助能力） | 访谈 + 竞品调研 |
| 交期变更通知 | 变更确认后自动推送，含原因与影响 | 无主动通知，客户平均 3.2 天后获知 | 机制缺失 | 工单数据分析 |
| 交付满足率 | 91%（H 企业 2025 年报） | 72% | 19 个百分点 | ERP 报表 |
| 节点状态更新 | 98% 系统自动采集 | 约 60%（依赖人工） | 38 个百分点 | 系统日志抽样 |
| 计划排程能力 | MRP 系统化，周级滚动 | 人工 Excel，2-3 天出一版 | 效率差约 5 倍 | 访谈 + 观察 |

### 2.2 根因分析

用「愿不愿 / 会不会 / 能不能」三层分解，每项追问两级：

| 层级 | 根因 | 追问（5Why 精神） | 证据 |
|------|------|-------------------|------|
| **会不会** | 需求未系统化管理，信息散落在邮件/微信/电话 | ① 为什么没系统化？→ 缺少客户需求收集的标准模板和流程；② 为什么没有标准？→ 过去需求量小，口头沟通够用，未建立规范 | 销管访谈 + 邮件抽查 |
| **会不会** | 销管与计划之间信息传递滞后 | ① 为什么滞后？→ 计划排产变更后无通知销管的机制；② 为什么无机制？→ 两个部门之间无系统对接，靠每周例会同步 | 流程观察 |
| **能不能** | 计划与排产能力不足 | ① 为什么不足？→ MRP 模块未启用，依赖人工经验排产；② 为什么未启用？→ 主数据（BOM、提前期、产能参数）不完整，无法跑 MRP | SAP 系统检查 + 计划员访谈 |
| **能不能** | 销管—计划—采购—生产信息孤岛 | ① 为什么会孤岛？→ 各部门使用不同系统或同一系统的不同模块，无统一数据视图；② 为什么没打通？→ 历史上各模块独立建设，缺乏端到端规划 | 系统架构审查 |
| **愿不愿** | 「对外透明」未纳入部门考核 | ① 为什么没纳入？→ 过往考核聚焦内部效率，客户体验指标未被分解到各部门；② 为什么没分解？→ 无客户体验量化数据，无法设定合理目标 | HR 考核文件审查 |

**根因小结**：表层是「信息不透明」，深层是三个互锁问题——① 需求管理缺规范（会不会）；② 计划能力与信息打通不足（能不能）；③ 客户体验缺乏考核驱动（愿不愿）。三者需同步解决，单点突破无法闭环。

### 2.3 机会点

按帕累托原则聚焦：

| 机会点 | 覆盖的痛点占比 | 预估价值 | 预估难度 | 优先级 |
|--------|---------------|----------|----------|--------|
| 客户门户 + 主动通知 | 78%（直接覆盖交期不透明投诉） | 高（客户体验直接提升 + 销管减负） | 中（需门户建设 + 通知通道） | 第 1 批 |
| MRP 排程能力提升 | 60%（交期不准的根因） | 高（交期可靠性根本改善） | 高（主数据治理 + 系统启用 + 人员培训） | 第 1 批（重点投入） |
| 内部信息打通（销管-计划-采购-生产） | 45%（变更传递滞后） | 中高（变更快速传递） | 中（接口开发 + 数据标准统一） | 第 2 批 |
| 客户需求标准化管理 | 35%（需求散落） | 中（减少信息丢失与误解） | 低（模板 + 流程约束） | 第 2 批（速赢） |
| 考核指标重构 | 30%（意愿驱动） | 中（长效机制） | 低（KPI 调整） | 第 2 批（速赢） |

### 2.4 优先级结论

**第 1 批（重点投入）**：客户门户与主动通知 + MRP 排程能力提升。两者互为依赖——MRP 是可靠交期的来源，门户是可靠交期的出口。缺少任一方，另一方的价值大打折扣。

**第 2 批（速赢 + 跟进）**：内部信息打通、需求标准化、考核重构。其中需求标准化和考核重构难度低、见效快，可在第 1 批进行期间同步启动。

**本期不做**：供应商生产进度透明化（依赖供应商侧系统建设，周期长）；AI 智能排程（需 MRP 先跑通，数据积累后再建模）。

## 三、方案设计

### 3.1 业务目标与方案概述

以「客户可自助查看 + 变更可预警 + 交期可承诺」为主线，建设客户交付透明化能力。

**关键能力**：
1. 客户自助查询订单交付状态（门户）
2. 交期变更主动通知（变更确认后 2H 内推送）
3. 交付节点状态自动/半自动采集
4. MRP 系统化排程（替代人工 Excel 排程）
5. 客户需求标准化录入与流转
6. 交付指标体系与看板

### 3.2 六色建模总览

> 以下为六色要素摘要。完整模型见 drawio 附图（`docs/diagrams/delivery-six-color.drawio`）。

| 颜色 | 维度 | 关键元素（摘） |
|------|------|---------------|
| 🔵 流程 | Process Flow | 订单交付主流程（下单→MRP→采购→生产→发货→签收）；交期变更流程（触发→评估→审批→通知→确认）；紧急插单流程 |
| 🟢 角色 | Actor | 客户、销管、计划员、采购员、生产调度、库管/物流、IT 管理员 |
| 🔴 规则 | Business Rule | 物料齐套规则、排产冻结窗口规则、交期变更通知规则、紧急插单判定与审批规则、客户指定物料管理规则 |
| 🟡 单据 | Document | 客户订单、采购申请单、采购订单、生产工单、发货通知单、客户签收单、交期变更申请单 |
| 🟣 实体 | Entity | 客户、物料、产品、BOM、供应商、仓库、产能日历、交付节点状态 |
| 🟠 场景 | Scenario | 新单交付、翻单交付、规格书变更、交期变更、紧急插单 |

### 3.3 端到端流程与场景

#### 流程清单

| 类型 | 流程名称 | 优先级 | 涉及角色 |
|------|----------|--------|----------|
| 主流程 | 订单交付（下单→采购→生产→发货→签收） | 关键 | 客户、销管、计划、采购、生产、物流 |
| 主流程 | 交期变更（触发→评估→审批→通知→确认） | 关键 | 计划、销管、客户 |
| 主流程 | MRP 物料需求计划 | 关键 | 计划、采购 |
| 支撑 | 物流与客户签收 | 一般 | 物流、客户 |
| 支撑 | 客户需求标准化录入 | 重要 | 销管、客户 |
| 异常 | 紧急插单 | 重要 | 销管、计划、生产（联合会签） |

#### 场景差异表

| 场景 | 流程差异 | 角色差异 | 规则差异 |
|------|----------|----------|----------|
| 新单交付 | 需确认规格书、BOM/软件版本 | 需研发确认 BOM | 规格书确认后方可进入 MRP |
| 翻单交付 | 跳过规格书确认，直接进入 MRP | 无需研发介入 | 历史 BOM 无变更则复用；有变更走变更流程 |
| 规格书变更 | 插入变更审批节点 | 研发 + 计划联合会签 | 变更后重新评估物料齐套 |
| 交期变更 | 插入评估→审批→通知→确认子流程 | 计划评估影响 → 销管通知客户 | 确认后 2H 内推送；客户 48H 未确认则电话跟进 |
| 紧急插单 | 联合会签 + 影响面通知 | 销管发起，计划/生产/采购会签 | 产能占用 > 20% 需事业部总经理审批 |

### 3.4 业务规则

以规则六要素格式列出关键规则：

#### 规则 1：物料齐套检查规则

| 要素 | 内容 |
|------|------|
| 名称 | 物料齐套检查规则 |
| 内容 | IF 订单所需物料在 MRP 运算后存在缺口 THEN 标记为「物料不齐套」，生成缺料清单并通知采购 |
| 目的 | 确保生产可执行性，防止开工后因缺料停工 |
| 触发条件 | MRP 运算完成后 |
| 执行主体 | MRP 系统（自动） |
| 生效范围 | 所有生产订单 |
| 落地方式 | 系统固化 |

#### 规则 2：排产冻结窗口规则

| 要素 | 内容 |
|------|------|
| 名称 | 排产冻结窗口规则 |
| 内容 | IF 距离计划开工日期 ≤ 3 个工作日 THEN 排产冻结，变更需计划主管 + 生产调度联合会签 |
| 目的 | 平衡生产稳定性与变更灵活性 |
| 触发条件 | 收到交期变更或插单请求 |
| 执行主体 | 计划员判断（系统辅助显示冻结状态） |
| 生效范围 | 所有已排产订单 |
| 落地方式 | 系统规则 + 制度规范 |

#### 规则 3：交期变更通知规则

| 要素 | 内容 |
|------|------|
| 名称 | 交期变更主动通知规则 |
| 内容 | IF 交期变更审批通过 THEN 系统在 2H 内通过门户消息 + 邮件推送给客户；若 48H 内客户未查看/确认，销管电话跟进 |
| 目的 | 确保客户及时获知变更，减少信息不对称 |
| 触发条件 | 交期变更审批单状态 = 已批准 |
| 执行主体 | 门户系统（自动推送）+ 销管（48H 后人工跟进） |
| 生效范围 | 全部客户（大客户额外增加微信/短信通道） |
| 落地方式 | 系统固化 + 考核指标（通知及时率 ≥95%） |

#### 规则 4：紧急插单判定与审批规则

| 要素 | 内容 |
|------|------|
| 名称 | 紧急插单判定与审批规则 |
| 内容 | IF 申请理由符合①客户产线停线风险 或 ②战略客户合同约定优先权 THEN 标记为紧急插单；插入后占用产能 >20% 须事业部总经理审批 |
| 目的 | 防止「紧急」标签滥用，保护已承诺交期 |
| 触发条件 | 销管提交插单申请 |
| 执行主体 | 计划员（初判）→ 相关部门会签 → 总经理（产能>20% 时） |
| 生效范围 | 所有插单申请 |
| 落地方式 | 系统流程 + 审批权限配置 |

#### 规则 5：客户指定物料管理规则

| 要素 | 内容 |
|------|------|
| 名称 | 客户指定物料管理规则 |
| 内容 | IF 订单包含客户指定物料（如指定品牌芯片）THEN 物料交期以客户确认为准，该物料导致的延期不计入内部交付指标 |
| 目的 | 区分可控与不可控因素，公正评价内部交付能力 |
| 触发条件 | 订单评审时识别到客户指定物料 |
| 执行主体 | 销管标注 → 计划确认 |
| 生效范围 | 含客户指定物料的订单 |
| 落地方式 | 系统标记 + 指标统计排除 |

**冲突解决原则**：合法合规 > 控制风险 > 业务目标 > 协同效率。当排产冻结期内大客户要求插单时，按此层级决策：不涉及合规与重大风险时，由业务目标（客户留存）决定是否破例。

| 客户签收单 | 签收确认 | 客户 | 订单关闭 | 订单 |
| 交期变更申请单 | 变更触发 | 计划员 | 变更通知 | 订单 |

#### 核心实体关系要点

- 客户 : 订单 = 1 : N
- 订单 : 订单行 : 物料 = 1 : N : N
- 产品 : BOM : 物料 = 1 : 1 : N
- 物料 : 供应商 = N : N（一个物料可有多个供应源）
- 订单 : 交付节点状态 = 1 : N（每个订单有多个节点状态记录）

### 3.7 智能化与 AI 赋能

| 流程环节 | 当前方式 | 目标方式 | 类型 | 依赖数据与规则 | 风险与人机分工 |
|----------|----------|----------|------|---------------|---------------|
| MRP 排程 | 计划员手工 Excel 排程，2-3 天/版 | MRP 系统自动运算 + 计划员调整确认 | 自动处理 | 完整 BOM、提前期、产能日历、库存数据 | 主数据不完整时 MRP 结果不可用；计划员保留最终调整权 |
| 交期变更影响分析 | 计划员人工评估影响面（哪些订单受影响） | 系统自动计算变更影响范围（关联订单、产能占用） | 智能辅助 | 排产数据、BOM、订单关联关系 | 系统提供分析结果供计划员确认，不做自动决策 |
| 客户交期查询 | 客户电话/微信问销管，销管查系统后回复 | 客户门户自助查询 + 对话式查询（自然语言） | 便捷交互 | 订单状态、节点时间、预计交期 | 二期规划（一期门户为结构化查询）；需注意权限隔离 |
| 异常预警 | 人工发现（如缺料后才被动获知） | 物料齐套预警、交付延迟风险预警（基于规则） | 智能辅助 | 库存、采购在途、生产进度、历史交期偏差 | 规则引擎实现（非 AI）；预警阈值可配置 |

**本期不涉及深度学习/大模型场景**。原因是：① MRP 主数据尚不完整，不具备数据条件；② 一期核心任务是流程闭环与数据标准化，AI 能力在二期数据积累后更有价值。一期聚焦规则自动化（通知、预警、影响分析）。

### 4.3 预警与闭环

```
数据采集（日/周）→ 阈值触发 → 根因归责 → 纠偏任务 → 效果验证 → 复盘沉淀
```

| 预警项 | 触发条件 | 归因方向 | 纠偏动作 | 责任方 |
|--------|----------|----------|----------|--------|
| 满足率连续下降 | 连续 2 周 < 80% | 排产不准 / 物料延迟 / 需求变更 | 根因分析会议，48H 内出纠偏方案 | 计划主管 |
| 通知及时率不达标 | 单周 < 90% | 系统故障 / 审批延迟 / 数据延迟 | IT 排查 + 流程抽查 | IT + 销管 |
| 门户活跃率低 | 连续 2 周 < 50% | 客户未感知门户价值 / 体验差 | 客户回访 + 使用引导 | 销管 |
| 交付周期异常上升 | 环比上升 > 10% | 产能瓶颈 / 供应商延期 / 插单过多 | 计划复盘，必要时冻结插单 | 计划主管 |

### 4.4 复盘机制

- **周期**：月度运营复盘 + 里程碑节点专项复盘
- **参与人**：项目经理 + 各部门代表 + 事业部负责人（季度参加）
- **输入材料**：指标趋势报告、预警与纠偏记录、客户反馈摘要
- **回溯规则**：若连续 2 个月指标未达标，回溯方案设计，评估是否需要调整方案假设或范围

### 5.2 系统固化

| 固化内容 | 方式 | 原因 |
|----------|------|------|
| 物料齐套规则 | 系统自动计算 | 高频、规则明确、人工计算易出错 |
| 排产冻结窗口 | 系统状态控制 + 人工决策 | 规则清晰但需人工判断例外 |
| 交期变更通知 | 系统自动推送 | 高频、时效性要求高（2H 内） |
| 紧急插单审批流 | 系统流程引擎 | 需审批轨迹留存 |
| 预警触发 | 系统规则引擎 + 人工归因 | 触发可自动，归因需人工判断 |

**保持人工弹性的项**：交期承诺的最终确认、客户关系敏感沟通、跨部门协调。
