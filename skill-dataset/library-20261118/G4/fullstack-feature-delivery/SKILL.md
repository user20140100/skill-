# 全栈功能落地（Fullstack Feature Delivery）

覆盖从需求输入（一句话口头描述、需求文档 PRD、交互稿原型）到前后端代码全部上线的功能开发任务。核心思想：**先对齐再动手、契约先行、兼容扩展、破坏性操作显式化**。

## 适用判断

- 适用：跨前后端的新功能（无论需求是一句话、需求文档还是交互稿）、需要先确认需求/出计划的任务、按接口文档做前端对接
- 不适用：单端 bug 修复（直接定位修复）、纯读代码的咨询问答、纯技术选型（用 tech-selection 类技能）

## 七阶段工作流

按顺序推进，每阶段有明确的"完成标志"，未完成不进入下一阶段。

### 阶段 0：需求甄别

先判定需求输入形态，按对应动作提炼为统一的「功能点清单 + 决策点」，未经确认不动代码：

**形态 A：口头/一句话需求**（信息量最小）——复述需求请用户确认，再显式列出隐含决策点。

**形态 B：需求文档（PRD）**——通读并提炼功能点清单（每条：动词 + 对象 + 预期结果），回读给用户确认理解无偏差；标注文档中的模糊点（"支持 XX 等"、无验收标准处）与遗漏点（异常分支、边界、权限）转为待确认问题。

**形态 C：交互稿/原型**——按「页面 → 操作 → 数据字段」三要素提取功能与数据需求清单；若同时拿到接口文档，先做接口满足度甄别（功能点 × 接口三态：满足/缺失/需确认），缺口进入后续阶段。

无论哪种形态，都必须确认的隐含决策点：

- 操作语义：批量编辑是"全量覆盖"还是"留空不改"（patch 语义）？覆盖导入是新增+更新还是删除重建？
- 范围与上限：涉及哪些字段？单次操作的数量上限？
- 触发方式：破坏性操作（覆盖/删除）由谁触发——默认行为还是用户显式勾选？
- 兼容性要求：已有调用方（前端页面、第三方）行为是否必须保持不变？

完成标志：用户对功能点清单和决策点给出明确答复（或认可你提出的默认方案）。

### 阶段 1：现状调研

**先读后写**。动手前必须摸清既有实现，产出"已有能力 vs 缺口"清单：

- 找到功能入口（API/Controller/页面组件），读完整调用链：入口 → 服务层 → 数据层
- 记录工程惯例：分层结构、命名、事务写法、错误处理、权限校验方式——后续代码必须与之同构
- 特别排查：被复用的通用组件有哪些引用方（扩展必须向后兼容）；数据库表结构是否支撑新功能
- 顺手记录存量缺陷（调研中发现的 bug 单独告知用户，与本次需求分开处理）

完成标志：能一句话说清"现在有什么、缺什么、复用什么、新建什么"。

### 阶段 2：方案与计划

把阶段 0/1 的结论转成决策完备的实施计划：

- 计划按"子系统/功能点"分组，每个改动落到具体文件路径
- 决策点全部写死（不留"待定"）；有取舍的写清选了什么、放弃了什么、为什么
- 涉及数据库/权限的变更，明确论证"为什么改/为什么不用改"及未来触发条件
- **跨端改动计划必须先获用户批准再写代码**

### 阶段 3：后端实现

**规范优先**：动手前先找工程规范——有（AGENTS.md、README、CONTRIBUTING、docs/、lint 配置等）则先理解再遵循；无则扫描既有代码归纳惯例后遵循。下述仅为规范未覆盖时的通用兜底实践，与工程规范冲突时以规范为准（明显有害的单独提出建议，不强推）：

按依赖顺序分层落地（模型/VO → 接口声明 → 领域/数据层 → 应用服务 → API 实现）：

- 事务：写操作按工程惯例加事务注解并指定 rollbackFor
- 边界校验：参数校验注解 + 业务校验（存在性、枚举合法性、上限）前置到应用层
- 导入/批量类操作优先"两阶段"：先全量校验再统一写库，失败零写入
- upsert 优先应用层分流（先查再分 insert/update），除非有唯一索引支撑
- 补单测：纯 Mockito 单测覆盖分支即可，不必依赖真实数据库

完成标志：编译通过或（无编译环境时）完成静态核查——所有调用方闭环、API 用法与工程现存用法一致。

### 阶段 4：接口契约文档

**前端动手前**产出对接文档，与代码同源（字段名、类型、约束逐一核对）：

必备章节：请求（方法/路径/网关前缀/参数表/校验规则）、响应（成功样例/错误码与文案对照表）、业务规则说明（如 Excel 模板规范、覆盖语义警告）、前端交互建议。

陷阱：写文档时发现的代码瑕疵（如缺长度校验）应先补齐代码再落文档，保持两者一致。

### 阶段 5：前端实现

固定顺序：**类型层（interface）→ 服务层（model/api 方法）→ 组件 → 页面接入**：

- 扩展通用组件只加可选 props，不改既有签名；调用方按需 opt-in
- 破坏性操作在 UI 上显式勾选 + 警示后果文案；提交前剔除空值以配合后端 patch 语义
- 数量上限等约束在前端前置拦截（给出提示），不要等后端报错
- 列表操作成功后：刷新查询缓存 + 清空勾选状态

### 阶段 6：验收闭环

- 有本地工具链：跑 lint + 类型检查 + **编译与单测**，改动文件零新增问题
- 无本地工具链：优先按 [environment.md](environment.md) 就地搭环境（系统级安装先获用户授权），确实搭不了再降级静态核查，把编译/测试命令明确交给用户执行
- 单测判读三要素：provider 正确、Tests run 数量等于预期且 > 0、Failures/Errors 为 0——警惕“Tests run: 0 + BUILD SUCCESS”假绿
- 曾以静态核查交付的用例，环境就绪后必须回补执行
- 给用户可执行的验收用例清单（正向 + 边界 + 回归），而非“已完成”一句话

### 阶段 7：知识沉淀

落地后把**可复用**的结论存入记忆：环境约束（哪些工程无编译器/有 Node）、通用组件的引用方约束、工程惯例例外。不记录仅本次有效的细节。

## 贯穿原则（速查）

1. 先读后写：有工程规范（AGENTS.md/README 等）先理解遵循，无规范先扫描归纳工程惯例；未完成现状调研不动代码
2. 契约先行：接口文档先于前端实现
3. 兼容扩展：可选参数 + 缺省值，不改既有签名
4. 破坏性操作显式化：默认安全，覆盖需勾选 + 提示后果
5. 计划批准后再动手（跨端改动）
6. 验证不降级优先：环境缺失先搭环境（见 environment.md），搭不了才静态核查 + 交用户编译命令；静态交付过的用例环境就绪后回补执行
7. 顺手发现的存量缺陷：告知用户、单独处理，不夹带进本次需求

## Prompt 工程范式

### 标准版（常规需求，推荐）

```
需求背景：<需求文档 / 交互稿链接，或一段需求描述>（评估射程以此为准）

落地范围：<前后端 / 仅后端 / 仅前端>，目标工程：<工程名与分支>

宿主约束：<技术栈及版本 / 既有兼容性要求 / 权限与合规要求>

验收环境：<后端部署地址 / 前端页面路由>

请按 fullstack-feature-delivery 七阶段流程落地：

1. 阶段 0-1 先做需求甄别与现状调研：产出「功能点清单 + 隐含决策点（附默认方案）」
   与「已有能力 vs 缺口」，未经我确认不动代码
2. 阶段 2 产出决策完备的实施计划（改动落到具体文件路径），获我批准后再实施
3. 阶段 3-5 按后端 → 接口契约文档 → 前端顺序落地：文档与代码同源，
   通用组件只加可选 props，破坏性操作显式勾选 + 警示后果
4. 阶段 6 给出可执行验收用例（正向/边界/异常/回归），并完成 lint 与类型检查
5. 阶段 7 沉淀可复用结论（环境约束、通用组件约束、工程惯例例外）
```

### 最小版（一句话口头需求）

```
需求：<一句话描述>
请按 fullstack-feature-delivery 流程落地：先甄别隐含决策点给我确认，
再调研现状出计划，批准后前后端实现并给验收用例
```

### 使用要点

- "评估射程以此为准"是范围锁：防止自行扩大/缩小需求范围
- 决策点在阶段 0 一次性集中确认，避免开发中途反复打断用户
- 破坏性操作（覆盖/删除/清空）必须在 Prompt 或阶段 0 中显式提及，不允许默认开启
