# 深度参考：各阶段决策细节与陷阱

## 阶段 0：需求甄别

### 输入形态分流

**形态 A：口头/一句话需求**

信息量最小，隐含决策点最多。动作：复述需求 → 列隐含决策点（附默认方案）→ 一次性集中确认。

**形态 B：需求文档（PRD）**

- 通读全文后提炼功能点清单，每条格式：「动词 + 对象 + 预期结果」（如"批量编辑资产：用户勾选多条后统一修改部分字段，预期仅勾选字段被更新"）
- 回读清单请用户确认理解无偏差——不要跳过回读，PRD 看似详实但双方理解仍可能分叉
- 三类"信号词"重点标注："等"（枚举不完整）、"支持"（程度不明）、"优化"（无验收标准）
- 主动找遗漏：异常分支、边界值、权限控制、并发/重复提交、数据迁移，转为待确认问题
- 非功能需求（性能/兼容/安全）若文档未提，需确认是否有隐性要求

**形态 C：交互稿/原型（axure / html / 设计稿）**

- 按「页面 → 操作 → 数据字段」三要素提取：每个页面有哪些操作入口，每个操作触发什么，展示/编辑哪些字段
- 字段清单要从原型标注中提取完整：字段名、类型、必填性、长度/枚举约束、默认值
- 若同时拿到接口文档：先做接口满足度甄别（功能点 × 接口矩阵，三态：满足/缺失/需确认），后端缺口清单进入阶段 2 计划
- 交互稿没有表达的信息（错误提示、并发、性能）主动列出请用户补充

### 决策点问题清单

逐条过一遍，未确认的必须问用户（或给出默认方案请其确认）：

| 维度 | 问题                               | 常见分叉                                   |
| ---- | ---------------------------------- | ------------------------------------------ |
| 语义 | 编辑是覆盖还是增量？               | PUT 全量 vs PATCH 留空不改                 |
| 语义 | "覆盖更新"是 upsert 还是删了重建？ | 新增+更新 vs truncate+insert               |
| 字段 | 哪些字段允许批量改？               | 全字段 vs 白名单（危险字段如编号一般禁改） |
| 上限 | 单次多少条？                       | 与后端批量 SQL、Excel 行数、超时联动       |
| 触发 | 破坏行为默认开还是显式选？         | 默认安全 + 显式勾选                        |
| 兼容 | 已有调用方是否必须不变？           | 决定新接口 vs 改老接口、可选参数 vs 必填   |
| 幂等 | 重复提交同一操作会怎样？           | 天然幂等（update）vs 需防重（insert）      |

## 阶段 1：现状调研检查单

- [ ] 工程规范文档优先盘点：AGENTS.md、README.md、CONTRIBUTING.md、docs/ 目录、checkstyle/lint/editorconfig 等配置——有则先读慢消化，后续所有代码与其对齐
- [ ] 功能入口与完整调用链（API → 应用服务 → 领域服务 → 数据层/页面组件 → model → 接口）
- [ ] 工程惯例：分层、命名、事务注解写法、参数校验方式、错误码体系、权限校验方式
- [ ] 复用点盘点：本次要动的**通用组件被谁引用**（全局搜引用方，决定扩展方式）
- [ ] 数据库：表结构是否支撑（用最新全量 SQL 脚本核对，不要凭记忆）
- [ ] 既有测试怎么写的（框架、mock 方式、命名）
- [ ] 存量缺陷清单（单独汇报，不夹带）

## 阶段 3：核心设计对照

### 规范优先的两步判定

| 情形                                                  | 动作                                                                                                                                            |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 工程有规范（AGENTS.md/README/CONTRIBUTING/lint 配置） | 先理解再遵循，后续代码与规范对齐；规范与通用实践冲突时以规范为准，明显有害的（如规范导致安全/数据风险）单独提出建议，不强推                     |
| 工程无规范文档                                        | 扫描既有代码归纳惯例（分层结构、命名风格、事务写法、异常处理、日志、测试写法），归纳后遵循执行；归纳结论可征得用户同意后落成 AGENTS.md 反哺工程 |

本节以下内容均为规范未覆盖时的兜底实践。

### 批量更新：patch 语义实现要点

- 入参对象：必填的 ids + 全部可空的字段集合；`null` 表示不改
- 数据层用 selective 更新（如 MyBatis `updateByExampleSelective`），切勿全字段 update 把 null 写库
- 应用层校验前置：去重、数量上限、至少一个修改字段、枚举合法性、目标记录存在性

### 导入覆盖：三种 upsert 策略

| 策略                                 | 适用条件                                | 风险                                 |
| ------------------------------------ | --------------------------------------- | ------------------------------------ |
| 应用层分流（先查再分 insert/update） | 业务键无唯一索引、需要区分新建/更新计数 | 多一次查询；需在同一事务内           |
| `INSERT ... ON DUPLICATE KEY UPDATE` | 业务键有唯一索引、字段映射简单          | 无法区分新建/更新；受索引约束        |
| 删除重建                             | 明确要"以文件为准"且无外键关联          | 丢 id/审计字段，主键变化引发关联断裂 |

**两阶段导入**（业界标准做法）：阶段一全量读 Excel + 校验（格式、必填、重复、枚举），任一失败则整体拒绝、零写入；阶段二事务内统一写库。杜绝"校验到第 100 行失败但前 99 行已落库"的部分写入。

### 向后兼容三手法

1. 可选请求参数（缺省 = 旧行为）
2. 新接口新路径（`/batch-update` 独立于单条 `PUT /{id}`）
3. 响应加字段不加结构变化

反模式：改老接口的必填参数、改字段含义、改默认行为且无开关。

## 阶段 4：接口文档骨架

```
# 功能名-接口文档
元信息：日期 / 后端部署环境 / 前端页面路由
## 接口 N
- 方法 + 完整路径（含网关前缀）
- 请求参数表：字段 | 类型 | 必填 | 约束（长度/枚举/上限） | 说明
- 成功响应样例（真实字段值）
## 错误码与文案对照表（前端据此做 toast 与分支）
## 业务规则（Excel 模板规范、覆盖语义警告、幂等说明）
## 前端交互建议（何时禁用、何时二次确认）
```

原则：**文档与代码同源**。写文档时逐字段核对代码；发现代码缺约束（如长度校验），先补代码再落文档。

## 阶段 5：前端接入检查单

- [ ] 顺序：interface 类型 → model 方法 → 新组件 → 页面接线（类型先行使后续全部有类型保障）
- [ ] 通用组件扩展：新能力全部可选 props；不传 = 行为与扩展前完全一致；逐一回归既有引用方
- [ ] 后端约束前置镜像：上限、长度、枚举在前端同步校验（体验）+ 后端兜底（安全）
- [ ] patch 提交前剔除空值（空字符串/undefined 都不发给后端，避免歧义）
- [ ] 成功后：invalidate 查询缓存 + 清空勾选 + 关闭弹窗；失败保持弹窗与已填内容
- [ ] 破坏性选项：Checkbox 显式勾选 + 后果文案（如"留空的选填列会被清空"）

## 阶段 6：验收用例设计

至少四类：正向主流程、边界（空选择/超上限/全空提交）、异常（后端报错文案呈现、网络失败）、**回归**（被扩展的通用组件在其他页面的行为不变）。

### 环境受限时的静态核查法（回退手段）

优先路径：先按 [environment.md](environment.md) 探测并就地搭建工具链（Windows/macOS 安装实录见该文件）；确实无法搭建时才用下列回退方法，且环境就绪后必须回补机器验证：

1. 新调用的每个 API（框架注解、工具类方法）在工程既有代码中找到至少一处同款用法比对
2. 所有调用方/被调用方闭环排查（新增方法的重载、签名变更是否影响既有引用）
3. 依赖注入、反射赋值的字段名逐一核对
4. 编译与测试命令显式交给用户执行，并写明预期输出

## 常见陷阱

- 部分写入：流式边读边写库的导入，校验失败必产生脏数据 → 两阶段
- NPE：Excel 空单元格 → 实体字段为 null，`str.length()` 直接炸 → 先判空
- 临时文件泄漏：上传文件用完必须 try-finally 删除
- 前后端约束漂移：前端 maxLength 与后端 @Size 不一致 → 以文档为契约对齐（存量不一致要单独报）
- 覆盖导入清空误会：用户以为"留空=不改"，实际全字段覆盖清空 → UI 警示文案必须明说
