# Shared Troubleshooting Core

本文件是 `personal-local-v1` 与 `managed-agent-v1` 唯一共用的排障主流程。进入本文件前必须先应用 `references/shared/intent-routing.md`、`references/shared/mcp-usage.md` 和 `references/shared/safety-rules.md`；profile 只负责准备运行环境和包装输出，不得复制、改写或跳过本文件中的分类、采证、推断、复审与降级规则。

`managed-chat-v1` 同样执行本核心，运行适配见 `references/shared/managed-chat-v1.md`。下文涉及平台 run、fileId、产物和机器控制块的 managed 专属条款仅指 `managed-agent-v1`；聊天使用原生读取、会话中的事实索引和正文输出，复审按聊天 Profile 执行，不加载 managed-result-contract.md。

进入本流程前，调用方提供所选 profile 的能力报告。入口 Skill 或可信身份不可用时停止；某项证据工具不可用不整体阻断。按当前目标选择已授权的可用渠道，关键证据无法取得时保留进展并受限收口。

## 2. 分类并加载业务 Skill

0. 使用 `references/shared/intent-routing.md` 的共同规则确认当前请求仍处于唯一的 `TROUBLESHOOTING` 路径，并遵守 `references/shared/mcp-usage.md` 的同一 MCP、requestId 和结果复用规则。
1. 使用 profile 预检阶段已经取得的 `get_project_route_catalog` 响应；尚未取得时实际调用一次。首次调用前检查 schema：支持 view 时传 `{"view":"routing"}`，已知问题环境时先按 `SKILL.md` 的环境归一化表生成 `environment`（例如本地化 → `边缘`，CLOUD → `云端`）；仅旧服务未声明 view 时省略该字段。校验 `projects` 是数组，保留返回的 `requestId` 和项目目录；不得按旧的 `categories/total` 结构解析，也不得用旧 run、目录名或模型记忆代替。
2. 具体 URL/标识符先按共享 MCP 规则调用 `resolve_project_candidates`，选中项目后用 `get_project_detail` 补齐完整分类记录再继续。根据问题环境、模块和现象从 `projects[]` 选择项目：
   - 使用 `name`、`description`、`aliases`、`fingerprints` 和 `routeHints` 判断业务匹配，使用 `environmentId/environmentName/routeHints.environments` 区分同名跨环境项目；本地化/边缘的实际环境标识取自目录，不猜测 ID。
   - 唯一匹配：保留 `projectUid` 和完整选中项目，后续提到“分类响应”均指该项目记录。
   - 多个匹配且当前证据不能消歧：请用户补充能够区分项目或环境的最小信息，不取第一条或仅凭同名合并。
   - 目录有效但无匹配：以 `skill_gap` 受限结束；结构非法或工具失败按 `platform_limit` 处理。
   - 代码工具通过该项目的 `projectUid` 选择主仓库，按共享代码规则查询目标集群实际部署记录并传 `ref`；不使用项目 defaultRef 替代部署版本，不传 repositoryId 或混用其他项目。
   - 运行资产从该项目的 `ccloudInfo[]` 选择，`appId` 不再是必有顶层字段。日志目标需要唯一对应的应用记录；信息不足时报告缺口，不把 `projectId` 或 `repositoryId` 当作 `appId`。只做数据库调查时不强制补齐应用信息。
3. 完整读取并执行 `references/shared/knowledge-loading.md`：在本次请求和所选项目内依次尝试 RAG、项目专属知识、项目 Skill，再制定调查计划。业务 Skill 为空时不阻断前两层知识加载；具体 Skill 适配由 Profile 提供，名称只取完整项目记录。共享流程统一处理知识来源、冲突、复用及降级，不改变当前排障模式。
4. 根据已取得的项目知识、业务 Skill、问题和分类元数据形成候选证据目标；优先利用相关权威证据源的能力与覆盖范围选择查询入口。知识说明和历史案例仅是调查线索，必须采集本案证据，不能直接认定根因。
   - 先建立并完成数据证据目标，再决定是否建立代码证据目标。不得因为问题看起来“以代码行为为主”就跳过数据验证。
   - 数据已验证正常、异常已确认但产生机制未解释，或设计/异常判定标准不清时，可以建立定向代码证据目标。
   - 代码证据目标一旦成立，必须按第 1 节读取 `references/shared/code-mcp.md` 和安全规则，使用 projectUid 建立唯一的 `effectiveCodeSource`；仍无法确定目标或代码 MCP 不可用时停止该代码目标并记录缺口，评估其他已授权证据渠道，不得猜测或切换到本地源码。
   - 知识来源为空或失败时，保留已经取得的材料，评估元数据和问题是否足以形成可验证目标；只有实际缺口阻止调查时才按第 7 节受限收口，不将缺少 Skill 本身视为失败。

项目知识与业务 Skill 提供“查什么”、判断规则和可信资源线索；`references/shared/ccloud-cli-tools.md` 等证据工具规则负责“怎么调用”。知识不得覆盖框架的 profile、证据、安全和授权边界。查到时间、调用业务或接口只是事实目标的完成，深入因果链与根因收口仍执行第 4、6、7 节。

### 2.1 全局排查建议：数据优先，代码后置

这是两个 profile 和所有业务 Skill 都必须遵守的默认排查顺序：**优先验证问题相关的数据或状态是否异常；数据正常后调查代码行为；数据异常后可定向追查产生机制。**“数据”包括当前问题直接涉及的业务记录、配置或开关（包括 Apollo `application` namespace）、关联关系、缓存或队列状态，以及真实请求和响应中的值；应以权威数据源、业务 Skill 或已确认的设计规则为判断依据，不以页面现象、模型常识或代码推测代替数据事实。

1. 先明确本次问题的预期数据状态、判定规则、查询对象、时间窗口和关联范围，再建立最小数据证据目标。至少核对相关记录的存在性、完整性、字段值、关联一致性和时序；“数据证据未完成”不等于“数据正常”。
2. 数据证据目标完成后按以下门禁分流：
   - **发现数据异常**：先记录实际异常、影响范围和来源，把它作为当前已确认异常或根因候选；若产生机制尚未解释，围绕该异常追查写入、删除、同步、消费或补偿链路，允许建立相应代码目标；以真实请求、日志、事件或数据关联验证实际发生，不能仅凭源码可能性或数据异常直接宣称根因闭环。
   - **数据已验证正常**：建立代码证据目标，检查代码如何读取、转换、过滤、判断、写入或展示这些已经核实的数据。
   - **设计或异常判定标准不清**：允许先查代码，但代码调查的唯一目的只能是补齐数据模型、预期状态、数据来源或判定规则；标准明确后必须回到数据验证，不能用“已经看过代码”跳过数据检查。
   - **既无法确认设计，也无法从允许的代码证据补齐判定标准**：按 `skill_gap` 或 `input_insufficient` 受限收口，不猜测数据是否正常。
3. 数据目标与代码目标存在前后依赖时必须串行；在数据尚未完成且没有“设计不清”例外时，禁止并行派发代码调查。代码只能回答数据门禁之后仍未解释的问题，不能替代对权威数据源的核验。

## 3. 形成调查计划并维护任务与事实索引

围绕问题建立：

- 候选假设以及各自的支持、反对信号。
- 能改变结论的最小证据。
- 数据库、日志、Apollo 配置、代码或知识的单一证据目标。
- 目标之间的依赖关系和停止条件。

宿主有子 Agent 能力时，可为独立证据目标使用 collect；单一目标可以由主控直接采集，不强制最少 collect 数量。collect 只返回新增事实与缺口；独立 inference 只分析已有证据，发现缺口交还主控取证。复审条件统一见第 6 节。

无依赖目标可以并行，有依赖目标必须串行。禁止为了增加步骤或 Agent 数量而重复查询。除非缺少用户才能提供的关键输入，否则不要求用户审批内部计划。

主控在派发前维护当前调查的任务与事实索引。任务状态只使用 `pending | active | completed | partial | blocked`；managed 将索引绑定当前 run，personal 只在当前会话维护。公共逻辑模型如下，personal 不要求输出机器 JSON：

```text
TaskCapsule
  taskId
  objectiveKey
  objective
  dependencies
  knownFacts: FactRef[]
  sourceConstraints
  deliverable
```

```text
FactRef
  factId
  statement
  source.type
  source.anchor
  source.observedAt
```

执行以下复用规则：

1. 派发前检查 `objectiveKey`、依赖和已有 FactRef。已完成任务的来源化事实仍适用且足以支持后续分析时，复用事实及来源锚点，不得重复派发同一目标或重新传递已有完整结果。
2. 相似目标用于事实冲突、来源失效、用户输入变化或 review 明确要求的必要交叉验证时，创建独立 `taskId` 并记录目的，不得自动阻断。
3. 主控只传目标、边界、真正必要的 FactRef、允许来源和交付要求；不得默认复制完整问题历史、其他 Agent 原文、无界工具结果或无关事实。不得使用固定字符数、事实数或 token 上限做有损截断，完成任务所必需的信息必须保留。
4. 子 Agent 只返回本任务新增的来源化原子事实、缺口和角色结果；不重复回灌问题背景、knownFacts、完整日志、SQL 返回或源码正文。输入不足时明确返回 gap，不猜测。
5. 主控或宿主不得把费用、预算、剩余额度、命中率、收益目标或是否继续的成本决策附加到任务胶囊；子 Agent 只完成业务任务。
6. 复用只消除已证明的重复工作。不得新增 Agent 数量、并发、回合或工具调用限制，不得改变业务 Skill 的证据顺序、成功条件或独立复审要求。

## 4. 沿因果链递归推进

排查不是找到第一个报错点就停止。维护一条可审计的因果链：

- **因果节点**：当前被解释的可观测异常，如入口请求失败、下游调用超时、线程池排队或数据库响应变慢。
- **因果边**：有证据支持的“上游现象由下游异常直接触发”关系。
- **已访问集合**：记录服务、接口、资源和异常类型的组合，用于识别重复节点与调用环。

从用户现象开始逐跳执行：

1. 每一跳都为当前节点取得能证明它确实发生的最小证据，并区分它是直接触发、候选根因还是尚未定性的现象。
2. 若当前节点仍依赖另一个未解释的异常，提出下一跳问题，例如“下游为什么超时”，并为下一跳建立最小证据目标。
3. 取得下一跳证据后再建立因果边；不能仅凭调用关系、错误文案或时间相邻推断因果。
4. 重复以上过程，直到满足根因资格或命中受限停止条件。不设固定服务层数或固定调查深度。

“调用 xx 服务超时”“RPC 失败”“数据库慢”“缓存不可用”等只解释了上游为什么失败时，属于直接触发或中间原因，不得直接作为根因收口。可操作根因必须同时满足：

- 能解释当前节点及其关键上游现象；
- 有来源化证据，且重要反对证据已处理；
- 不再依赖一个尚未解释、且可继续调查的更深异常；
- 能导出具体修复、缓解或验证动作，而不是只把责任转移给另一个服务。

递归推进受以下边界约束：

- 下一跳已在已访问集合中时，明确报告重复节点和调用环，不循环调查。
- 时间、调用次数、上下文或运行预算不足时，以实际已获证据受限收口，不为追求深度耗尽所有预算。
- 单一证据渠道失败不能立即停止。日志缺失或无权限时，评估仍适用的替代证据候选：指标、分布式链路、源码、数据库状态、Apollo 配置或可复现实验；这些是可用性候选，不改变第 2.1 节的数据优先门禁。源码用于数据正常后的行为解释、已确认异常的成因追查或设计标准补齐；只调用当前 profile 已授权且已完成门禁的工具。
- 替代渠道均不可用、缺失关键用户输入、检测到调用环，或继续调查已不能改变判断时，才按第 7 节输出受限结论，并明确最后确认节点、未知下一跳、已尝试渠道和恢复动作。

## 5. 采集证据

证据必须匹配本案环境、机构/实体、故障时间窗和版本。工具返回的分页、截断、部分失败和缓存状态属于证据限制，不能把不完整查询的“没查到”当成不存在。当前状态不能代替故障时状态；默认分支固定 commit 不等于已匹配部署版本。版本无法对齐时明确标注，避免跨版本闭环。恢复上下文中的任务不是必跑清单；按证据有效性和当前目标重新决定下一步。

- 数据库和日志只能使用 profile 已验证的 ccloud-cli 绝对路径，并严格采用 `references/shared/ccloud-cli-tools.md` 的环境分流、ID 来源和命令格式。
- Apollo 配置只读证据必须先读取并遵守 `references/shared/apollo-config.md`；只使用当前项目已确认的 `apolloAppId` 和目标环境对应地址，不读取或传递完整配置正文。
- 代码调查只使用 `effectiveCodeSource`，必须通过 `aiTroubleShot` MCP 读取和检索源码；每次核对返回的 `projectUid`、`requestedRef` 和 `resolvedCommit`，后续传 `ref=resolvedCommit` 固定快照；版本变化时停止并核对来源，禁止搜索或读取本地副本。
- MCP 入参必须来自当前问题或当前调用的真实返回，不得使用占位值。
- 每条事实必须包含实际观测、脱敏来源锚点和观测时间；事实中禁止混入“可能、推测、应该”等判断。
- SQL 执行前按 `safety-rules.md` 确认表结构，只允许只读查询，并限制返回数量。

单个方向失败时保留其他方向已经取得的有效证据。工具报错后只允许依据已读工具契约修正一次明确的调用错误；不得枚举参数、资产名、集群或地址做盲目试探。

## 6. 推断与独立复审

采证后区分：

- 已确认事实与分析判断。
- 直接触发与更深层根因。
- 支持证据、反对证据和仍未排除的候选。

只有存在竞争假设、跨来源冲突，或事实只能确定直接触发时才执行独立 inference；权威证据已经直接闭环时跳过 inference。

任何准备输出 `concluded` 的结果都必须经过独立复审。review 必须反问“下游异常为什么发生、当前根因是否还能被更深原因解释”，并检查关键事实来源、逻辑跳跃、直接触发与根因混淆、未排除候选和会改变结论的证据缺口。仅把故障定位到另一个服务不能通过复审。复审要求补证时，只补采一个明确目标一次；仍不能通过则降低结论强度。

“独立复审”由 profile 实现：managed 必须使用独立 review Agent；personal 有子 Agent 时优先使用独立 review Agent，没有时由当前会话切换到对抗立场完成。

## 7. 失败与收口

统一使用以下归因：

- `concluded`：关键证据有来源，根因闭环且独立复审通过。
- `platform_limit`：MCP、ccloud-cli、权限、预算、模型或运行环境导致关键证据不可获得。
- `skill_gap`：工具正常且已执行既定调查，但仍缺少闭环所必需的业务规则、表、接口或判断路径。分类的 `skillName` 为空是正常配置，不自动产生 `skill_gap`，也不得作为限制原因；只有实际调查确认某项业务知识缺口阻止继续或闭环时才使用。
- `input_insufficient`：缺少时间窗口、模块、机构、实体或可定位现象，且不能安全推断。

门禁通过后发生失败时，不得只返回最后一条工具错误。即使不能闭环，也必须保留并输出：

1. 问题摘要。
2. 已执行的排查思路。
3. 已确认事实及来源。
4. 当前能成立的判断和不能成立的判断。
5. 最终失败点、缺失证据和恢复动作。
6. 置信度、限制和排查归因。

工具失败不自动推翻此前的有效证据，也不得把工具报错本身冒充业务根因。

## 8. 公共结果语义

面向人的最终结果至少包含：

- 结论或受限结论。
- 关键证据与来源。
- 分析判断。
- 直接触发与根因。
- 建议动作。
- 复审结果。
- 置信度、限制和排查归因。

profile 只能改变结果的承载形式：personal 直接回复用户；managed 按 `managed-result-contract.md` 先完整输出最小机器控制块，再原样输出相同的人类可读语义。首次排查、补充描述重跑和 checkpoint 恢复均使用同一顺序。
