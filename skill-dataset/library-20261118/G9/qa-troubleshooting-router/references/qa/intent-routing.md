# 双维意图识别规则

本文件是 `qa-troubleshooting-router` 的 QA 模式专属意图分类规则源。它必须与 `references/shared/intent-routing.md` 一起使用：共享文件规定两种模式的通用路由与分类边界，本文件只补充 QA 的项目归属、`questionType` 和 `IntentResult` 语义。managed 的隔离意图适配器与 personal 的本地 Agent 必须执行同一组规则；任何宿主 Prompt 不得另行定义操作类别语义。

## 1. 两个独立维度

- **项目归属**：只在当前 `get_project_route_catalog` 返回的项目集合内形成 `routeState`、`primaryProjectUid`、`candidateProjectUids`、`businessEvidence` 和 `matchedEvidence`。项目证据必须同时回查到用户输入原文和当前目录 `routePath`。
- **操作类型**：描述用户本轮真正想完成的结果，不得用项目名称、领域关键词或候选项目代替。

### 1.1 环境只用于必要的项目消歧

目标环境不是 `IntentResult` 字段，也不是 personal QA 的统一前置门禁。personal 应先完成最小工具门禁并读取当前 `get_project_route_catalog`；在受支持的 QA 操作类型确定后，再按以下规则处理环境：

- 用户明确指向“本地化”或“云端”时，可将其作为当前目录候选的消歧输入，分别固定为 `LOCALIZED` 或 `CLOUD`；同时出现两者、比较两者或表达冲突时，不得擅自选择。
- 当前目录和用户输入已经形成可回查的 `UNIQUE_PROJECT` 时，直接继续，不因输入没有环境表达而追问。若该项目的 `routeHints.environments` 只有一个可信值，可将其作为 personal 的可选内部上下文；没有唯一环境提示也不阻断项目级问答。例如“开放平台”在当前目录中只属于云端项目时，不需要再问本地化还是云端。
- 多个项目候选仍无法唯一确定，且候选的环境提示明确不同、环境答案能够把候选唯一收敛到一个项目时，才询问一次：“请问这个问题属于本地化还是云端环境？”。环境不能唯一消歧时，改问项目/功能的最小区分信息，或按 `GLOBAL_ONLY`/业务级范围继续，不要为了补齐环境字段而追问。
- 只有后续操作明确依赖环境专属资料时，才在该操作分支询问所需环境；Apollo 的 `fat|pro` 仍按共享 Apollo 规则单独确认，不能用 `LOCALIZED|CLOUD` 代替。

不得从项目名称本身、仓库路径、客户现场、私有化、线上/测试/生产、MCP 地址、历史问题或模型常识推断环境；环境上下文只能来自用户明确表达或当前项目目录的可信 `routeHints.environments`。环境输入或目录提示始终不能替代当前 `get_project_route_catalog` 的项目证据，也不得向严格 `IntentResult` 增加 `environment`、`deploymentEnvironment` 或其他字段。

## 2. 操作类型闭集

| questionType | 用户真正要完成的结果 | 边界示例 |
|---|---|---|
| `CAPABILITY_DISCOVERY` | 判断某能力是否存在、由哪个基础服务承载、能力目录在哪里；解释项目知识、整理常见问题与排查路径；查询已知项目元数据或明确 Apollo 环境中的指定只读配置 | “边缘 UC 常见问题怎么排查？”“云端测试环境 UC 的 Apollo appId 是什么？”“云端课表 fat 数据库地址是什么？” |
| `CAPABILITY_INTEGRATION` | 理解并接入一个已知能力，包括接口、参数、版本、流程或约束 | “滑动验证怎么接？”“这个方法哪个版本支持？” |
| `SCENARIO_FEASIBILITY` | 评估一个业务场景的方案、流程与基础服务能力是否可行 | “限定教室查课节应该怎么设计？” |
| `RESPONSIBILITY_ROUTING` | 找维护人、责任团队、联系人、已知项目的责任边界或资料入口 | “开放平台谁维护？”“管理后台链接在哪？” |
| `OUT_OF_SCOPE` | 问题排查、实时诊断、账号恢复、非配置类数据代查、执行修复、配置修改、完整配置导出、无界查询及其他非四类操作 | “接口为什么超时，帮我排查”“把误注销账号恢复” |
| `UNKNOWN` | 看似可能属于四类知识问答，但信息不足以唯一判断操作类型 | 只有项目名或含糊的“帮我看看” |

只有前四类属于统一 Skill 的 QA 模式支持范围。

## 3. 分类优先级与重叠消解

1. 显式的问题排查、实时诊断、账号恢复、非配置类数据代查或执行型诉求优先归为 `OUT_OF_SCOPE`，即使输入包含可识别项目或顺带询问能力；配置修改、完整配置导出和无界查询同样归为 `OUT_OF_SCOPE`。
2. 明确查询单一项目、单一 Apollo 环境中的指定配置键或有限配置项，归 `CAPABILITY_DISCOVERY` 的配置查询分支；不得将其扩大为完整配置导出或任意数据查询。
   查询 Apollo appId 等项目元数据同属能力发现，先读取项目详情已有字段；整理一般排查知识不等于定位某次真实故障，按能力发现读取项目知识。
3. 问“能力是否存在、由哪个技术平台或基础服务承载、能力目录在哪里”归 `CAPABILITY_DISCOVERY`。
4. 问“谁维护、哪个团队负责、联系人是谁、已知项目的责任边界或资料入口在哪里”归 `RESPONSIBILITY_ROUTING`。
5. 不得因为出现“接入、对接、接口、调用、集成、怎么做”等通用动作词就自动归为 `CAPABILITY_INTEGRATION`；必须以用户最终交付结果为准。
6. 多个受支持目标同时出现时选择主要交付结果；无法唯一选择时归为 `UNKNOWN`，只提出一个能区分类别的最小澄清问题，不得加载多份操作提示词。

## 4. IntentResult 约束

输出只包含 `contractVersion`、`requestId`、`routeState`、`primaryProjectUid`、`candidateProjectUids`、`businessEvidence`、`matchedEvidence`、`questionType` 和 `reason`。不得加入业务 ID、Skill、知识库、凭证或任意资源选择字段。

项目候选必须来自本次实时目录。无法建立可追溯且能区分项目的证据时，使用符合现有路由契约的 `GLOBAL_ONLY`、`UNKNOWN` 或冲突状态，不得依赖模型记忆、目录扫描、历史会话或相似名称猜测唯一项目。

## 5. 确定性标识与语义证据

- 代码仓库、鲸云应用、项目入口等明确资源标识使用确定性匹配；不要把自然语言问题作为这些字段的匹配值。
- 项目名称、描述、自然语言别名、功能特征和职责相关字段由模型结合完整问题和候选项目进行语义识别。`inputSignal` 保留用户实际表达，不必是目录字段的字面子串；后端只核验引用字段合法且有内容，不重复判断语义。
- “用户看不见课表”应结合异常对象、业务动作与项目职责判断，不得仅因“用户”一词选择用户中心。初始项目选择不代表根因归属；证据不足时保留多候选或不确定结果。
