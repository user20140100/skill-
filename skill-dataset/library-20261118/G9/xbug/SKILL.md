# CVTE Jira xbug 抓取与分析（/xbug）

本技能通过聊天中的 **`/xbug`** 显式调用（已关闭自动触发，避免误跑 Jira/解压流程）。调用后请用户**在同一消息或下一条**附上 Jira 链接或工单 KEY。

## 触发条件

用户在执行 `/xbug` 后提供 `https://jira.cvte.com/browse/<KEY>` 类链接，或明确给出工单号（如 `ODMAFSALE-805`），并要求：下载 xbug、解压、用大模型分析、产出 Markdown 报告、回写 Jira。

## 前置条件

- 已配置 **MCP Atlassian**（`mcp-atlassian`）或具备等效的 Jira REST 访问能力（账号/Token）。配置方式可与本机 `jira-fix` 技能（`~/.agents/skills/jira-fix/SKILL.md`）中的「配置 MCP Atlassian」章节对齐。
- 工作区根目录下存在 **`log/`** 目录（若不存在则创建）。所有产物放在 `log/` 树下，路径中必须包含 `log` 段。

若无法访问 Jira：说明阻塞原因，并提示用户手动将 zip 放到 `log/<KEY>/`，再继续本地分析步骤。

## 命名与路径约定

- **工单 KEY**：从 URL 解析，例如 `https://jira.cvte.com/browse/ODMAFSALE-805` → `ODMAFSALE-805`。
- **下载目录**：`log/<KEY>/`（zip 原文件可放于此目录下的子目录 `attachments/` 或直接放 `log/<KEY>/`，以不混淆解压结果为原则）。
- **解压目录**：`log/<KEY>/extracted/`（或 `log/<KEY>/xbug/`，任选其一但全程保持一致）。解压后不应破坏已有同名文件；必要时使用独立子目录并记录实际路径。
- **报告文件**：`log/<KEY>/<KEY>问题分析.md`（若用户指定其他文件名，以其为准并仍在 `log/<KEY>/` 下）。

## 工作流程

### 1. 解析工单与拉取元数据

1. 从用户输入提取 **KEY**。
2. 通过 MCP 或 REST 获取：`summary`、`description`、`priority`、`issuetype`、`fixVersions` / `versions` / 自定义「软件版本」字段（以实例为准）、`attachment`、`comment`（可选，用于上下文）。
3. 在附件中筛选 **xbug 包**：名称含 `xbug`、或团队约定的 `*.zip` 日志包；若有多个 zip，全部下载并在报告中列表说明用途。

### 2. 下载 zip 到 `log/<KEY>/`

1. 确保 `log/<KEY>/` 存在：`mkdir -p log/<KEY>`（相对于工作区根目录）。
2. 使用 MCP 提供的「下载附件」能力，或 REST：`GET /rest/api/2/issue/{KEY}?fields=attachment` 取得 `id`、`filename`、`content`（下载 URL），再下载到 `log/<KEY>/`。
3. 记录每个文件的 **本地相对路径** 与 **原始文件名**，写入报告「输入材料」小节。

### 3. 解压

1. 解压到 `log/<KEY>/extracted/`（或已选定的解压根）。
2. 禁止覆盖未确认的重要文件；中文路径注意编码。
3. 若 zip 带密码且未知：在报告与 Jira 备注中说明，并列出需要从附件说明/提交人处获取的信息。

### 4. 时间锚点（可选）

若 zip 文件名含 **4 位时间**（如 `1421.zip`、`..._1421_....zip`），将 `HHMM` 解释为当天 **`HH:MM`**（如 `1421` → `14:21`），在日志检索中优先围绕该时刻前后扩展窗口（如 ±10～30 分钟，按日志密度调整），并在报告中写明采用的窗口与依据。

### 5. 大模型分析（本对话内完成）

按 **问题点** 组织内容；一个工单可有多个问题点。每个问题点必须包含三段，且顺序固定：

1. **日志支撑**：贴关键 log 片段（带文件路径与行号/时间戳若可得），说明为何该片段与 Jira 标题/描述相关。
2. **问题分析**：结合现象、时序、模块，推断失败链路或异常行为；若用了时间锚点，说明如何缩小范围。
3. **代码定位**：在工作区内搜索符号、TAG、进程名、服务名等，给出 **文件路径 + 函数/大致行范围**；必要时继续追读调用链，给出 **根因假设** 与 **修改/验证建议**（标注置信度：高/中/低）。

全篇须与 Jira **标题/描述**对齐；避免无日志支撑的臆测。

### 6. 报告模板（写入 `<KEY>问题分析.md`）

报告开头 **元信息块**（尽量填全，字段名可随 Jira 实际字段调整）：

- 工单 KEY、链接、标题、类型、优先级、状态  
- **软件版本**（来自 `fixVersions`/`versions`/描述/附件名中的版本线索）  
- **问题类型**（缺陷/稳定性/兼容/性能等，结合 issuetype 与描述归纳）  
- 分析时间、分析输入（zip 列表与解压路径）

正文：

- **背景与复现摘要**（来自 Jira + 附件说明）  
- **问题点 1**：日志支撑 → 问题分析 → 代码定位（含根因与建议，可选）  
- **问题点 2**：…  
- **总结**：一句话结论 + 后续行动项（验证步骤、是否需要提 MR、是否需要硬件/驱动配合等）

写作语言：**简体中文**（与用户习惯一致）。

### 7. 同步到 Jira 备注

1. 将报告 **相对路径**（如 `log/<KEY>/<KEY>问题分析.md`）与 **执行摘要（3～8 条 bullet）** 写入 Jira comment。  
2. 若评论长度限制：拆成主评论 + 续评，或只贴摘要并注明「完整报告见仓库路径」。  
3. 勿在备注中粘贴密钥；大段日志用「见本地报告」代替。

## MCP / 工具使用提示

- 优先使用已配置的 **mcp-atlassian** 工具读取工单与附件；具体工具名以当前环境 MCP 描述为准（调用前阅读工具 schema）。  
- 需要 `curl` 下载时，使用 Jira 文档中的 **attachment content** URL，并携带认证。更多 REST 细节见 [reference.md](reference.md)。

## 自检清单

- [ ] zip 已落在 `log/<KEY>/` 下  
- [ ] 解压目录名为工单 KEY 之下级路径，结构清晰  
- [ ] 报告文件名符合 `<KEY>问题分析.md`  
- [ ] 每个问题点均含：日志支撑 → 分析 → 代码定位  
- [ ] 报告头含软件版本、问题类型等元信息  
- [ ] Jira 已添加备注（摘要 + 报告路径）
