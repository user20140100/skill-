# 服务稳定性扫描报告契约

格式版本：3.1。必须读取并复制 [固定报告模板](../assets/report-template.md) 填充。报告只回答扫了什么、现状是什么、未来做什么；**现状与对应行动必须在同一表格同一行内呈现**，让读者无需跨表查找上下文。用户明确指定格式时优先遵从。

## 正文结构

固定两个二级章节，保持模板表格列名，不添加独立现状表和任务表。

1. **扫了什么**：对象、实际扫描内容及完成情况，固定七个检查方向。缺口在同一格简述原因，不能把计划检查写成已检查。
2. **现状与治理建议**：先用一段话说明总体事实与关键边界，再用唯一一张表逐项列出 ID、优先级、问题、现状、要做什么。每行是一个独立问题，现状直接给出对象、关键数值/触发条件和影响，行动针对这一现状。不能只写“优化SQL”“完善告警”等脱离上下文的标题。独立问题不得为了按方向归类而压成一行。

**不输出验收标准、负责人、任务状态或截止日期字段**，也不将删除的字段改写成表后固定段落。扫描完成情况仍用于说明证据覆盖，与任务状态不同。无需健康分、数量统计、置信度等额外字段。

未发现问题的检查方向在第一章保留，不虚构任务；重要已有保障可在第二章表前简述。无治理项时表格填无。复杂机制确有必要时追加简短说明，不逐项重复表格。占位符全部替换，未知不得用空白或0代替。

## 待办必须逐项具体列出

每行只表达一个能够独立执行的动作或一个紧密相连的单点修改。写成“对哪个对象，在什么位置，修改/确认什么”，而不是方向性话术。现状必须提供足以理解动作的上下文；对象未知时明确“从哪些已知日志/调用点识别哪个对象”，不能凭空指定组件或配置。

- 禁止“完善告警闭环”一行打包绑定、业务失败、MQ年龄、STW、无数据与通知。分别列“核对某应用的策略绑定”“增加某链路业务失败指标及策略”“验证某路由的通知送达”等，逐行说明依据；未确认缺失时先核查，不直接要求新增。
- 禁止“补齐GC/STW和池容量取证”一行打包三种问题。按GC取数、具体safepoint原因/发起者、某个池的等待指标分别列出。
- SQL需定位到表/指纹/Mapper方法及访问问题；不同SQL或归档与导出分别成行。线程池需定位池名/工厂方法、拒绝或等待路径。
- 禁止仅写“优化性能”“加强监控”“排查根因”“按SLO治理”。必须说明具体改动或下一项有区分力的查询、输入和预期回答的问题；不要求增加验收标准列。
- 已识别STW时，现状写出原因定位进度及证据边界。根因明确后列对应修复动作；尚有阻塞时，按缺失证据逐项列取证动作，不能只给一条“继续排查STW”。没有发现事件时也不能虚构根因。

## 判断与优先级

- 扫描完成情况：已完成 / 部分完成 / 未完成 / 不适用 / 不在范围。完成不代表健康；GC强制CLI取证失败为未完成，仅部分实例取得证据为部分完成。
- 总体结论：存在稳定性风险 / 当前范围未发现明显风险 / 证据不足，无法判断。有确证问题采用第一项并说明盲区；关键适用项未完成且无确证问题时不能采用第二项。
- P0：已确认正在造成严重用户影响；P1：显著已发生影响或证据充分的高风险路径；P2：条件触发风险、观测短板；P3：影响较小的改进。不能仅凭危险代码模式定P0。

## 事实与证据

现状中自然区分已发生异常、代码/配置风险、观测缺口；未证实上线的代码注明版本限制。关键数值保留单位、窗口及口径，不把样本数当总量、日志条数当失败请求数、CLI报错当服务异常。没有SLO不编造阈值。

告警行说明已有覆盖、需要完善和未验证范围；未核验的策略不能写成已确认缺失。GC/STW/池容量缺口写明取不到什么及其影响，行动说明如何补齐。CLI支持的查询优先实际执行；GC必须CLI取证。

现状就近链接必要证据。实际命令、ID、HEAD/版本/实例、数据完整性、DDL/计划、完整告警矩阵等存于同名 `-evidence/` 目录，以 `index.md` 记录来源、窗口、单位和限制，使用E001起编号。正文不展开整套取证元数据。证据脱敏，不输出凭证和业务明细；关键失败不能藏在附件中。

## 编号与交付

首次使用STAB-001起编号，按P0→P3及同级用户影响排序。只合并同一对象的重复动作；同一根因需要不同修改、不同取证结果时分别成行。已有报告复用仍相同的待办编号，拆出新动作使用新编号并在证据说明中保留原编号关系，不因排序改变编号。共享资源的问题保留实际归属。

交付检查：两个章节、七项扫描齐全；治理表只有模板五列；每行现状可独立理解且与单项具体行动对应，没有多个独立待办打包成话术；重要告警与补证未遗漏；关键事实有证据；链接有效；不将计划写为已实施。不重复输出被删除的管理字段。
