# 组织服务 STW 与线程池耗尽排查经验

来源：用户提供的组织服务历史排查记录，2026-10-26整理。原始分享地址及访问标识不纳入技能文件。以下为历史案例的方法总结，未独立重新验证其原始日志；不能将当时组件、路径、数值或结论直接套用到待扫描服务。

## 关键案例与可复用判断

| 历史现场 | 证据支持什么 | 不能据此推断什么 |
|---|---|---|
| 一次运行期RedefineClasses暂停约467ms，随后出现拒绝；拒绝后自动ThreadDump又暂停约140ms | 类重定义暂停已发生，时间线支持瞬时拥堵假设；需要追发起者和恢复瞬间负载 | 不能仅因存在APM/Sentinel就锁定发起Agent，不能只凭时间接近证明全部因果 |
| 同一实例此前类重定义多集中启动前几分钟，运行数小时后出现单独长事件 | 应对比启动/运行期及正常时段，追延迟插桩/配置刷新触发条件 | 不能将启动时正常增强统一列为异常，也不能把另一次普通Remark当同一原因 |
| 另一波拒绝时，多数工作线程等待Hikari连接；STW发生在拒绝后的自动抓栈 | 直接堵塞点是连接获取，抓栈停顿是后果 | 尚不能确定哪个SQL、主从池或网络导致连接供不应求 |
| 降低慢SQL筛选阈值后，发现数秒内多次112～406ms的大结果查询 | 高频中等延迟与大结果传输也可能占连接，要核对单实例调用与连接持有时长 | 库侧合计不能当单实例流量，未达500ms不代表无风险；事后慢查询不能解释更早首次拒绝 |
| G1 Remark约291ms，主要是ref-proc约228ms；紧接Cleanup及拒绝，后续ThreadDump又增加暂停 | 可定位到GC具体阶段，GC是高置信触发因素，ThreadDump放大拥堵 | 未定位引用类型和对象持有者，不能宣称找到具体业务对象根因；没有FGC也可能长停顿 |
| 某次300个工作线程中299个等同一个PrintStream锁、1个持锁写输出；STW在拒绝后 | 同步异常打印锁是直接阻塞机制，应查实际Agent异常与输出链路 | 不能沿用此前GC/慢SQL结论；无历史时间戳的当前NPE不是逐条历史因果证据 |

## 根因定位的层次

1. **现象**：请求超时、拒绝或暂停指标尖峰。
2. **直接机制**：具体safepoint操作、GC阶段、连接池等待或共享输出锁。
3. **触发来源**：哪个版本的Agent、哪个调用点/配置事件、哪类引用/持有者、哪个池和SQL/事务路径。
4. **影响链**：触发在拒绝之前还是之后；流量/容量如何共同作用；正常时段反例能否排除替代解释。

只完成第二层时，不能写已完成全部根因定位。案例对类重定义发起者和GC引用对象仍保留未知，Skill应继承这种证据边界，继续给出具体追查路径。

## 取证方法

- 用同实例GC、安全点日志与故障自动快照重建毫秒级时间线；检查日志时间、JVM uptime、轮转和截断。
- 通过启动参数、JAR版本、栈内完整包名核对真正运行组件。业务Sentinel适配器和平台Sentinel插桩Agent可能是不同制品。
- 优先查操作审计、动态配置和候选Agent源码调用点；已排除人工Arthas时追自动重转换逻辑。
- 在实际Instrumentation调用点记录时间、目标类、ClassLoader、线程和发起栈，比业务层加慢日志更接近来源。新加日志只抓未来事件，不能重建早已消失的栈。
- 文件类型需确认：Dubbo_JStack是线程dump，不能用于计算引用对象数量；已有hprof也不直接证明历史ref-proc耗时来源。
- 不以增大Dubbo线程池、增大堆或关闭全部Agent作为通用结论；治理动作跟随已定位机制。
