# STW：异常停顿与根因定位

规则 ID：STW-01 长 safepoint/暂停；STW-02 运行期类重转换/插桩来源；STW-03 停顿与业务拥堵的因果链。

执行本规则前读取 [组织服务排查经验](stw-investigation-experience.md)。目标是尽可能定位到**什么操作暂停了 JVM、为何在这个时刻触发、哪个组件/对象导致耗时、它与业务异常是什么关系**。只发现 STW 曲线或只列“建议排查”不算完成根因定位；证据不足时必须明确卡在哪一层，不能编造结论。

## 1. CLI 定位实例与事件

首先使用 ccloud-cli，具体参数按当前 help：

- `observe logs/logs-count`：按绝对时间、目标实例查询首次业务超时/拒绝与暂停事件，确认日志存储字段、原始时区和覆盖。不要把日志条数当请求数。
- `observe metrics-list` → `metrics`：只查询实际目录返回的暂停、CPU限流、请求量与池等待指标；目录没暴露或报错要记录，不假设一定支持GC明细。
- `app pods/detail/comprehensive`：核实实例身份、启动时间、发布版本、JDK/收集器、实际返回的JVM/Agent配置。不输出凭证。
- 优先读取已采集的GC、安全点、Agent日志和故障时自动保存的线程快照。GC数据必须经CLI取证，不以APM截图替代。

已有平台文件位置可作为发现线索，例如 `/app/psdcloud/jvm-gc.log`、`/app/psdcloud/safepoint.log`、`/app/Dubbo_JStack.log.<时间>`；**这些是历史案例路径，不是每个服务都有的保证**，需核对目标实例的配置或实际文件。覆盖日志轮转及故障时间，检查文件是否截断。

如果证据仅在容器内，遵循 `ccloud-runtime-debug` 的容器执行与授权要求，使用当前CLI支持的一次性、有界只读命令读取已有文件；本技能不额外授权容器执行。不能为扫描自行触发jstack、GC、heap dump、动态attach或类重转换。受此边界阻塞时，把确切文件、目标实例、所需窗口写入取证待办，不泛称“缺监控”。

## 2. 先建立时间线，再判定方向

按每个实例分别记录：JVM启动/发布 → 首次异常前的暂停 → 首次拒绝/超时 → 自动ThreadDump等诊断 → 恢复。保留事件起止、uptime、原因、持续时间及时间精度；区分到达安全点时间（TTSP）与安全点内操作耗时。已有日志字段不能推算的值保持未知。

必须区分：

- 暂停先发生：可能导致积压，仍要结合流量、队列与连接占用判断，不单凭时间邻近定因果。
- 拒绝先发生、ThreadDump后发生：抓栈停顿是后果或放大因素，不可倒因为初始诱因。
- 线程大量等待连接或锁，但无对应JVM全局暂停证据：按连接池/锁阻塞继续排查，不把普通线程阻塞称为STW。

请求P99尖峰、进程CPU降低、Trace缺口都不能单独证明STW。GC累计耗时或类重转换API耗时也不直接等于暂停时长。

## 3. 分支定位到具体机制与来源

### A. RedefineClasses / 类重转换

1. 由safepoint原始记录确认直接VM操作、时长和发生时uptime。`RedefineClasses` 名称不能区分上层redefine还是retransform调用。
2. 查询同一时刻的诊断/热更新操作审计、Agent配置变更及日志；用户已明确排除人工操作时，不反复要求确认Arthas，转查自动Agent路径。
3. 核对线上实际Agent JAR版本、插件列表、启动参数、线程快照中的完整包名；再定位匹配版本的源码。包名/制品不同的业务适配器不能代替真正的插桩Agent；某类出现在栈里仅证明参与调用，不能证明它发起重转换。
4. 搜索 `retransformClasses`、`redefineClasses`、Instrumentation、AgentBuilder等调用/安装点，追踪延迟插桩、首次类加载、动态配置刷新、插件启停的具体触发条件，与运行期事件对齐。不要只枚举“可能是APM或Sentinel”。
5. 如果日志无法追溯发起者，列具体观测改动：在已定位候选Agent的Instrumentation调用点记录开始/结束、线程、类名/ClassLoader及发起栈；限制日志量，避免输出字节码。普通业务AOP和事后jstack通常无法找回已结束的发起栈。
6. 只有无法修改候选Agent时才把启动期观察型Transformer作为后续方案：正确注册重转换支持，识别 `classBeingRedefined != null`、返回null不改字节码，并说明回调栈不保证完整归因。新增Agent属于后续变更，先验证兼容与开销，不在扫描中安装。

最终区分“已确认类重定义暂停”“发起组件/目标类已确认或尚未知”“业务拥堵是否由它触发”，不能合成一个未经证明的APM根因。

### B. GC / CGC_Operation

1. 将safepoint与同一实例GC事件对齐，确认收集器、具体阶段（Young、Remark、Cleanup等），不能只看Full GC次数。G1 Remark可能产生长STW而没有FGC。
2. 分解可用的阶段耗时：引用处理、类卸载等；对比正常时段与启动期，查看回收前后占用与后续Mixed GC效果。不能因一次长暂停就判断内存泄漏或建议扩大堆。
3. 若慢在引用处理，继续查已采集的Soft/Weak/Final/Phantom引用数量/阶段耗时、相关JVM配置与已有对象分配证据。缺数据时明确补何种统计、要区分“引用积累过多”还是“处理效率问题”。
4. 有现成且时间匹配的堆dump时才按授权离线分析数量、引用链和持有者；线程dump不能代替堆dump，堆dump本身也不能还原历史某阶段的全部耗时。没有对象级证据，不点名某业务缓存为根因。

定位停在ref-proc时要明确“具体引用类型/持有者未定位”，继续制定有针对性的取证动作，不能写“GC导致，调参解决”。

### C. 连接等待、同步打印锁及其他拥堵

使用故障当时已有线程快照，按状态、相同锁对象/持有线程、完整调用链统计各类线程。区分拒绝瞬间和恢复后快照，后者不能还原当时active精确值。

- Hikari `ConcurrentBag.borrow`：确认哪个池、active/idle/pending、获取/持有时间，再查SQL频次、结果量、锁/网络与事务。慢日志阈值可能漏掉高频百毫秒查询；没有超过500ms的SQL不排除连接耗尽。不能以连接等待直接证明慢SQL根因。
- PrintStream/日志锁：确认等待锁与持有者，沿调用链定位同步printStackTrace或输出写入，核对异常来源与日志采集背压。当前无时间戳的异常只能作线索，不能直接覆盖历史时刻。
- CPU throttling、宿主机调度、网络或下游阻塞按实际证据排查，避免把不同事件都归因于上次已修复的问题。

这些分支可能说明STW只是后续取证开销，应在现状中明确纠正因果方向。

## 4. 做正常时段与跨实例对照

汇总同一JVM有效窗口内全部相关操作，区分启动预热与持续运行期：次数、暂停分布、最长事件、发生后是否拒绝。再对比相同版本其他实例、相似流量下没有报错的同类停顿、相似拒绝但没有长暂停的事件。没有可比事件就明确缺少反例，不能假设所有停顿必然导致拒绝。

异常阈值取服务目标与自身基线，不把案例中的毫秒值设为全局标准。发布/实例重启改变窗口时重新对齐，不跨实例做累计计数差分。

## 5. 根因与待办输出

原始时间线、操作分布、线程分类和候选排除依据放入证据附件。正文“现状”必须简明说明：**事件/直接机制 + 触发来源定位结果 + 用户影响链及仍缺的证据**。

已定位则给出具体组件/代码位置的修复动作。未闭环时写“根因未定位完成”，给出已知原因、尚缺的一项关键证据以及明确的查询/日志改动对象；按独立动作分行，不用“补GC/STW/池监控”打包。证据不足不算通过，也不能为了满足根因要求强行归因。
