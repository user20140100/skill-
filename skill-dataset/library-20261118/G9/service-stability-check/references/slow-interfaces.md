# API：高频慢接口

规则 ID：API-01 高频且慢；API-02 尾延迟/错误突增；API-03 放大调用与超时链。

使用 observe transactions 分别按 p99、tpm、errorRate 排名，合并候选接口；通过 metrics-list 的 transactionMetrics 与 transaction-metrics 读取精确接口的时间序列。阈值取服务/接口 SLO，不把全部接口共用 500ms 当成既定标准。

接口名来自返回值，不猜测。HTTP 按路由模板聚合，避免带用户 ID 的 URL 分散基数；RPC 区分方法与调用方向。入口 access log 不能代替内部 RPC 覆盖，Trace 采样不代表全量。

区分三种证据：

- 请求量与 p99 同时高：可确定为高流量尾延迟风险，但不能推算超过阈值的请求次数。
- 有完整直方图/合规全量计数：才计算慢请求次数与比例，明确阈值、分母与窗口。
- 仅慢 Trace 样本：用于定位调用链，不能证明高频、全量占比或全局 p99。

对候选接口用 traces → trace-detail 定位 SQL、下游、排队、锁、序列化等耗时段，再扫描对应代码的 N+1、同步串行调用、重复远程请求、缓存击穿、大响应和无界批量。Trace detail 可能只保留目标应用节点，缺失的外部节点不能当成没有下游。

按“用户影响+频率+累计成本”排优先级，避免只追一次最慢请求。不同实例/版本、正常业务峰值、低样本误差均需记录。

验收：代表流量下接口 P95/P99/错误率满足目标、慢请求计数下降、无下游调用或重试放大；结果正确。没有全量指标时单列观测待办，不编造频次。
