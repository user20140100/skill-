# GC：FGC、高频 YGC 与内存趋势

规则 ID：GC-01 老年代/Full GC；GC-02 年轻代频率与耗时；GC-03 回收后存活集增长。

## 必须使用 ccloud-cli 取证

GC 信息必须使用 ccloud-cli 获取，不以 computer-use、Grafana 或 APM 页面作为替代取数渠道。

1. 通过 `ccloud-cli observe metrics-list` 发现目标应用可用的 GC、堆、老年代、分配、CPU 指标，再通过 `ccloud-cli observe metrics` 查询。参数、跨鲸云路由和时间窗口遵循 [取证与工具](evidence-and-tools.md)，指标 ID 只取实际目录返回值。
2. 必要时通过 ccloud-cli 日志能力读取已采集的 GC 日志；JVM 参数、Pod 启动时间和发布版本也经 CLI 的只读能力确认。应用日志没有 GC 关键字不代表完整 GC 日志无事件。
3. 保存脱敏命令、目标应用/实例、绝对窗口、指标定义/单位、CLI 返回或失败信息，区分成功取得的数据与尚未覆盖的实例。
4. 接口错误、权限报错或能力不可用时，按 CLI 技能核对身份与目标路由后停止重复请求，报告标记“GC 检测未完成”，列出修复工具/补齐访问或指标的待办；错误原因尚未证实时不直接断言用户缺权限，已知 CLI bug 标为工具阻塞。不转用浏览器，不猜测指标 ID，也不以截图汇总值替代 CLI 证据。目录没有 FGC/YGC 指标时，不把缺失解释成零。

保留 GC 算法/JDK 版本；缺少元数据时明确标记未知。

## 判定

- 明确曲线是累计计数、累计耗时、窗口计数还是速率。累计 counter 用相邻差分除以实际时间；重启/计数器重置不记为负 GC，不跨实例做差。
- 计算适用的每实例 FGC/YGC 频率、暂停耗时/观测时间、最长暂停、回收前后堆与存活集趋势，关联请求量、分配速率、错误率和延迟。累计 GC time 未必全为 STW，先核对指标定义。
- 按收集器解释事件：G1 mixed/concurrent cycle 不能一概标 FGC，ZGC/Shenandoah 的周期/并发耗时不能直接当停顿。
- 区分启动预热和持续运行期。单次 Full GC 可提示复核原因，但无影响证据不能自动升级为严重事故；高频 YGC 也需结合堆大小、分配速率、暂停和 SLO 判断。
- 使用现有 SLO 和基线决定异常，记录阈值与依据；不预设“每分钟 X 次必定有风险”。

代码回溯：大对象/批量集合、缓存无界、重复反序列化、请求并发放大、显式 System.gc、堆与容器内存预算不匹配。仅凭这些代码模式只能标潜在风险，不能断言内存泄漏。

治理与验收：明确减少何种分配/存活、限制何种批量或调整何种预算；代表峰值下 GC 暂停与接口 SLO 达标、回收后存活集稳定。参数调整属于后续变更，不主动触发 GC/heap dump。
