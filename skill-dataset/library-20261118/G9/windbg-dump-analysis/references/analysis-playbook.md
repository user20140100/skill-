# 分析 Playbook

> Step 3 的参考。通用反向推理方法论 + 崩溃路径 + 挂起路径 + 分级。
> 方法论提炼自一份 C++ 对象生命周期崩溃复盘（飞书 wiki `ANYSwegrQiOHm6kJL4mc2v0anrc`），但推理结构适用于所有类型崩溃与死锁。

## 核心洞察：现场能直接告诉我们的往往很少

复杂问题的现场看起来"信息齐全"，但真正能直接读出来的很少：

**崩溃**：崩在哪个线程、抛异常的是哪个函数、异常类型。**没有的**：业务代码帧（栈顶全是运行时 / asio / std）、具体错误描述（`system_error` 是泛型）、状态为什么无效。

**挂起**：哪些线程在等待、等什么。**没有的**：哪个是因哪个是果、等待关系里的环在哪、是死锁还是死循环还是资源耗尽。

现场离真正的 bug 隔了十万八千里，**栈 / 线程状态不会直接指过去**。

## 通用反向推理链

不论崩溃还是挂起，都用同一条推理结构：

```text
1. 现象是什么？
   崩溃：异常码 / 异常类型 / 崩溃点
   挂起：线程状态 / 等待关系

2. 该现象在什么前提下发生？（语义层，不涉及具体代码）
   例：io_context::run() 抛 system_error → io_context 状态无效
   例：线程 T1 等 T2 持有的锁 → T2 也在等 T1 持有的锁

3. 什么代码结构能造成该前提？（模式匹配 → 查 crash-deadlock-patterns.md）
   例：状态无效 → 没构造完 / 正被析构
   例：互等 → 锁获取顺序不一致成环

4. 在当前代码里验证哪个结构成立
   → 回到版本对齐后的源码，定位具体结构
```

每一步都是"在什么前提下 X 会发生"，顺着问号往回推，直到回到代码里能定位的具体结构。

## 崩溃路径

跑 `!analyze -v` 拿异常码，按异常码选锚点：

### 0xC0000005 访问违规（最常见）

看 `!analyze -v` 的 faulting address：

| faulting address | 含义 | 推理方向 |
|------------------|------|----------|
| `0` / 小值 | 空指针解引用 | 指针未初始化 / 已被置空仍用 |
| 已释放地址 | UAF（use-after-free） | 对象生命周期：析构后仍被回调访问 |
| 结构体成员小偏移 | 成员越界 / 对象类型错误 | 数组越界 / 错误 downcast |

`.ecxr` 切异常上下文后 `k`，`!heap -p -a <addr>` 查地址所属堆块。

### 0xC0000374 堆破坏

⚠️ **崩溃点通常不是破坏点**。堆被破坏后，后续堆操作才触发异常。需用 PageHeap 复现，让崩溃点 = 破坏点：

```bash
gflags /p /enable <process>.exe /full   # 启用 PageHeap
# 复现后崩溃点即真正的破坏点
```

推理方向：缓冲区越界写 / double free / 释放后写。

### 0xC00000FD 栈溢出

看栈深度，找无限递归 / 栈上大对象 / 线程栈过小。

### C++ 异常 → terminate → abort

```
!analyze -v; .exr -1; k
```

`.exr -1` 看异常对象类型。推理方向：哪个线程抛了未捕获异常 → 边界 catch 缺失（放大器，见下）。**接住 ≠ 修好**——找到为什么抛异常才是根因。

### 现场信息少（栈顶全是运行时帧 / 泛型异常）

走完整反向推理链。典型场景：`io_context::run()` 抛 `system_error`、`std::thread` 析构异常、纯运行时帧崩溃。

→ 对照 [`crash-deadlock-patterns.md`](crash-deadlock-patterns.md) 的并发时序类 / 资源生命周期类模式。

## 挂起路径

挂起没有异常码，从**所有线程状态**出发。

### 1. 列所有线程栈

```
~*k
```

找处于等待状态的线程：`WaitForSingleObject` / `EnterCriticalSection` / `Sleep` / `recv` 等。记录每个等待线程在等什么资源、谁持有。

### 2. 查锁状态找环

```
!locks
```

`!locks` 列出所有临界区及 `OwningThread`。结合 `~*k` 构造等待图：

```
T1 持有 L1，等 L2
T2 持有 L2，等 L1
→ 环 = 死锁
```

→ 对照 [`crash-deadlock-patterns.md`](crash-deadlock-patterns.md) 的锁死锁模式。

### 3. 区分死锁 / 死循环 / 资源耗尽

```
!runaway
```

| 现象 | 判定 | 推理方向 |
|------|------|----------|
| 全部线程 idle，CPU 低 | 死锁 / 阻塞 | 找等待环 / 阻塞源 |
| 某线程 CPU 占满 | 死循环 / 活锁 | 该线程栈找循环 |
| 无明显 CPU 占用但响应慢 | 资源耗尽 | `!handle` / `!heap -s` 看句柄 / 内存 |

资源耗尽：`!handle`（句柄）、`!heap -s`（堆）、`!peb`（进程环境块）。→ 对照资源耗尽模式。

## 放大器识别：缺边界 catch

`_CxxThrowException` 之后直接 `terminate → abort`，没有 catch 帧兜住 → 工作线程 lambda 没包 `try/catch`。

```cpp
// ❌ 放大器：异常无人接住 → 进程崩溃
thread_([this]{ while(is_running_) ioc_.run(); });

// ✅ 止血：接住异常，进程不崩
thread_([this]{
    while(is_running_) {
        try { ioc_.run(); }
        catch(const std::exception&) { /* log */ }
    }
});
```

⚠️ **接住异常 ≠ 修好根因**。`try/catch` 只是止血，真正的修复是根因治理。缺边界 catch 是把"可恢复异常"放大成"进程崩溃"的放大器。

## 验证原则

时序 / 并发问题（UB、死锁）依赖时序，开发机上 99% 不出事，只在特定时序下命中。因此：

- **"改完跑几遍没崩 / 不卡"不能证明修复成立**
- 必须能从代码层面讲清根因：为什么这个结构会在某时序下出问题，修复后为什么不会
- 理想情况附 dump / 快照 + 根因推导，而非"我改了试试"

## 分级判定与各档动作

| 档位 | 判定 | 动作 |
|------|------|------|
| 简单 | 现场直接指向问题 | 直接定位 → 修复 |
| 中等 | 部分线索，需多步命令 | 系统化分析 → 修复 |
| 复杂 | 现场信息少 | 走反向推理链 → 给思路，不直接修 |

## 复杂档输出模板

复杂档**不直接修**，输出分析思路让用户确认方向：

````markdown
### 复杂问题分析：[摘要]

**1. 现场能直接读出的**
- 类型：崩溃 / 挂起
- 关键：异常码 / 崩溃栈，或 线程状态 / 等待关系
- 现场缺什么：无业务帧 / 泛型异常 / 等待关系不明

**2. 反向推理链**
- 现象 → 前提 → 代码结构（→ 查 crash-deadlock-patterns.md）

**3. 假设（按可能性排序）**
- H1（高）：... → 验证方法
- H2（中）：... → 验证方法
- H3（低）：...

**4. 验证方案**
- 静态：查代码定位结构
- 动态：动态插桩（日志 / 埋点）/ PageHeap 复现 / 多次取快照对比

**5. 建议修复方向**（等用户确认后再改）
- 若 H1 成立：...
- 若 H2 成立：...
````
