# 门牌日志问题诊断

使用本 Skill 分析门牌应用业务日志时，先判断材料的实际覆盖范围，再建立可复核的事件链路。不要仅根据异常关键词、单条 HTTP 日志或某个业务关键词判断根因。

## 覆盖范围

当前版本覆盖门禁与开门上报、考勤与签到、人脸认证、同步与配置、节目与展示。领域手册是此 Skill 的维护产物；docs 目录中的分析报告和建设记录是独立文档，不作为运行此 Skill 的必需依赖。

## 先判断材料能回答什么

在选择业务领域前，先完成以下快速分流：

1. 确认日志产物类型、实际时间范围、包名/进程和是否跨重启或校时。日志来源、XLog、logcat 和 HTTP 覆盖范围不确定时，先读 [日志采集与可观测性](references/shared/observability-and-log-collection.md)。`data/log_boot` 等系统启动快照未包含应用 XLog，只能说明该快照未覆盖 XLog，不能证明应用未打点。
2. 阅读 [分析契约](references/analysis-contract.md)，收集版本、时区、期望与实际结果、原始日志位置和可用关联键。历史日志版本不明或不同于代码基线时，当前源码只能用于解释或对照。
3. 判断材料属于哪种分析模式：
   - **运行链路分析：** 有用户操作或自动任务前后的连续日志，按领域手册建立时间线。
   - **跨域链路分析：** 一个领域是入口、另一个领域是副作用或前置条件，按真实因果顺序读取多个手册。
   - **覆盖范围分析：** 只有启动、导出或系统快照，先说明可覆盖的初始化/同步链路和未覆盖的业务操作；不要补造领域结论。
   - **代码对照分析：** 缺少运行证据时，只输出代码事实、可能解释和最小补充取证，不输出历史运行结论。

关键节点不在当前日志覆盖范围内时，结论应止于“最早可见节点”或“材料未覆盖”，而不是继续把推断升级为根因。

## 选择领域手册

根据用户入口和最终副作用选择主领域，而不是只按 TAG 或异常关键词路由：

- 开门、门锁、opened、开门图片、IoT 开门：主读 [门禁与开门上报](references/domains/access-control.md)
- 打卡、考勤记录、课程签到、签到图片、考勤联动：主读 [考勤与签到](references/domains/attendance-and-sign.md)
- 相机、人脸识别、人脸特征同步、用户识别回调：主读 [人脸认证](references/domains/face-authentication.md)
- refreshAll、rebind、绑定、配置、模板、同步页：主读 [同步与配置](references/domains/sync-and-configuration.md)
- 节目发布、unPublish、Uips、节目顶层展示、播放或资源下载：主读 [节目与展示](references/domains/program-and-display.md)

以下组合通常需要联合阅读，但仍要以日志中的实际因果关系为准：

| 问题表现 | 主领域 → 联合领域 |
| --- | --- |
| 人脸识别后门未开或没有开门上报 | 人脸认证 → 门禁与开门上报 → 设备与 IoT |
| 人脸考勤、签到图片或记录缺失 | 考勤与签到 → 人脸认证 / 网络与 API |
| 刷新、绑定后节目或配置没有生效 | 同步与配置 → 节目与展示 / 生命周期与协程 |
| 任务已落库但服务端没有事件 | 门禁与开门上报 → 持久化与重试 → 网络与 API |

不要因同一人脸识别回调、相邻时间戳或相同用户标识，就把开门、考勤和签到自动归为同一笔业务。

## 建立和验证链路

1. 以用户可感知的入口或自动任务触发为起点，选定一个窄时间窗；先按强关联键匹配，缺少强键时明确弱关联的误配风险。
2. 从主领域手册列出期望节点，在日志中逐一记录“出现、未出现或材料不覆盖”；多次操作、重启或 PID 变化时拆成独立事件链。
3. 仅在链路触及相应边界时读取公共参考：
   - HTTP、服务端业务码或 CStore：[network-and-api.md](references/shared/network-and-api.md)
   - 页面退出、协程取消、异步上传：[lifecycle-and-coroutines.md](references/shared/lifecycle-and-coroutines.md)
   - Room 任务、重试、重启或解绑：[persistence-and-retry.md](references/shared/persistence-and-retry.md)
   - IoT 指令、硬件回调、开门状态：[device-and-iot.md](references/shared/device-and-iot.md)
4. 对异步和外部调用分别确认“触发、任务/请求已创建、响应或回调、业务成功、本地状态更新”。某一层成功不等于下一层成功；超时或页面结束也不自动等于底层独立任务停止。
5. 将最早可被日志或目标版本代码直接证实的异常节点定义为断点。后续节点缺失时，保留服务端、硬件、日志等级和版本差异等替代假设，并提出最小补充取证。

## 输出约束

使用 [分析契约](references/analysis-contract.md#报告格式) 的固定报告格式，并在“适用版本与日志时间范围”中同时说明日志产物类型、可见应用进程/时间段和未覆盖的关键节点。

- 结论分别标为“日志事实”“代码事实”“推断”或“待验证项”；当前源码不能直接证明历史版本的运行行为。
- 对 DoorLockReportManager，任务成功落库与网络上报成功是不同节点；前者出现并不代表服务端已经收到事件。
- 原始日志含用户标识、卡号、人脸文件键或请求头时，输出中应脱敏；不要复制完整敏感值。
- 当材料只支持覆盖范围结论时，也按报告格式输出，并把“下一步最小取证”精确到时间窗、TAG、关联键或数据库状态。
