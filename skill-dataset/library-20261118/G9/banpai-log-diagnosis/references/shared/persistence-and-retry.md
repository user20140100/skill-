# 开门上报任务、持久化与重试

开门事件使用 `open_door_report_tasks` 作为 Outbox。代码基线为 `ab680809`，Room 数据库版本为 15。

## 任务状态模型

| 状态/动作 | 持久化记录 | 内存标记 | 可观察证据 |
| --- | --- | --- | --- |
| 已入队 | 插入一条带 UUID `taskId` 的记录 | 无或等待上传 | `enqueue | 任务已落库` |
| 图片上传中 | 记录仍在，`faceFileKey` 可为空 | `uploadingTaskIds` | `uploadFaceImage | 开始上传` |
| 图片上传完成 | 更新 `faceFileKey` | 移除上传标记 | `图片上传成功`；失败则仅移除标记 |
| 正在上报 | 记录仍在 | `reportingTaskIds` | `reportTask | 开始上报` |
| 上报成功 | 删除记录 | 移除上报标记 | `上报成功并删除任务` |
| 上报失败 | 保留记录 | 移除上报标记 | “上报失败，保留任务…”或“请求异常，保留任务” |
| 解绑清理 | 删除所有记录 | 清空所有集合 | `clearData | 解绑会话已清空…` |

记录存在只表示“客户端尚未确认服务端业务成功”，不代表还未发起请求。不要把数据库中有记录简单诊断为“请求从未发送”。

## 选取与重试规则

- DAO 按 `localId DESC` 分页读取，`OpenDoorReportTaskSelector` 再按 `localId DESC` 选出不在上传或上报集合中的任务；较新的可发送任务优先。
- 轮询间隔为 3 秒。一次扫描会逐个处理就绪任务；单条失败不会主动删除其他就绪任务。
- 图片上传失败、图片写入失败或上传异常不会删除任务；移除上传标记后，后续扫描以 `faceFileKey=null` 上报。
- 没有将重试次数、下次重试时间或图片失败原因写入任务表。重启后内存集合丢失，遗留任务可再次进入上报选择。

## 幂等性限制

任务本地 `taskId` 唯一，但当前 `OpenDoorReportRequestBody` 不包含它。若服务端已接收事件而客户端在响应前超时，客户端会保留任务并在后续扫描再次发送；日志只能确认客户端未收到成功响应，不能单独证明服务端是否已经入库。

报告该类问题时，应把“服务端是否按其他业务字段去重”列为待验证项，不要声称客户端实现了端到端恰好一次上报。

## 排查建议

对“开门成功但后台无记录”，按以下顺序缩小范围：

1. 是否出现一次 `enqueue | 任务已落库`？没有时查入队调用、未绑定和 `userCode`。
2. 是否出现 `reportPendingTasks` 的 ready 任务及对应 `reportTask | 开始上报`？没有时查 Manager 初始化、上传标记、解绑或日志覆盖。
3. 是否有“上报成功并删除任务”？有则客户端链路完成，转向后端查询条件/数据可见性。
4. 若反复失败或任务残留，检查具体业务码、网络错误、服务端幂等和绑定会话。
