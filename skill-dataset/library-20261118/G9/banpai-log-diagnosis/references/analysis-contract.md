# 日志分析契约

## 适用范围与代码基线

本文件定义 `banpai-log-diagnosis` 的统一取证和输出规则。当前覆盖门禁与开门上报、考勤与签到、人脸认证、同步与配置、节目与展示；源码事实基于代码基线 `ab680809`（2026-09-09 工作区检查）。

日志所属版本与该基线不一致时，必须把当前源码作为“可能的解释或对照”，不能表述为该历史版本已确认执行的逻辑。

## 最小输入

开始前尽量取得以下信息；缺失时继续可做的分析，但在结论中列为限制。

| 信息 | 用途 |
| --- | --- |
| 应用包名、版本、渠道和设备型号 | 判断源码、日志格式和硬件路径是否可比 |
| 问题发生时间、时区和至少前后 30 秒日志 | 建立时间线，避免相邻事件串线 |
| 用户期望与实际结果 | 明确是鉴权、开门、图片还是服务端事件的问题 |
| 原始日志或可定位的归档路径 | 复查原始证据，不以转述替代日志 |
| `taskId`、`eventId`、脱敏用户标识、设备序列号等 | 将异步任务、IoT 指令和 HTTP 请求关联起来 |
| 复现频率、网络状态、是否解绑/重启 | 判断重试、会话清理和偶发硬件问题 |

没有 `taskId` 时，使用“同一用户/设备 + 狭窄时间窗 + authType/status”的组合关联；必须说明这比 `taskId` 弱，连续操作时可能误配。

## 证据等级

| 类型 | 定义 | 表述要求 |
| --- | --- | --- |
| 日志事实 | 原始运行日志直接记录的事件 | 写明时间、TAG/请求和可关联字段 |
| 代码事实 | 目标版本源码能直接验证的行为 | 写明代码基线、类和符号；不得外推到其他版本 |
| 推断 | 由事实支持但缺少直接记录的解释 | 使用“可能”“高概率”等限定词，并列出替代假设 |
| 待验证项 | 当前证据无法判断、但会改变结论的事项 | 说明最小的补充日志、数据库查询或复现方式 |

“未看到日志”只有在确认日志完整、级别已开启、时间窗口正确且该节点必定会打点时，才能作为较强的负向证据；否则只能说明“当前材料未覆盖该节点”。

## 标准步骤

1. **归类问题。** 从用户描述判定入口和期望副作用，例如“人脸识别后门已开，但后台没有开门记录”。
2. **规范化时间。** 统一时区和日期，确认日志是否跨文件、跨重启或跨进程；先圈定前后 30 秒，再按证据扩大范围。
3. **建立时间线。** 按领域手册列出期望节点，记录每个节点的时间、证据、关联键和判断，不先跳到根因。
4. **检查异步边界。** 明确任务在哪个 coroutine scope 创建、是否已落库、是否等待外部调用、是否可能被取消、重启后能否恢复。
5. **检查外部边界。** 对每个 HTTP/IoT 调用分开验证“准备发起、实际请求、响应/回调、业务成功、本地状态更新”。
6. **形成结论。** 给出最早的已确认断点；若只能提出假设，明确其证据和最小验证办法。

## 隐私与日志处理

- `userCode`、卡号、人脸 `fileKey`、下载 URL、设备序列号、`x-device-*` 请求头以及完整请求体均视为敏感信息。
- 报告使用前 3 后 3 位、哈希或“用户 A/事件 A”等替代标识；同一标识在一份报告中保持一致。
- 不要求上传人脸原图来证明图片上传问题；优先使用 `taskId`、CStore 返回状态和 `faceFileKey` 是否回填。

## 报告格式

```markdown
## 结论
- 结论：
- 置信度：高 / 中 / 低
- 适用版本与日志时间范围：

## 已确认事实
- 日志事实：
- 代码事实：

## 事件时间线
| 时间 | 证据（TAG/请求） | 关联键 | 对应节点 | 判断 |

## 断点与原因
- 最早已确认断点：
- 根因推断：
- 尚未排除的替代假设：

## 影响与建议
- 影响范围：
- 下一步最小取证：
- 修复或配置建议：
```

“修复建议”必须与已确认断点对应；若断点尚在服务端或日志覆盖不足，不应直接建议修改客户端业务代码。
