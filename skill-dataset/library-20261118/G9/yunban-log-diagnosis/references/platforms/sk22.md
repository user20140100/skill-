# SK22 平台基线

适用条件：确认 APK 的 `type=sk22`，核对 APK/JS 版本与参考提交 `1735b1d25cfd20528e160011abb76689beaf5bcc`。`android/app/build.gradle` 将 `main + sk22` 装入 SK22，并引入 UDI SDK；不合入 `uds`、`legacy` 源码集或 OpenSDK。还要记录 `dev/demo/pro` 与 Debug/Release。

## 装配与能力边界

| 能力与源码 | 当前分支 | 排查时的分流 |
| --- | --- | --- |
| `sk22/.../platform/binding/PlatformBindings.kt#createServices` | 用 `BuildConfig.UDI_SDK_KEY` 初始化 `UdiRuntime`，装配 `UdiPlatformServices`。 | 初始化请求成功和每项 UDI 能力可用是不同节点。 |
| `sk22/.../platform/udi/UdiPlatformServices.kt` | 电源、显示、系统校时、门禁输出、状态灯有 UDI Adapter。系统栏、保活、平台版本、安装命令、APK 安装、补光返回 `NOT_CONFIGURED`。 | 先区分能力本来未装配、缺 token/SDK 初始化失败、已发请求但回调失败。 |
| `sk22/.../platform/udi/UdiRuntime.kt`、`sk22/.../handler/DeviceHandler.kt` | UDI 初始化 → 板端 HTTP 请求 SN，失败重试 → 解析结果 → DeviceHandler 提交并释放初始化链。 | SN 不走 UDS/OpenSDK 或系统属性；兜底值不能当真实板端 SN。 |
| `sk22/.../platform/udi/event/UdiNfcCardEventModule.kt` | UDI 事件订阅 → payload 校验/映射 → `NfcCardReadWorkflow` → RN 与韦根输出。 | 订阅、收到事件、接受卡号、RN、韦根是不同节点。 |

省略的路径前缀是 `android/app/src/`。上表是当前源码装配，不代表现场 APK 必然同版或运行时执行到该路径。

## 关联键与时序

| 链路 | 优先关联键 | 易误合并处 |
| --- | --- | --- |
| UDI 初始化与 SN | PID、一次 `udi_init`、`udi_sn attempt`、最终 `result`、DeviceHandler `commit` | 同 PID 的重试是一次 SN 决议过程；`result=requested` 属于 SDK 初始化，不是 SN 决议。 |
| UDI 刷卡 | `source_decimal`、`rn_hex`、`wiegand_decimal` 的源码映射，订阅生命周期 | RN 与韦根格式不同；`listener_received` 可能被 `ignored`，不能仅靠时间与别次刷卡合并。 |
| 定时电源 | `action`、`stage=clear_power_control_tasks/set_power_control_task`、计划时间与设备时钟 | 清理与设置是两阶段；后续实体关机/唤醒不在同一个回调里。 |

`UdiNfcCardEventModule` 接受卡号后调用公共 `NfcCardReadWorkflow`。该流程先请求响铃，后台再按 RN、韦根顺序提交；`rn_dispatched` 只证明 Native 发出 RN 事件，`wiegand_complete` 只证明平台回调。`UdiPlatformServices` 中静态未配置能力的 `NOT_CONFIGURED` 与运行时缺 token 要分别记录原因码。

## 日志指纹与证据边界

| 搜索键 / 通道 | 能确认的节点 | 后续要找的节点或限制 |
| --- | --- | --- |
| `UdiRuntime [udi_init] action=request`、`result=requested/configuration_error/failed` / 直接 Android Log | 请求 UDI 初始化、缺 token 或初始化异常。 | `result=requested` 不等于所有能力就绪；仅有 XLog 文本时此类直接 Log 可缺席。 |
| `UdiRuntime [udi_sn] action=request attempt=...`、`action=retry`、`result=valid_stable_sn/unavailable reason=...`；`Sk22DeviceHandler [udi_sn] action=commit status=... reason=...` / 直接 Android Log | SN 请求/重试/决议与 DeviceHandler 提交。 | 有运行时决议但无提交时，检查初始化链、进程覆盖；隐藏原始 SN。 |
| `UdiNfcCardEvent [nfc_tag] subscribe_skipped/subscribe_failed/subscribe_requested`、`listener_received`、`ignored`、`accepted` / XLog | 订阅状态、事件是否到达及 payload 是否通过映射。 | `accepted` 仅到卡号映射；接着追 `NfcCardReadWorkflow [nfc_card]` 的 RN/韦根分支。卡号需脱敏。 |
| `UdiDevicePowerAdapter [request]/[complete]`、`[power_task_request]/[power_task_complete] ... stage=... status=... reason=...` / XLog | UDI 请求与回调；定时任务可区分清除旧任务、设置新任务。 | `complete` 是 SDK/HTTP 回调层，不证明设备已经关机或按时唤醒。 |
| `UdiDisplayControl`、`UdiAccessControl`、`UdiStatusLightControl` 的 `[request]/[complete]` / XLog | 对应 UDI Adapter 请求与回调状态。 | 控制器/屏幕/灯的实际外部状态仍需现场或系统证据。 |

## 按现象定位断点

1. **启动/绑定缺 SN**：按 `[udi_init]` → `[udi_sn] request/retry/result` → `Sk22DeviceHandler commit` → 身份消费方查。`configuration_error reason=udi_token_missing` 和板端 SN 不可用不同；只有 `result=requested` 时不能写“SN 已就绪”。最小补证是启动阶段 logcat、APK 配置版本和相同 PID 的后续日志。
2. **刷卡未上屏或未开门**：按订阅 → `listener_received` → `accepted/ignored` → `NfcCardReadWorkflow` → RN/韦根查。`accepted` 中的十进制源卡号与 RN 十六进制映射值要按源码核对后关联，报告只留脱敏标识；门禁外部结果另证。
3. **定时关机/唤醒异常**：先找 `MCUOperationService` 计划，再查 `[power_task_schedule]`、清理和设置两阶段的 `[power_task_complete]`。任一阶段失败可定位到 UDI 回调；两阶段成功仍要设备时序或现场结果。
4. **系统栏、保活、安装或补光异常**：先检查是否属于 `UdiPlatformServices` 的未配置能力；若是，按 `NOT_CONFIGURED` 的代码事实解释，不误套 SK05/SK06 的 UDS/Legacy 排查路径。

| 最晚可见节点 | 当前能判定的范围 | 最小补证 |
| --- | --- | --- |
| `[udi_init] result=requested` | UDI 初始化请求已提交。 | 后续 SN 结果、目标 Adapter 的请求/回调或 SDK 状态。 |
| `[udi_sn] result=...`，无 `commit` | 运行时已给出 SN 决议；DeviceHandler 提交未在文本中确认。 | 同 PID 的直接 Android Log 与初始化链结果。 |
| `[nfc_tag] accepted` | 卡号映射完成。 | `NfcCardReadWorkflow` 的 RN/韦根结果和门禁侧证据。 |
| `[power_task_complete]` 两阶段成功 | UDI 接受计划。 | 实际设备关机/唤醒时刻及系统时钟。 |
