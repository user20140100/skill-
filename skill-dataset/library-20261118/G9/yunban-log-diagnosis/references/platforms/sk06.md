# SK06 平台基线

适用条件：确认 APK 的 `type=sk06`，并核对 APK/JS 版本与参考提交 `1735b1d25cfd20528e160011abb76689beaf5bcc`。`android/app/build.gradle` 将 `main + sk06 + uds + legacy` 装入 SK06；另记 `dev/demo/pro` 与 Debug/Release。

## 装配与入口

| 能力与源码 | 当前分支 | 排查时的分流 |
| --- | --- | --- |
| `sk06/.../platform/binding/PlatformBindings.kt#createServices` | 系统栏、电源、显示、状态灯、门禁输出、保活、安装命令、平台版本、补光用 UDS；系统校时与 APK 安装用 Legacy。 | 确认调用方走到哪项能力，不能把所有失败归为 OpenSDK。 |
| `sk06/.../handler/DeviceHandler.java#init` | OpenSDK 已连接时直接解析 UDS SN；否则最多等待 60 秒，再走兜底。异常/无效也走 `FallbackSnHelper`；结果只解析一次。 | `getSerialCode` 只读已保存结果，不会同步等 SDK。需要覆盖完整等待窗和同一进程。 |
| `uds/.../UdsAccessControlAdapter.kt` | 接收公共刷卡链路的门禁输出请求，校验卡号、检查 UDS helper 后调用 SDK。 | 这是输出端；输入来源和 RN 分支要回到 NFC domain 核对。 |
| `uds/.../UdsPowerControl.kt`、`UdsAppKeepAliveAdapter.kt` | 同步电源入口、保活 helper。 | 本地接受不证明物理动作或进程持续存活。 |

省略的路径前缀是 `android/app/src/`。SK06 的补光实现位于 `sk06/kotlin/.../platform/uds/UdsFaceFillLightControl.kt`，不要套用 SK05 或 SK22 的能力判断。

## 关联键与时序

| 链路 | 优先关联键 | 易误合并处 |
| --- | --- | --- |
| SN 决议 | PID、一次 `[init]`、`source=uds/fallback/none`、`result` | OpenSDK 连接回调可能早于 `init`；超时和迟到连接不能按日志邻近强行合成两次 SN 结果。 |
| NFC/韦根 | 同次刷卡的卡号映射、`NfcCardReadWorkflow` 状态与 `UdsAccessControl action=send_card` | RN 用十六进制、韦根用十进制；`wiegand_complete` 表示 Adapter 回调，不是控制器反馈。 |
| 电源/保活 | `action`、请求时刻、PID、设备状态 | `[accepted]` 是本地接口返回，不是跨重启的持续效果。 |

`DeviceHandler` 的 `mSnResolved` 让首次决议胜出；超时兜底后到达的 SDK 连接不应被解释为 SN 又被板端值覆盖。`ConfiguredPlatformServices.kt` 对未配置能力返回 `UNSUPPORTED`，判断能力前先看本机型绑定。

## 日志指纹与证据边界

| 搜索键 / 通道 | 能确认的节点 | 后续要找的节点或限制 |
| --- | --- | --- |
| `sn_sk06 [wait] ... timeout_ms=60000`、`[uds] ... open_sdk_connected` / XLog | 等待或收到 OpenSDK 连接回调。 | 等待日志之后的 60 秒缺失时，不能判定超时还是日志不全。 |
| `sn_sk06 [timeout] ... action=fallback`、`[resolve] ... source=uds/fallback/none result=...` / XLog | 进入兜底及本次 SN 解析来源和结果。 | `source=fallback` 不是板端 SN；`result` 与来源都要保留，SN 值要脱敏。 |
| `sn_sk06 [ready] ... result=...`、`[capacity] ... state=release` / XLog | SN 结果已提交、初始化链被放行。 | `state=release` 单独不等于有效 SN；后续绑定/IoT 状态另查。 |
| `UdsAccessControl [rejected] ... empty_card_id`、`[request] ... card_length=... wiegand_type=... uds_ready=...`、`[not_ready]`、`[accepted]` / XLog | 门禁输出请求被拒绝、helper 不可用或同步接受。 | `[accepted]` 只在 Adapter 层；需关联同次刷卡输入、RN 反馈和门禁侧动作。 |
| `UdsPowerControl [request]/[accepted]`、`UdsAppKeepAlive [request]/[accepted]/[not_ready]` / XLog | 本地平台接口的请求与接受/未就绪。 | 无电源物理完成回调；保活接受也不证明之后没有系统杀进程。 |

## 按现象定位断点

1. **启动停在 SN 阶段**：按 `[init]` → `[wait]`/`[uds]` → `[resolve]` → `[ready]` → `[capacity]` 排序。区分“SDK 未连上后兜底”“UDS 返回无效后兜底”“已有有效 SN 但后续绑定失败”。最小补证是同一 PID 覆盖至少 60 秒的启动日志和实际 APK 版本。
2. **刷卡未开门**：从 NFC 输入/RN 路径关联 `UdsAccessControl action=send_card`。`[not_ready]` 可将断点定位到 helper；`[accepted]` 后要门禁侧日志或现场结果，不能凭应用日志宣布开门成功。
3. **电源、显示、保活或补光异常**：先找调用方决策，再查对应 UDS Adapter 的 `request` 和结果。若设备真实状态与 `[accepted]` 不符，明确最后可见节点是 SDK 同步接受，补 SDK/系统状态。

| 最晚可见节点 | 当前能判定的范围 | 最小补证 |
| --- | --- | --- |
| `[wait]` | 已进入 OpenSDK 等待；后续尚未在文本中确认。 | 同 PID 覆盖完整 60 秒窗口的 `[uds]`/`[timeout]`/`[resolve]`。 |
| `[capacity] state=release` | 初始化链放行。 | 同次 `[resolve]`/`[ready]` 与下游设备身份结果。 |
| `UdsAccessControl [not_ready]` | 门禁输出 helper 在请求时不可用。 | 前段 NFC/RN 日志、UDS 连接状态与后续重试。 |
| `UdsAccessControl [accepted]` | 门禁输出请求被同步接受。 | 控制器/现场反馈。 |
