# diff-analysis-report 使用说明

> 版本：V2.4（三方差异版 + 多形态需求文档 + 用例执行报告 + 发布纪律） | 更新日期：2026-10-31
> 一句话：给它**分支范围 + 需求文档（飞书链接 / Figma 设计稿 / 本地 md / 图片均可）+ 需求用例文档**，它做代码 diff 影响分析、对比"需求 / 代码 / 用例"三方差异，按用例静态执行判定输出用例执行报告（PASS/FAIL/SKIP 汇总 + 失败用例列表），产出带风险清单和差异性用例的分析报告，并自动发布为飞书在线文档。

---

## 一、使用前准备

| #   | 要准备的东西       | 说明                                                                                                                                                                 | 没有会怎样                                 |
| --- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| 1   | **分支范围**     | 源分支 → 目标分支（如 `develop...feature/v0.17.0`），支持多仓库；本地需已 clone 且能 fetch 到这两个分支                                                                                         | 无法开始，会主动询问                            |
| 2   | **需求文档**     | 五种形态任一：**飞书链接**（浏览器需已登录飞书）/ **Figma 链接**（如 `https://www.figma.com/design/<fileKey>/<名称>?node-id=xxx-xxx`，建议带 node-id 定位到具体画板）/ **本地 md 路径** / **图片**（需求截图、长图、设计切图）/ **本地 demo 文件夹**（交互原型工程：双击 index.html 可开的单文件包，或含 README+src 的源码工程） | 会按形态自动选获取方式；仍失败则要求粘贴全文或提供文字版，需求对照环节缺失 |
| 3   | **该需求的用例文档** | xmind（新旧格式均可）或表格类文档——就是这个需求自己的测试用例，不是通用主流程用例库                                                                                                                      | 三方差异退化为两方（需求 × 代码），报告中会注明             |
| 4   | 业务背景文档       | **不用准备**。skill 文件夹自带两份（校园安防相关项目总览 / 核心功能说明），每次运行自动读取                                                                                                               | —                                     |

**明确不做的事**：不读取通用主流程用例文档；不做漏合检查；不做性能/安全专项测试；不执行真实测试（第五章用例执行结果为基于代码证据的静态判定，非真实跑测）。

## 二、怎么调用

在 Claude Code 里用自然语言即可，触发方式任选：

```
/diff-analysis-report
```

或者直接说需求（关键词：diff 分析 / 影响范围分析 / 变更风险评估 / 分支对比测试报告）：

```
用 diff-analysis-report 对比 cisp-devops 和 cisp-ps-25-factory-app 两个仓库的 develop...feature/v0.17.0，
需求文档是 https://cvte.feishu.cn/wiki/xxxx，
用例文档是 D:\xxx\KDS设备接入_激活.xmind
```

需求文档换形态时用法相同，直接把链接/路径换掉即可：

```
# Figma 设计稿（链接用 Figma 里「Copy link」复制，建议定位到具体画板/Frame）
用 diff-analysis-report 对比 xxx 仓库 develop...feature/v0.18.0，
需求文档是 https://www.figma.com/design/5O4tWFngEnVv7QD13EGUAB/2609A?node-id=3037-5883，
用例文档是 D:\xxx\用例.xmind

# 本地 md 或图片（截图、长图、设计切图都可以）
用 diff-analysis-report 对比 xxx 仓库 develop...feature/v0.18.0，
需求文档是 D:\需求\v0.18.0.md（或 D:\需求\交互说明.png），
用例文档是 D:\xxx\用例.xmind

# 本地 demo 文件夹（交互原型工程，直接给文件夹路径）
用 diff-analysis-report 对比 xxx 仓库 develop...feature/v0.18.2，
需求文档是 C:\Users\cvter\Downloads\希沃录播_校级安防_V0.18.2_通行规则_通行规则下发，
用例文档是 D:\xxx\用例.xmind
```

信息不全时它会逐项追问，不会瞎猜。

## 三、它会做什么（内部 9 步）

| 步骤       | 做什么                                                                                                | 产出                         |
| -------- | -------------------------------------------------------------------------------------------------- | -------------------------- |
| 1. 范围与背景 | git diff 统计；读取自带的两份业务文档建立背景                                                                        | 变更规模、业务上下文                 |
| 2. 需求对照  | 按需求文档形态自动选获取方式：本地 md 直接读；图片视觉读取并转写表格/批注；飞书走登录态浏览器；Figma 走 MCP 拉节点树（text 图层文字即需求原文）；产出"需求点→实现→差距"映射 | 差距项（G-x 编号）                |
| 3. 代码解析  | 逐模块深读 diff；大 diff 会派子代理并行；间接影响必须有调用链证据                                                             | 影响面（直接/间接）                 |
| 4. 质量快检  | 冲突标记 Grep、误删符号查引用                                                                                  | 一行式结论，问题才展开                |
| 5. 风险识别  | 每条风险带 file:line 证据；高风险二次验证后才标高                                                                     | 风险清单（R-x 编号）               |
| 6. 三方对照  | 需求 × 代码 × 用例文档逐点核对；代码疑点用 git grep 验证                                                               | 四类差异 + 待确认清单               |
| 7. 用例执行判定 | 以每条用例为单元，用代码证据静态判定：PASS（已在代码中实现）/ FAIL（与代码矛盾，附证据）/ SKIP（证据不足）                                      | 执行汇总表 + 失败用例列表              |
| 8. 用例清单  | 差异性用例成表（编号 + 三方状态 + 三段式备注）                                                                         | 差异性用例清单                    |
| 9. 输出    | 直接创建飞书在线文档（不经本地 md 报告文件中转）；无法创建时才落本地 md                                                            | **飞书文档链接**（主交付物）；本地 md（兜底） |

## 四、输出物与怎么读

### 4.1 报告结构（全量版六章）

| 章          | 内容                                | 重点看什么                     |
| ---------- | --------------------------------- | ------------------------- |
| 一、变更范围与影响面 | 变更规模表、直接/间接影响、需求对照表               | 需求对照表的"差距"列——需求有但代码没有的都在这 |
| 二、变更质量快检   | 漏合/冲突标记/误删，各一行                    | 只在"发现问题"时才需要关注            |
| 三、实证风险清单   | R-x 编号、结论（已证实/待确认）、证据、等级、**建议验证** | "建议验证"列指向用例编号或专项补充编号      |
| 四、测试用例清单   | 三方差异用例表                           | 见 4.2 的读法                 |
| 五、用例执行报告   | 执行汇总表（总用例/通过 PASS/失败 FAIL/跳过 SKIP 的条数与占比）+ 失败用例列表（用例主题 + 失败原因说明） | FAIL 的失败原因说明都带代码证据；SKIP 占比高说明可静态判定的用例少 |
| 六、局限性      | 静态分析的边界、未覆盖项                      | 交报告前扫一眼                   |

diff < 20 文件且 < 1500 行时自动出简版（仅第一、三、四、五章）；无用例文档时第五章整节省略。

### 4.2 用例清单的"三方状态"怎么读

每条用例按**需求 / 代码 / 用例**三个来源标注：✓＝有，✗＝无，△＝部分或待确认。

| 状态样式           | 含义               | 这条用例怎么来的                 |
| -------------- | ---------------- | ------------------------ |
| 需求 ✓、代码 ✓、用例 ✗ | 需求有、代码实现了、用例没写   | 按需求+代码行为起草的补充用例          |
| 需求 ✓、代码 ✗、用例 ✗ | 需求有、代码没实现        | 补了用例，同时登记为差距项（G-x），需推动实现 |
| 需求 △、代码 ✓、用例 ✗ | 需求只写了一部分         | 按代码实际行为起草                |
| 需求 ✗、代码 ✓、用例 ✗ | 代码自加的能力，需求没提     | 补测试覆盖，并确认是否该有            |
| 用例 ✓（预期冲突）     | 三方都有，但用例预期和代码对不上 | 修正用例——改 xmind 的预期        |

**备注说明**是三段式，逐源写清依据：需求文档（有/无＋依据章节）、代码（有/无＋对应模块）、用例（有/无＋差异点）。

「代码」源状态与第五章执行结果对应：代码 ✓≈PASS（已在代码中实现）、代码 ✗ 或预期冲突≈FAIL、代码 △≈SKIP（证据不足待确认）。

### 4.3 风险和用例怎么互查

- 第三章风险表的"建议验证"列写的是 `用例N` 或 `专项补充-N`
- `用例N` → 去第四章清单按编号找；`专项补充-N` → 第四章表尾的"风险专项补充"（无用例覆盖、需要专门构造场景的风险）
- 反向：看到某条用例，其备注里的差距编号（G-x）说明它依赖某个待兑现的差距

## 六、已知边界与注意事项

1. **飞书登录态**：需求链接依赖浏览器已登录 cvte.feishu.cn；链接打不开时它会要你粘贴全文，不要让它凭空猜需求
2. **Figma 需求稿**：读取走 Framelink MCP（token 已配好，无需额外操作）。只能读到 **text 图层文字**与图层结构、组件属性——嵌在位图/贴图里的文字读不到，重要说明请设计侧用文本图层写；链接建议带 `node-id` 定位到具体画板，否则会拉整个文件（结果很大、分析变慢）；超大结果自动落盘分段读取属正常现象，不代表出错
3. **图片需求文档**：直接视觉识别，图中表格/流程图/批注会转写为结构化需求点；分辨率过低或文字太小时会要求换可辨版本，不会猜
4. **xmind 格式**：老格式（content.xml）与新格式（content.json）都支持；xmind 内含图片的节点提取不到（如需求文档里"异常逻辑补充"是图片的场景），相关用例会标注待确认
5. **后端黑盒**：diff 只含前端仓库时，涉及后端/边缘的结论（如跨系统联动）都会标"联调确认"，不会拍死
6. **编码坑（已内置规避）**：Windows 下命令通道传中文文件名可能乱码，skill 内部用内容特征识别文件、Python 直接写 UTF-8 文件；如遇单个命令失败属已知现象，它会自动换方法
7. **风险结论可信度**：`[已证实]` 都有 file:line 证据且高风险做过二次验证；`[待确认]` 会写明缺什么证据，别把待确认当定论
8. **用例执行结果口径**：PASS/FAIL/SKIP 是基于代码证据的静态判定，不是真实跑测——FAIL 必有 file:line 或检索式证据，并标注根因类型（实现缺失/交互归属分歧/规则冲突/文案不符），交互归属分歧需产品定夺、不是缺陷定论；SKIP 表示证据不足（可能由后端/其他系统兑现），既不是失败也不是通过，别把 SKIP 当定论
9. **报告发布**：报告自动导入飞书「我的文档库」，文档标题即报告标题（由临时上传文件名承载）；浏览器实例被残留锁占用时自动清理恢复，登录态不丢——以上均为内部纪律，无需手动操作

## 七、常见问题

**Q1：需求文档不是飞书链接行不行？**
行，共支持五种形态：飞书链接、Figma 链接（走 MCP 读设计稿，text 图层即需求原文）、本地 md 路径、图片（截图/长图/切图直接视觉识别）、本地 demo 文件夹（交互原型：README 通读圈范围 + 浏览器遍历页面截图读文案 + 源码型 demo 直接读组件提特征串）。word/pdf 等其他格式建议先另存为 md 或截图后再给。

**Q2：没有该需求的用例文档怎么办？**
会退化为"需求 × 代码"两方对照、第五章用例执行报告整节省略，并在报告注明；建议后续补用例文档后再跑一次拿完整三方差异与执行结果。

**Q3：只分析某个模块/仓库行不行？**
行，调用时说明聚焦范围（如"只分析 src/services/"或"只看 devops 仓库"）。

**Q4：报告生成后修改了 md，飞书文档会同步吗？**
不会自动同步——飞书文档是导入时的快照；重大修改后重跑步骤 9 重新发布一份即可。

**Q5：能对非安防项目的仓库用吗？**
流程通用；但自带的两份业务背景是安防产品线的，其他项目建议替换 skill 文件夹里的业务文档或运行时口头说明背景。
