# 代码 Diff 影响分析与测试报告生成（V2.1）

资深测试架构师角色：基于 Git 分支差异做变更分析，**结合需求文档与该需求的用例文档做三方差异对比**，按 [report-template.md](report-template.md)（V2.1）输出报告。

## 核心原则

1. **结论导向**：报告的价值在风险清单、需求差距和结论，不在变更流水账
2. **证据优先**：每条风险必须有 `file:line` / Grep / commit 证据；无证据不得写入风险清单
3. **三方差异导向**：用例产出来自"需求 × 代码 × 用例文档"三方对比，用三方状态（✓/✗/△）标注；差异用例先写入需求用例文档再进清单（单一来源）；每条已证实风险必须有验证路径（清单用例或专项补充）
4. **禁用 Emoji**；变更类型仅用 `[新增]`/`[修改]`/`[修复]`/`[重构]`/`[配置]`/`[依赖]` 文本前缀

## 输入

- 必需：
  - 源分支 A → 目标分支 B（或 commit/tag），可多仓库；未指定时询问
  - **需求文档**：支持五种形态——飞书链接 / Figma 设计稿链接 / 本地 md 文档 / 图片（截图、长图、设计切图）/ 本地 demo 文件夹（交互原型工程），获取策略按形态分派（见步骤 2）
  - **该需求的用例文档**：xmind/表格等（触发三方差异对照）。
- 业务背景（skill 自带，每次运行必读，见步骤 1）：
  - 本目录 `业务知识/` 文件夹下的**全部文档**——当前含项目总览（仓库定位/业务闭环/调用链）与核心功能说明（核心功能与业务链路）；增补业务文档时直接放入该文件夹即可，无需改动 skill
- 可选：聚焦范围（如"只分析 xx 目录"）

## 执行流程

### 1. 确定对比范围与业务背景

仓库根目录执行：`git fetch`、`git merge-base A B`、`git log A..B`、`git diff --stat A...B`。记录 merge-base、文件数、增删行数。多仓库逐个执行，注意每条命令显式 `cd` 到对应仓库。

随后 Read 本 skill 目录下 `业务知识/` 文件夹中的**全部**文档（当前含：相关项目总览——仓库定位/业务闭环/调用链；核心功能说明——核心功能与业务链路），作为影响面与间接影响判断的业务背景；该文件夹可随业务发展增补文档，skill 无需改动。

### 2. 需求对照（提供需求文档时）

- **获取策略（按需求文档形态分派）**：
  - **本地 md**：Read 直接读取；超长文档先看目录结构再分段通读，不跳读正文
  - **图片**（需求截图/长图/设计切图）：Read 直接视觉读取（PNG/JPG 等）；多图逐张读并汇总为统一需求点清单；图中的表格、流程图、批注需转写为结构化文字；分辨率过低或文字不可辨时要求用户提供可辨版本或文字版，**不得猜测图片内容**
  - **本地文件夹（交互 demo/原型工程）**：先 `find` 摸清结构并统计文件类型（html/图片/源码/文档），再 Read README 等文档并**通读**——demo 包的 README 常是需求正文（交互规则/状态机/文案/边界全在文字里），且通常圈定了范围（哪些「沿用原平台」是背景、哪些是本需求新增），以它为需求边界防把通用外壳误当需求。交互页面按形态打开：
    - 单文件 index.html（脚本样式已内嵌）→ 浏览器 `file:///` 直接打开；本地存储/IndexedDB 受限时 → 先 Read 自带服务脚本确认安全（仅 node 内置模块、无外部网络调用、有路径校验）再 `node serve.mjs` 起本地端口打开；**禁止在 demo 目录 npm ci/npm install**（依赖生命周期脚本风险；demo 无需装依赖即可运行）
    - playwright 遍历页面/抽屉/弹窗，**边走边截图视觉读取**——界面文案即需求原文（与 Figma text 图层同地位，是三方对照特征串的第一来源）；README 指引的演示路径（如「搜索 xx 可查看各状态」）要按说明触发核验
    - **源码型 demo**：src/ 页面组件可直接 Read，是文案/状态机/交互最精确的需求载体，也可 grep 提特征串；注意 demo 源码是需求侧参照物而非被测代码，不得与目标仓库实现混同
    - 图片资产 Read 视觉读取；视频无法观看 → 要求关键帧截图或标待确认
  - **飞书链接**：WebFetch 被拦（内网/登录域）→ 改用浏览器工具会话打开（可能已有登录态）；虚拟滚动渲染的文档需边滚动边按 data-block-id 去重收集（表格头/重复渲染块再做文本级去重），滚动收集 JS 片段固化于 `scripts/collect_feishu_doc.js`（粘贴进 browser_evaluate 执行）；正文内嵌图片可对图片元素截图后视觉读取（browser_take_screenshot 指定元素），读不出再标待确认；仍失败则要求用户粘贴全文
  - **Figma 链接**：从 URL 提取 fileKey 与 node-id（`node-id=3037-5883` 转为 `3037:5883` 传参），调 Framelink MCP `get_figma_data` 拉取节点数据；结果超大时自动落盘，对落盘文件分段 Read（先定位 NODES 段再通读节点树；GLOBAL_VARS 段是设计令牌，跳过不影响需求理解）。提取要点：Frame 层级与命名；**全部 text 图层——界面文案即需求原文，是后续三方对照特征串的第一来源**；附在画板内的「XX说明」类规格 Frame（常含交互表格、BUG 修复说明）；componentProperties（「替换文案」类属性即动态文案占位）。无 node-id 时拉整文件按画板逐个梳理；关键切图可再用 `download_figma_images` 下载辅助理解。注意：嵌入图片（非 text 图层）里的文字读不到，与 xmind 图片节点同款边界，相关点标待确认
  - 所有形态共同纪律：获取失败则要求用户粘贴内容或提供文字版，**不得凭空推测需求**
- 产出"需求点 → 实现 → 差距"映射表：每个需求功能点对应哪些仓库/模块、是否完整实现、缺口
- 需求中提到但 diff 中无对应实现的功能点（尤其跨系统联动），登记为差距并进入风险清单（`[待确认]`）

### 3. 解析变更与影响面

- Read 变更文件与上下文，Grep 查调用方；**间接影响必须有 Grep/Read 证据**，否则不列入影响面
- 大 diff（>50 文件）建议并行子代理分仓库深读，主线程汇总并对高风险结论做二次交叉验证
- 多仓库结论冲突时以实际代码为准（`git show 分支:path`），文档记录滞后不算数

### 4. 变更质量快检（不单独成章，发现问题才展开）

- **冲突标记**：Grep 一次（`<<<<<<<`/`>>>>>>>`/`=======`），命中写入风险清单
- **误删**：diff 中被删符号在目标分支 Grep 引用（整文件删除必查；超大 diff 可按模块抽样并注明）。发现"删了仍被引用"或孤儿文件/文档悬空引用 → 写入风险清单
- 误注释、重复实现**不设专项检查**；分析过程中顺带发现且有实际价值的才写入风险清单

### 5. 实证风险识别

每条风险字段：风险ID（R-001 递增）/ 结论（`[已证实]`/`[待确认]`/`[已排除]`）/ 类型 / 证据（file:line + diff/Grep/commit）/ 影响链 / 等级 / 建议验证。

- `[已证实]` 才可标高；`[待确认]` 必须写明缺什么证据
- 高风险界定：核心业务、写库、权限、对外 API、删除仍被引用、交付架构变更、漏合致功能缺失
- 高风险结论（如"缺守卫""死锁"）须二次验证后再采信
- 版本分支混装多需求/版本性变更时，风险「类型」带归属标签（所属需求 / 版本性），避免跨需求风险混杂难排优先级

### 6. 需求用例文档三方对照（提供该需求的用例文档时，如 xmind）

- 使用**该需求专属的用例文档**（xmind/表格等）；
- **三方对比**：需求功能点 × 代码实现 × 用例覆盖，输出四类差异——需求有/用例缺、需求有/代码无（差距项，标责任方）、用例有/代码无或不一致、代码有/用例缺
- 代码侧疑点必须用 `git grep`/`git show` 验证后再下结论（如弹窗组件是否存在、字段是否回显、接口返回范围），不得凭 diff 印象断言。检索纪律：
  - **多角度特征检索**：从用例预期与需求文档提取多组特征串（界面原文文案——优先取 Figma text 图层/飞书文档原文，组件/字段名、接口路径、错误码）逐一 grep，单角度检索不得下结论
  - **命中≠实现**：grep 命中后必须读上下文甄别语义——如「激活时间」命中但仅用于 AI 服务激活时间，不能据此判定设备激活时间已实现
  - **✗ 的边界**：「代码 ✗」仅指本次 diff 涉及的仓库分支无实现；可能由后端/其他系统兑现的（如跨系统通知），标差距项＋责任方，不拍死 ✗
  - **△ 兜底**：措辞可能漂移、或无特征串的纯逻辑行为（grep 判定不了）→ 标 △ 进待确认清单，宁可待确认不给错误否决；用例预期保留界面原文文案可显著提高检出率
- 差异用例先写入需求用例文档或独立差异清单文档（保持单一来源），含「待确认清单」（需产品/后端定夺的事项）
- **覆盖度清点**：先按需求功能点清点 xmind 对用例的覆盖（需求点 × 用例分支对照）；无用例覆盖的需求点必须以「需求 ✓、用例 ✗」行进入第四章清单，不得静默遗漏
- xmind 解析：直接运行固化脚本 `scripts/parse_xmind.py`——`python -I <skill目录>/scripts/parse_xmind.py <xmind路径> <输出txt>`，兼容 content.xml/content.json，输出缩进文本树＋末行 leaf_cases=N 叶子用例计数（Python 以 UTF-8 直写文件，`-I` 模式勿依赖 stdout）
- **特征串预检索**：解析后运行 `scripts/grep_features.py`——`python -I <skill目录>/scripts/grep_features.py <解析txt> <仓库目录> <目标分支> <输出md> [pathspec...]`，把用例预期中的引号文案批量 `git grep -F` 到目标分支（数秒完成），产出「特征串 → 命中 file:line / 未命中」命中表；判定子代理以该表为起点只做语义甄别（命中≠实现、措辞漂移核对），不逐条现场 grep
- 飞书文档滚动收集的浏览器 JS 片段固化于 `scripts/collect_feishu_doc.js`（粘贴进 browser_evaluate 执行），无需现场编写

### 7. 用例执行结果判定（提供用例文档时）

以用例为执行单元，用目标分支代码证据对每条用例做**静态执行判定**（非真实跑测），产出用例执行报告：

- **判定口径**（复用步骤 6 检索纪律：多角度特征检索、命中≠实现、读上下文甄别语义）：
  - **PASS（通过）**：多角度特征检索命中，且上下文语义与用例预期相符——该用例已在代码中实现
  - **FAIL（失败）**：代码证据与用例预期矛盾——本次涉及仓库内多角度检索均无命中且责任在本仓库，或命中但字段/文案/逻辑与预期不符；FAIL 必须附 `file:line` 或检索式证据，禁止凭 diff 印象下 FAIL；每条 FAIL 标注根因类型：**实现缺失 / 交互归属分歧（用例面向的 UI 属于其他端或归属未定，需产品定夺，不拍死为缺陷）/ 规则冲突 / 文案不符**
  - **SKIP（跳过）**：无法取得可判定证据——纯逻辑行为 grep 判定不了、可能由后端/其他系统兑现、措辞漂移等；宁可 SKIP 不给错误结论
- **一致性**：判定与三方状态「代码」源对应（PASS≈代码✓、FAIL≈代码✗或预期冲突、SKIP≈代码△），同一条用例两处结论不得矛盾
- **产出**（写入报告第五章）：
  1. **执行汇总表**：指标/条数/占比，固定四行——总用例、通过 PASS、失败 FAIL、跳过 SKIP；占比分母为总用例、保留一位小数，PASS+FAIL+SKIP=总用例
  2. **失败用例列表**：仅列 FAIL，三列——用例主题、根因类型、失败原因说明（含证据 file:line 与差异点）；同根因 FAIL 在表下集中一段根因说明，明细行一句话引用；无失败写「无失败用例」
- SKIP 不单独成表，跳过原因归并第四章备注说明与待确认清单，防膨胀
- **大用例量（>50 条）**：建议拆两个子代理接力（实现事实提取 → 逐条判定），判定表直接带三方状态「代码」源列，供第四章清单推导，避免单代理超长耗时

### 8. 测试用例清单（纪律，防膨胀）

- 输出为**一张清单表**，列固定：**用例编号**（从 1 递增）、**三方状态**、用例标题、前置条件、操作步骤、预期结果、**备注说明**
- 三方状态：按**需求 / 代码 / 用例**三源分别标 ✓（有）/ ✗（无）/ △（部分或待确认），如「需求 ✓、代码 ✓、用例 ✗」；状态可推出分类（需求 ✓＋用例 ✗＝需求补充用例；需求 ✗＋代码 ✓＋用例 ✗＝代码差异用例；用例 ✓ 但与代码冲突＝修正用例）
- 备注说明用**三段式逐源说明**：需求文档：有/无＋依据章节、Figma 画板或 demo 页面/README 要点；代码（分支）：有/无＋对应模块与实现；用例（xmind）：有/无＋差异点
- **编号与第三章风险清单「建议验证」列互相引用**：清单内用例覆盖的风险写「用例N」，未覆盖的写「专项补充-N」
- 需求差距编号（G-x）随代码段写入备注说明；风险关联统一由第三章「建议验证」列维护，备注说明只保留三源逐源说明
- 每条 `[已证实]`/关键 `[待确认]` 风险须有验证路径：能被清单用例覆盖的并入备注说明；不能覆盖的以**一句话一条**列于表后「风险专项补充」（编号 专项补充-N），不再单独成表
- 禁止另造"正常/异常/边界/回归"四表结构（那是凑格式的来源）

### 9. 输出（直接生成飞书在线文档）

- **分级**：diff < 20 文件且 < 1500 行 → 简版（仅第一、三、四、五章）；否则全量
- 先 Read report-template.md，版本固定 V2.1，占位符全部替换
- **主交付物：飞书在线文档——直接创建，不产出本地 md 报告文件**。按优先级依次尝试：
  1. **云盘导入入口**（路径已验证）：浏览器打开已登录的飞书云盘主页（cvte.feishu.cn/drive/home）→「上传」→「导入为在线文档」→ 位置选「我的文档库」（共享团队位置可能被权限分类器拦截）→ 格式选「Markdown」→ 文件选择器上传 → 轮询 `/space/api/import/result/{ticket}` 至 job_status=0 取在线文档链接
     - **临时 md 写到 `<工作区>/.playwright-mcp/import-tmp/`**——browser_file_upload 仅允许工作区根内文件，系统临时目录会被拒；**文件名直接用最终中文报告标题**（导入的在线文档以文件名为标题，可免去后续改名：docx 标题编辑、云盘重命名入口、wiki 改名 API 均不可靠）；导入完成后删除整个临时目录
     - **浏览器实例锁恢复**：navigate 报 "Browser is already in use" 时（remote-debugging-pipe 模式无法重连残留实例），按可执行路径结束 `*ms-playwright*` 的 chrome 进程、删除 profile 目录下 lockfile（进程未杀会报 Device or resource busy），再重新 navigate——登录态在 profile 内保留不丢失
     - **导入后核验**：滚动收集文档块，确认表格数量与关键章节（尤其第五章执行汇总/失败列表）存在；异常再降级到方式 2/3
  2. **页面内导入接口**：若无导入入口，在飞书页面上下文内用 fetch（携带登录态，用 Blob 从内存构造上传体，不落本地文件）调网页端 Markdown 导入接口（`/space/api/box/upload/*`、`/space/api/import/*`）创建导入任务，轮询完成后取在线文档链接。注意：页面策略 SDK 只放行导入相关白名单接口，`/space/api/wiki/*` 等其他 API 会被拦截，勿依赖
  3. **空白文档粘贴**：再不行，新建空白在线文档按章节粘贴内容，提示用户手动核对表格格式
- **兜底：仅当以上全部失败**才生成报告到本地：路径用户指定，默认 `<主仓库>/docs/test-reports/diff-test-YYYYMMDD-HHmm.md`，并在回复中说明失败原因
- 最终回复：成功附飞书在线文档链接；失败附本地路径 + 失败原因

## 特殊规则（触发时对应风险必须有场景/用例）

数据库写操作 → 数据一致性与恢复；对外 API → 契约与兼容；并发 → 竞态；第三方/跨系统 → 联动与降级；高风险 → 破坏性与异常恢复

## 局限性（写入报告末章）
