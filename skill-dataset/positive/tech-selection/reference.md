# Reference：数据采集、打分细则与质量工具

## 一、硬数据采集

### 1. GitHub 仓库指标

```
GET https://api.github.com/repos/{owner}/{repo}
```

关键字段与解读：

| 字段              | 解读                                                   |
| ----------------- | ------------------------------------------------------ |
| stargazers_count  | 社区规模（横向对比两候选方倍数关系即可，绝对值无意义） |
| forks_count       | 实际二次开发热度                                       |
| open_issues_count | 与 star 联看维护压力（体量大 issue 少 = 健康）         |
| pushed_at         | 距今 < 30 天 = 活跃；> 180 天需警示                    |
| created_at        | 经营年限（长期经营 > 频繁重启）                        |
| license.spdx_id   | 宽松（MIT/Apache-2.0）可 fork 兜底；传染性协议需评估   |

### 2. npm 周下载量

```
GET https://api.npmjs.org/downloads/point/last-week/{package}
```

- 注意口径：国内用户多走 npmmirror 镜像，npm 官方统计会**低估以国内为主的库**；文档中如实标注该偏差，必要时用 star 数、知名案例佐证修正
- 候选方若有新旧多包名，各查一次并说明合计口径
- 也可查指定时间窗：`/downloads/point/{YYYY-MM-DD}:{YYYY-MM-DD}/{package}`（观察趋势）

### 3. 版本史与升级方式（长期维护的关键证据）

- GitHub Releases / CHANGELOG：首版时间、当前 major、上一 major 发布时间与间隔
- 官方迁移指南是否存在 → 区分「渐进迁移（可控破坏）」与「重写级破坏（废弃 API/插件）」
- discussions/issues 中社区对升级成本的真实反馈
- 维护主体性质：商业公司（有变现动力）/ 企业兼职（受内部业务优先级影响）/ 纯社区（看核心维护者人数）

### 4. 商业模式查证

- 官网定价页、公司背景：核心开源 + 何种变现（Pro 订阅/咨询/托管）
- 关键判断：核心库是否依赖闭源部分？停维时 fork 成本（代码可读性、架构复杂度、测试覆盖）

## 二、五维打分锚点（1~5 分）

### 长期维护成本

| 分  | 锚点                                                                          |
| --- | ----------------------------------------------------------------------------- |
| 5   | 专职商业团队或超大社区，7 年+持续经营，大版本升级有官方迁移指南，停维概率极低 |
| 4   | 活跃维护，偶有破坏性变更但可预期、有文档                                      |
| 3   | 企业兼职团队维护，节奏受内部业务影响，或有历史停滞后重启记录                  |
| 2   | 维护缓慢，issue 明显积压                                                      |
| 1   | 实质停维                                                                      |

### 研发投入资源

| 分  | 锚点                                                 |
| --- | ---------------------------------------------------- |
| 5   | 与团队技术栈零摩擦，能力对齐需求，估时显著低于对照方 |
| 4   | 少量学习成本 + 等量实现工作量                        |
| 3   | 需桥接层/双心智模型，或估时约为对照方 1.5 倍         |
| 2   | 桥接税随每次迭代线性放大                             |
| 1   | 需重写候选方部分内核                                 |

### 可扩展性

| 分  | 锚点                                                         |
| --- | ------------------------------------------------------------ |
| 5   | 扩展即用团队既有技能（如「再写一个组件」），无第二套心智模型 |
| 4   | 扩展需学候选方特定机制，但文档完善、模式统一                 |
| 3   | 每个扩展点都要过桥接/适配层并逐个验证                        |
| 2   | 扩展需 fork 改源码                                           |
| 1   | 封闭不可扩展                                                 |

### 能力与场景（有效能力口径）

| 分  | 锚点                                   |
| --- | -------------------------------------- |
| 5   | 需求画像 R 项全部原生覆盖且可控粒度细  |
| 4   | R 项覆盖，少量需自实现                 |
| 3   | 基本覆盖但实现路径绕（需验证交互细节） |
| 2   | 多项 R 需绕开候选方自行实现            |
| 1   | 核心 R 项不支持                        |

### 性能与体积

| 分  | 锚点                                           |
| --- | ---------------------------------------------- |
| 5   | 显著更轻/更快，且有生产规模背书                |
| 4   | 同级规模均无压力，本方更轻                     |
| 3   | 同级规模均无压力，无实质差异（此时维持低权重） |

> 打分必须先写「关键依据」再给分；依据无法落到数据或 R 项的，不给分。

## 三、反选条件设计方法

从落选方每项真实优势出发，转写为条件句：

1. 宿主技术栈匹配（落选方一等支持、胜出方不可用）
2. 落选方独有且被证实的刚需能力（逐条验证本项目是否真的需要）
3. 文档/社区语言约束（团队无法有效使用英文资料）
4. 合规约束（信创/国产化/安全审计）
5. 未来场景演化（如可预见的多形态平台需求）

每条标注「本项目是否命中」；全部不命中时写明「反选通道关闭，二选一成立」。若任一命中，回到 Phase 0 重开决策。

## 四、常见陷阱

| 陷阱                             | 对策                                        |
| -------------------------------- | ------------------------------------------- |
| 证实性偏差（只找胜出方证据）     | 强制「公道话」段 + 反选条件表               |
| 无效供给（被功能列表吸引）       | 回需求画像逐条对射程                        |
| 共同短板当区分项                 | 标注为「业务层能力/非区分项」               |
| 数据时效（结论过时复用）         | 标注采集日期；超 6 个月的结论复用前必须重测 |
| 权重暗箱（先打分后配权重凑结论） | 权重先与用户确认再打分                      |
| 镜像源偏差（误判国内生态）       | 标注口径，多源交叉验证                      |
| 工作量拍脑袋                     | 分工作项列对比表，含「持续成本」列          |

## 五、成稿质量 checklist

- [ ] TL;DR 含推荐 / 总分 / 核心理由 / 反选命中情况
- [ ] 每条 R 有出处；非区分项已标注
- [ ] 数据表含采集日期与 API 端点
- [ ] 落选方优势有专段公道话
- [ ] 反选条件逐条命中验证
- [ ] 风险对冲措施具体可执行（非口号）
- [ ] 行动项含时机/负责人占位
- [ ] 与上游文档（预研/需求）互链
