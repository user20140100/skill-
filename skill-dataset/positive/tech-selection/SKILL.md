# 技术选型深度对比（Tech Selection）

为「二选一 / 多选一」技术决策产出可评审、可追溯的对比文档。方法论源自实战沉淀（完整案例见 [examples.md](examples.md)）。

## 核心理念（不可违背）

1. **考题先行**：先从需求提炼「候选方必须满足的硬性要求清单（R1..Rn）」，再评估候选方——评分锚点是需求射程，不是候选方的能力清单。
2. **硬数据实测**：社区/生态类论断必须有实测数据（GitHub API、npm 下载量、版本发布史）支撑并标注采集日期；禁止凭印象断言。
3. **公道话与反选条件**：落选方的真实优势必须如实写入；显式枚举「什么情况下应反选落选方」并逐条验证本项目是否命中——这是对抗证实性偏差的核心机制。
4. **无效供给不计分**：候选方能力若不在需求射程内，不作为优势计分，只注明「无效供给，反而增加理解与裁剪成本」；两方的**共同短板不构成区分项**。

## Prompt 工程范式

### 高保真 Prompt 模板（已验证：一轮产出完整选型决策文档）

```
需求背景：<需求文档 / 预研文档链接，或一段需求描述>（评估射程以此为准）

候选方案：<方案A> vs <方案B>（二选一；多选一写明选几个）

宿主约束：<技术栈及版本 / 团队技能构成 / 许可证·合规要求（如信创）>

请深度对比 <方案A>、<方案B>，产出可评审的选型决策文档：

1. 先从需求提炼硬性要求清单（R1..Rn），业务层能力标注为非区分项
2. 实测生态数据（GitHub 指标 / npm 周下载量 / 版本升级史），全部标注采集日期
3. 五维加权评分，权重先与我确认后再打分
4. 枚举「什么情况下应反选落选方」，逐条验证本项目是否命中
5. 给出推荐结论、可执行的风险对冲措施与行动项
```

多选一（3 个及以上候选方）：先按宿主硬约束 + 基本面粗筛出两强，再对决赛深度对比，避免全维度铺开稀释采集深度。

### 驱动高质量选型的关键要素

| 要素             | 为什么重要                                                       | 示例                                                       |
| ---------------- | ---------------------------------------------------------------- | ---------------------------------------------------------- |
| 候选方与决策形式 | 谁 vs 谁、选几个，是 Phase 0 决策框定的第一输入                  | 「React Flow vs LogicFlow，二选一」                        |
| 需求来源         | 考题先行：R1..Rn 是评分锚点，无需求画像则对比失去射程           | 需求文档链接 / 预研文档 §4.8                               |
| 宿主硬约束       | 技术栈、许可证、合规直接构成反选条件甚至一票否决项              | 「React 18 + TypeScript」「需信创合规」                    |
| 权重显式确认     | 对抗「先打分后配权重凑结论」的权重暗箱陷阱                      | 「维护 30 / 研发 25 / 扩展 20 / 能力 15 / 性能 10」        |
| 产出形态约定     | 触发成稿模板 + 质量 checklist 自检，而非聊天式结论               | 「产出可评审的选型决策文档，落到 docs/」                   |

### 低质量选型的反模式

- 只报库名（「A 和 B 选哪个」）→ 无需求射程，退化为百科式功能罗列；应先补需求画像再评估
- 不给宿主环境 → 技术栈匹配类反选条件无法验证，研发投入估分失去锚点
- 用印象代替实测（「A 社区更活跃」）→ 违反硬数据红线，结论不可追溯
- 一次全维度对比 5+ 个候选方 → 采集深度下降；应先粗筛出两强再对决赛
- 选型与实施混在一问（「选完直接装上」）→ 未过评审与 POC 硬闸门就引入依赖，决策翻转时全量返工

### 衔接范式

选型决策文档经评审通过后，按风险对冲行动项先过 POC 硬闸门（估时口径 / 关键交互验证），再正式引入依赖；结论超过 6 个月未落地，复用前必须按数据时效陷阱重测（见 [reference.md](reference.md)）。

## 工作流程

```
Progress:
- [ ] Phase 0 决策框定
- [ ] Phase 1 需求画像
- [ ] Phase 2 硬数据采集
- [ ] Phase 3 基本面对比
- [ ] Phase 4 五维深度分析
- [ ] Phase 5 加权评分矩阵
- [ ] Phase 6 反选条件验证
- [ ] Phase 7 风险对冲
- [ ] Phase 8 成稿与自检
```

**Phase 0 决策框定**：明确决策问题（谁 vs 谁、选几个）、宿主硬约束（技术栈/许可证/合规）；与用户确认评估维度与权重（默认值见下，调整须用户认可）。

**Phase 1 需求画像**：从需求文档提炼 R1..Rn 硬性要求，每条注明出处；剔除「业务层能力」（两方均不提供、由自有代码实现），标注为**非区分项**。

**Phase 2 硬数据采集**（命令与端点见 [reference.md](reference.md)）：GitHub 指标、npm 周下载量（注明镜像源偏差口径）、版本史与升级方式（渐进迁移 vs 重写级破坏）、商业模式查证；全部标注采集日期。

**Phase 3 基本面对比表**：出品方、维护主体性质（商业公司 / 企业兼职 / 纯社区）、商业模式、许可证、核心模型、典型用户。

**Phase 4 五维深度分析**（打分锚点见 reference.md）：

1. **长期维护成本**：升级连续性、停维兜底（fork 成本）、问题解决效率、人才池
2. **研发投入资源**：一次性（分工作项列对比表）、持续（每次迭代的隐性税）、年度升级成本
3. **可扩展性**：先定义「对本项目」的真实扩展含义再比较
4. **能力与场景**：区分「通用能力」与「有效能力」，按有效能力口径打分
5. **性能与体积**：本项目规模富余且无差异时按低权重处理

**Phase 5 加权评分矩阵**：1~5 分 × 权重，逐行附「关键依据」。

**Phase 6 反选条件验证**：把落选方的每项真实优势转写为「应反选的条件」（技术栈不匹配 / 落选方独有刚需 / 文档语言约束 / 合规约束 / 未来场景演化），逐条标注本项目是否命中；零命中时明确写「反选通道关闭，二选一成立」。

**Phase 7 风险对冲**：选定方的风险清单 + 可执行对冲（锁版本、架构隔离、fork 预案、POC 硬闸门、沉淀内部中文 cookbook、禁止依赖闭源组件等），禁止口号式措施。

**Phase 8 成稿**：按下方模板输出；成稿后跑 reference.md 的质量 checklist 自检。

## 默认权重（调整需用户确认）

| 维度         | 默认权重 | 说明                   |
| ------------ | -------- | ---------------------- |
| 长期维护成本 | 30%      | 基础设施类选型默认最高 |
| 研发投入资源 | 25%      | 一次性 + 持续成本并重  |
| 可扩展性     | 20%      | 按本项目扩展语义打分   |
| 能力与场景   | 15%      | 按有效能力口径         |
| 性能与体积   | 10%      | 非决策级差异时更低     |

场景调整：短生命周期工具可降维护至 15%、升研发投入；核心基础设施可升维护至 40%。

## 输出文档结构模板

```markdown
# [X vs Y 选型深度对比]

> 数据采集日期 / 上游文档链接

1. TL;DR（推荐 + 总分 + 三条核心理由 + 反选条件命中情况）
2. 需求画像（R1..Rn 表，注明出处与非区分项）
3. 基本面对比（硬数据表，含采集日期）
4. 五维深度分析（每维先公道话后打分）
5. 加权评分矩阵
6. 反选条件验证表
7. 风险对冲表
8. 结论与行动项
9. 附录：数据来源（API 端点与采集日期）
```

## 质量红线

- 禁止无数据支撑的断言（"社区活跃"必须附 star/下载量/日期）
- 禁止隐藏落选方优势；禁止把无效供给计为优势
- 禁止用共同短板作区分项
- 禁止未经用户确认擅自定权重
- 结论必须可追溯到「需求画像条目 + 实测数据」
