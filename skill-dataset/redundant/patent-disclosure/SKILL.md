# 专利交底书撰写助手

根据用户提供的技术材料（产品文档、PRD、会议记录、代码设计文档等），按照公司软件类专利交底书模板生成完整的专利交底书 Markdown 文档。

## 输入材料

用户可能提供以下一种或多种材料：
- 产品需求文档（PRD）
- 技术架构设计文档
- 会议记录/讨论纪要
- 代码仓库中的相关文件
- 口头描述的技术方案

如果用户只提供了粗略描述，主动询问补充信息直到能提炼出明确的技术方案。

## 工作流程

### 第一步：理解技术方案

阅读用户提供的所有材料，提炼出：

1. **技术领域**：这个方案属于什么领域
2. **要解决的问题**：现有技术的哪些不足促使了本发明
3. **核心技术方案**：用什么方法解决问题
4. **关键创新点**：与现有技术相比，本方案有哪些差异化的新颖之处

向用户确认提炼结果是否准确，确认后进入下一步。

### 第二步：拟定发明名称和关键词

根据技术方案拟定：
- **发明名称**：格式为"一种[技术手段]的[目的/效果]方法及系统"
- **检索关键词**：为每个核心创新点准备 1-2 组检索关键词（每组 3-5 个词）

### 第三步：专利检索（调用 patent-search 技能）

使用第二步拟定的关键词，调用 `patent-search` 技能进行智慧芽检索。该技能会：
1. 协助用户登录智慧芽
2. 逐组执行检索
3. 提取相似专利
4. 分析差异点
5. 返回结构化检索结果

将检索结果填入交底书的"智慧芽检索记录"表格。

### 第四步：按模板撰写交底书

读取模板文件 `references/template.md`，按以下结构生成完整交底书：

#### 声明确认
保留原文，签名处留空或填入用户姓名。

#### 一、基本信息
- 填写发明名称
- 选择应用状态（A/B/C/D）
- 填入第三步的检索结果

#### 二、背景介绍
**（一）现有技术方案：**
- 描述现有技术的工作流程（分步骤）
- 用 Mermaid 流程图展示现有技术的处理流程
- 要具体到技术细节，不能泛泛而谈

**（二）现有技术的问题：**
- 逐条列出问题（问题1、问题2...）
- 每个问题先用加粗标题概括，再用一段话展开解释
- 问题要与后续的发明方案对应（每个问题对应一个创新点）

#### 三、本发明方案
**（一）方案描述：**

结构要求：
1. 先列出总步骤概述（S1、S2、S3...）
2. 画整体方案流程图（Mermaid）
3. 逐步骤详细说明，每个步骤包含：
   - 技术问题是什么
   - 技术方案是什么
   - 用 Mermaid 画该步骤的细节流程图
   - 标注"重要技术点"或"核心发明点"

流程图要求：
- 使用 Mermaid 代码块（```mermaid）
- 图类型选择：整体架构用 `graph TB`，状态转换用 `stateDiagram-v2`，时序交互用 `sequenceDiagram`，数据流用 `graph LR`
- 节点文字简洁，复杂说明放在图外的文字中

**（二）实际应用举例：**
- 用一个具体场景串联整个技术方案
- 分阶段描述用户如何使用、系统如何响应

#### 四、创新点说明
- 逐条列出（创新点1、创新点2...）
- 每条格式：加粗标题 + 与现有技术的对比说明
- 突出"本发明做了什么不同的事"

#### 五、可替换方案
- 列出核心模块的替代实现方式
- 说明替换后方案仍然成立的原因

### 第五步：输出与确认

将完整交底书保存为 `.md` 文件，输出路径建议：
- 如果用户指定了路径，按指定路径
- 否则默认保存到项目的 `docs/prod/专利/` 目录下

文件命名：`专利交底书_{发明名称简称}.md`

### 第六步：DOCX 转换

Markdown 输出完成后，默认继续生成 DOCX 版本以便提交；不要把 DOCX 转换作为可选项再询问用户。

先检查文档是否包含 Mermaid 图：

- 若不包含 Mermaid 图，直接执行转换脚本。
- 若包含 Mermaid 图，必须明确告知：外部服务会接收流程图源码，可能包含未公开技术细节；优先建议用户提供本地/自托管 Mermaid 渲染服务地址。
- 只有在用户明确同意将 Mermaid 图发送到外部服务后，才能追加 `--allow-external-rendering`；否则应使用本地/自托管渲染服务，或说明 DOCX 转换被外部渲染安全策略阻断。

执行脚本：

```bash
python3 ~/.claude/skills/patent-disclosure/scripts/convert_to_docx.py <输出的.md路径> [--output <自定义.docx路径>]
```

如用户明确同意使用外部 `mermaid.ink` 渲染：

```bash
python3 ~/.claude/skills/patent-disclosure/scripts/convert_to_docx.py <输出的.md路径> --allow-external-rendering [--output <自定义.docx路径>]
```

如使用本地或自托管渲染服务：

```bash
python3 ~/.claude/skills/patent-disclosure/scripts/convert_to_docx.py <输出的.md路径> --mermaid-base-url <本地或自托管地址> [--output <自定义.docx路径>]
```

- Mermaid 图默认禁止发送到外部服务；如需使用 `https://mermaid.ink/`，必须获得用户明确同意并传入 `--allow-external-rendering`
- 图片输出默认在同级 `diagrams/` 目录，可随 docx 一并提交；如果图中包含敏感信息，提醒用户转换后可自行清理该目录
- 需要依赖：`pandoc` 和 `Pillow` 库（pip install Pillow）
- 如果依赖不满足（如 pandoc 未安装），清晰告知用户缺少什么、如何安装，而不是跳过
- 转换完成后，告知用户 docx 路径和图片目录路径；失败时说明原因

## 写作原则

1. **具体到可实现**：目标是让一个刚入行的人根据描述能具体实现出来。避免"优化了xxx"这类模糊表达，要写清楚具体怎么做。

2. **问题-方案对应**：第二节的每个问题要在第三节有对应的解决方案，第四节的创新点要能回溯到具体的方案步骤。

3. **图文结合**：每个核心技术点都配 Mermaid 流程图，让审阅者能快速理解方案逻辑。

4. **差异化明确**：始终围绕"我们做了什么不一样的事"展开，而不是泛泛描述AI/大模型/云计算等通用概念。

5. **语言风格**：正式但不晦涩，避免过度使用专业术语堆砌。关键概念首次出现时给出简要解释。
