# ERP / 业务系统测试用例编写

## 何时启用

用户需要：**编写、补全、评审、去重**功能测试用例，或输出 **需求覆盖度** 时，按本技能执行。

## 编写取向

- 模拟**终端用户**真实操作（菜单/单据/审批/仓配/财务等），顺序为 **主流程 → 分支流程 → 异常流程**。
- 贴近 **ERP、业务系统、端侧产品** 实际使用，避免纯接口描述代替用户路径（除非用户明确要求仅接口层）。

## 用例质量标准（评审 checklist）

1. **需求覆盖**：显性/隐性规则、正向/反向/异常；核心逻辑不漏测。
2. **可执行**：前置条件、**操作步骤**、测试数据、预期结果**唯一、无歧义**，他人无需二次沟通即可执行。
3. **有效不冗余**：每条验证独立逻辑或风险点；删除重复与无效用例。
4. **粒度**：一用例**一个核心验证点**；不堆多条无关逻辑。
5. **优先级**：核心/高风险 **P0/P1**，边缘低优；执行顺序合理。
6. **易维护**：字段完整、命名统一；缺陷高发区（边界、空值、特殊字符、并发、异常链路）有覆盖。

## 用例输出字段（必须齐全）

| 字段 | 要求 |
|------|------|
| 功能模块 | 菜单/模块/子系统 |
| 测试项 | 一句话说明验证点 |
| **操作步骤** | **编号步骤**：进入路径、点击/录入顺序、提交或触发动作；关键观测位置（页签/单据状态/提示区） |
| 测试数据 | 可复现的具体数据（账号、物料、单号、数量等） |
| 前置输入/前置条件 | 环境、权限、主数据、已有单据 |
| 预期结果 | 可判定：界面、提示、状态、数据结果 |
| 验证结果 | 执行后的实际结果：通过/不通过/待重新验证；未执行时写明原因 |
| 对应需求项 | 与需求文档条目/编号一致；多对一时标明主验证与顺带覆盖（见下） |
| 优先级（建议） | P0 / P1 / P2 |

**操作步骤**禁止模糊表述（如「按流程操作」）；**预期结果**应与步骤可一一对照。

## 飞书多维表格落地方法

当用户要求把用例写入飞书多维表格（Base）时，必须使用结构化字段，不得把所有内容拼接到单个“文本”字段。推荐建立“01-测试用例”表，字段顺序如下：

| 字段 | 类型 | 规则 |
|------|------|------|
| 测试用例ID | 文本（主字段） | 统一编号，如 TC-P01、TC-O01；覆盖度说明使用“测试说明” |
| 功能模块 | 文本 | 支持按模块筛选、分组 |
| 测试项 | 文本 | 一句话验证点，可包含场景标题 |
| 前置输入/前置条件 | 文本 | 环境、权限、主数据、已有单据 |
| 测试数据 | 文本 | 具体账号、单号、物料、数量、日期等 |
| 操作步骤 | 文本 | 编号步骤，写清菜单路径、输入顺序、触发动作和观察位置 |
| 预期结果 | 文本 | 与步骤对应的唯一、可判定结果 |
| 验证结果 | 单选或文本 | 推荐单选：通过、不通过、待重新验证；未执行时填写原因 |
| 对应需求项 | 文本 | 标注主验证/顺带覆盖及需求编号 |
| 优先级 | 单选 | P0、P1、P2；默认让 P0/P1 场景优先执行 |

如果用户还需要缺陷闭环，建立独立的“02-测试问题反馈”表，推荐字段为：反馈人、日期、溯源变更单号（可按团队习惯简化为“单号”）、物料编码、问题描述、截图、问题类型、问题状态、跟进人、问题处理结果、问题处理结果截图。其中：

- 问题类型为单选，枚举：系统BUG、优化需求、咨询答疑、业务操作问题。
- 问题状态为单选，枚举：待处理、处理中、待验证、已闭环。
- 截图、问题处理结果截图使用附件类型，不写入普通文本字段。
- 日期使用日期时间类型；反馈人、跟进人是否使用人员字段，按用户现有表结构保持一致，不擅自改型。

### Base 写入与核验要求

1. 写入前先读取真实 Base、数据表、字段和视图 ID；不能把 Wiki URL 或孤立 token 当作 `base_token`。
2. 先读取字段结构，再按字段类型构造记录；单选只能写入已存在的枚举值，附件必须走附件专用能力。
3. 设置视图可见字段和顺序，确保核心列（含验证结果、优先级）没有被隐藏；字段存在不代表用户在当前视图可见。
4. 写入后回读字段定义、枚举、视图可见列和记录数量；至少抽样核对一条用例和一条问题反馈记录。
5. 对用户手工调整后的表格做差异检查时，分别比较：表名、字段增删改、字段类型、单选枚举、视图列顺序/隐藏状态、记录内容和空表状态；只报告差异，不擅自覆盖用户调整。

## 需求覆盖度（输出时必须带规范）

**公式**：需求覆盖度 = **至少被一条用例关联的需求点数** ÷ **当期纳入统计的需求点总数**。  
在报告中写清**分母范围**（如本迭代、本模块）。

**必须同时遵守**：

1. **需求点粒度**：以需求文档中的**需求内容条目**（清单编号或可验收小节）为统计单位；**禁止**按段落随意拆合，避免虚高/虚低覆盖。
2. **覆盖关系**：一条用例对应多个需求点时，标明 **主验证点** 与 **顺带覆盖**，便于评审是否仍需单独用例。
3. **未覆盖清单**：与覆盖度**同批输出**表格：需求点标识、未覆盖原因（排期、环境/数据不具备、与既有用例重复验证、外部依赖未就绪、本迭代不纳入等）。

## 交付物结构建议

1. 用例表（或 Markdown 表格）按模块分组，列与上表一致。  
2. **需求覆盖度**一行：百分比 + 分子/分母说明。  
3. **未覆盖需求点清单**（含原因）。  
4. 可选：**用例与需求追溯简表**（用例 ID、主验证需求 ID、顺带需求 ID）。

## 自检（输出前快速过一遍）

- [ ] 每条用例是否有**编号操作步骤**与**可判定预期**？
- [ ] 主流程、关键分支、关键异常是否都有代表用例？
- [ ] 多需求映射是否标了主验证/顺带覆盖？
- [ ] 覆盖度分母是否与需求清单一致、并附未覆盖清单？
