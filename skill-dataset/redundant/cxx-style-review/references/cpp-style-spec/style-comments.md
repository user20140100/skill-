## 1-3 注释
说明：注释的总体原则是帮助开发者快速理解代码的作用或者含义。

### 1-3-1 文件首部/函数 注释格式


修改：格式待定
1-3-1-1、\[ES] 每个文件都必须含有首部注释，文件首部注释格式：
```
/* Copyright (C), xxxx-xxxx, Liuhuan Info Tech. Co., Ltd. All rights reserved.
 * Function:
 * Author:
 * Update:
 */

说明：
第1行为版权声明，xxxx-xxxx表示 文件创建年份-文件最后更新年份；
第2行为介绍文件作用，简述其作用即可；
第3行为作者，参与代码编写的作者都可以写上；
第4行为记录比较大的更新变动；

1行超过120字符时，允许换行，换行注意对齐。
```

正例：
```
/* Copyright (C), 2024-2025, Liuhuan Info Tech. Co., Ltd. All rights reserved.
 * Function: xxx数据处理
 * Author: liuguangyi@cviauto.com / yuanchuqin@cviauto.com
 * Update: 2024-1-1 首次创建 / 2025-1-1 适配6125平台
 */
```

1-3-1-2、\[ES] 函数的作用较为简单时可以使用单行注释，但函数作用较为复杂需要更详细的解释时，函数首部注释格式为：
```
/**
 * @brief   简述函数功能（一句话概括）
 * @details 详细说明函数的实现逻辑、使用场景、特殊处理等（可选）
 *
 * @param  param1 参数1的名称，说明其含义、取值范围、是否可为NULL等
 * @param  param2 参数2的名称，同上（多个参数依次列出）
 * 
 * @return  返回值的类型及含义，不同返回值代表的场景（如成功/失败的标识）
 * 
 * @note    注意事项（如线程安全性、调用前需满足的条件等，可选）
 * @warning 警告信息（如可能导致的风险，可选）
 * @see     相关函数或宏定义（可选）
 */
 
 说明：写注释时，上述写了‘可选’的字段可以不写，但有时建议都写上
```

### 1-3-2 细则

1-3-2-1、\[ES] 请不要加无意义的注释。

反例：
```
// 获取文件信息
int GetFileInfoById(const fileId, FileDate* date) {
    // do some thing...
}
// 这里函数命名已经足够让开发者理解函数的作用，注释内容多此一举，是无意义的注释。
```

1-3-2-2、\[ES] 注释语言统一使用中文（固定格式除外），内容要简洁准确，请不要使用含糊不清的词语，或表述的句子带有歧义。
说明：目前六环大部分开发者第一语言为中文，中文能更简洁准确描述代码含义，且更易于被阅读者理解。

1-3-2-3、\[ES] 自身命名不能够完全表达出含义的函数、变量、结构体、枚举等，建议加注释加以解释。

1-3-2-4、\[ES] 注释应该位于被解释代码的末尾或上方，请不要将注释插入到代码中。

反例
```
// 不符合注释规范，注释嵌入到了代码中
if (currentValue > FIRST_LEVEL_THRESHOLD) /* 开启恢复惩罚机制 */ {
    // do some thing
}
```

1-3-2-5、\[ES] 修改代码时，如果代码作用、含义变更，要同步修改注释；如果代码删除，对应注释也要删除。

1-3-2-6、\[ES]\[SC] 被注释的代码请不要提交上库。
说明：注释代码，开发者可以在本地调试时使用，但请不要提交上库。如果大家都将注释的代码提交上库，库上无用代码会越积越多，影响代码整洁、影响代码可读性、影响代码维护，如某个开发者在开发过程中不小心将注释的代码去掉注释符并提交上库，将会引入新的问题。
