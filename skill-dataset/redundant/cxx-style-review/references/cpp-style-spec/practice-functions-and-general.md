## 2-5 函数

### 2-5-1 通用规则

2-5-1-1、\[ES] 函数的代码行数不允许超过60行（包括函数头、末行右大括号、空行、注释，但不包括函数首部注释），超过60行的函数需要进行拆分。
说明：函数超过60行时，大部分屏幕已经无法在不纵向滚动的条件下浏览整个函数的代码，不利于开发者理解函数上下文。函数行数越多，可读性越差。

2-5-1-2、\[ES]\[DS] 函数内，大括号嵌套层数不允许超过4层，其中循环嵌套层数不允许超过3层。
说明：对于if条件分支产生的嵌套，检查是否能使用“卫语句”减少嵌套层数；对于循环层数超过3层的代码，时间复杂度的次数高，可用性非常差，要思考用时间复杂度更好的算法。

改为圈复杂度

2-5-1-3、\[ES]\[SC] 对于条件判断中类似“不满足则不做任何事”的逻辑，应该使用“卫语句”提前返回。
说明：使用“卫语句”的好处，一是防御错误条件下执行了不该执行的代码，二是减少大括号嵌套层数，可读性更好。

正例：
```
void FilterData(Data* data) {
    if (data == nullptr) {
        return;
    }

    // do some thing
}
```

反例：
```
void FilterData(Data* data) {
    if (data != nullptr) {
        // do some thing
    }
}
```

2-5-1-4、\[ES] 在声明函数时，对于非指针类型参数、非引用类参数、或不允许修改的指针类型参数、不允许修改的引用类型参数，请加const修饰，移动语义除外。
说明：非指针类型参数、非引用类参数，是实参的拷贝，一般只用于读取（一般不做修改操作，如果需要修改，可以再定义一个局部变量，将入参赋值（拷贝）给这个局部变量，对这个局部变量进行修改），所以用const修饰；而不允许修改的指针、引用类型参数用const修饰能让编译器进行检查，防止错误的修改。

2-5-1-5、\[ES] 在定义函数时，无参数函数的括号中写上void关键字，函数实现处不需要。
说明：声明函数出，空参数用void关键字，可以非常醒目的表示该函数不需要入参。

2-5-1-6、\[ES] 声明函数时，输入类型参数应该放在输出类型参数前。

正例：
```
uint32_t GetValidData(const Data *src, const uint32_t srcSize,
    Data *des, uint32_t desSize);
// src、srcSize为输入型参数，放在前面；des、desSize为输出型参数，放在后面
```

2-5-1-7、\[SC] 提供给外部使用的函数（C语言非static函数，C++类非中private域下的函数），都必须进行入参校验，如指针非空校验，变量取值范围（如果有范围要求）校验等。

2-5-1-8、\[SC] 对于调用外部的函数，如果返回值非void的，需要进行返回值校验（执行结果值判断，指针非空校验等），确认不进行返回值校验的，加上void关键字标明。

正例：
```
// memset函数绝大概率不会有问题，忽略返回值校验，用void标明
(void)memset(arr, 0, sizeof(arr));
```

【建议】

2-5-1-9、 \[ES] 定义函数时，入参请不要超过5个。
说明：入参过多时，对调用者不友好，应该将参数封装为结构体或数据类。

2-5-1-10、\[ES] 函数中使用到的局部变量，应该在最接近使用的代码前定义，一是缩小局部变量作用范围，防止未初始化就使用问题，二是让局部变量的作用更清晰。

正例：
```
bool ProcessData(uint32_t* data, uint32_t size) {
    if ((data == NULL) || (size == 0)) {
        return false;
    }
    // do some thing
    uint32_t count = 0;  // 在最接近使用的代码处定义
    for (uint32_t i = 0; i < size; ++i) {
        if (data[i] != 0) {
            ++count;
        }
    }
    return true;
}
```

反例
```
bool ProcessData(uint32_t* data, uint32_t size) {
    uint32_t count = 0;  // 未在最接近使用的代码处定义
    if ((data == NULL) || (size == 0)) {
        return false;
    }
    // do some thing
    for (uint32_t i = 0; i < size; ++i) {
        if (data[i] != 0) {
            ++count;
        }
    }
    return true;
}
```

2-5-1-11、\[ES] 函数中，对于在同一个if - else if - else 、 switch - case 中多个分支均使用的变量，应该提取到条件分支外，避免多次在不同的分支上声明定义。

2-5-1-12、\[DS] 函数中超过5行，重复次数超过3次的相同或相似（只是部分变量不同，可以通过参数方式变成一样）的代码段，必须封装为函数。
说明：防止类似代码片段反复出现，反复出现的代码，为维护增加难度，为霰弹式修改等问题提供了来源。

2-5-1-13、\[SC] 对于多进程/多线程可以访问的变量，请不要定义函数返回该变量的指针、引用。
说明：函数返回多进程/多线程可以访问的变量指针、引用，调用者可能对于变量的临界属性未知，对临界变量进行了不受保护的并发读写操作，会产生未知的严重错误。

2-5-1-14、\[DS] 功能类函数只做具体的业务功能，其参数只允许计算类参数，不要出现控制类参数。（调度类函数设计时也不宜有过多的计算型参数。）
说明：函数可以分为调度类函数、功能类函数。调度类函数指的是根据不同的条件（如：全局变量、配置值、成员变量、入参等）执行不同的逻辑分支的函数，功能类函数是指根据入参做具体业务、计算的函数，如果具体功能类函数还做调度控制，说明设计不规范。这样的函数会导致后期维护、升级中，函数内部代码被反复修改，而不是通过拓展新函数达到目的。

【规则描述待修正】

### 2-5-2 C++规则

2-4-2-1、\[SC] C++函数声明时优先考虑引用传递参数，且引用不允许修改时，必须使用const关键字修饰。
说明：优先考虑引用传参是为了避免不必要的拷贝，且比起指针，引用不容易出错。

2-4-2-2、\[ES] C++函数尽量减少使用输出类型参数，而是直接通过return进行返回（多个返回值可以通过std::pair、std::tuple返回），调用结果可以通过异常机制进行处理。

## 2-5 综合

### 2-5-1 禁用的关键字/禁用的编码方式

2-5-1-1、\[SC] 请不要使用assert断言。
说明：断言对错误的处理方式十分不友好，应该改为对应异常处理机制。

2-5-1-2、\[SC] 请不要使用goto。
说明：goto破坏程序执行的顺序结构，使得执行流程变得混乱，代码更容易出错，可读性降低等弊端，使用goto实现的流程可以用为break、continue代替。

2-5-1-3、\[SC] 请不要使用union联合体（共用体）。
说明：联合体中，多个字段共享一出内存，且某时使用哪个字段还需要熟悉业务、上下文条件下进行判断，误用则导致数据被覆写、读错数据等问题，不论是可读性、可维护性、安全性都造成不好的影响。

【业务层不要使用】

2-5-1-4、\[SC] 请不要使用魔鬼数字。部分常用且意义固定的字面量除外，如0、'\0'等。
说明：魔鬼数字是指直接出现在代码中的数字、字符、字符串（日志除外）字面量。魔数的存在，使得代码可读性、可维护性都降低，应该用规范命名的常量、宏替代。

### 2-5-2 全局变量/结构体

2-5-2-2、\[ES] C语言文件内全局变量必须定义为static，如果有需要提供给外部文件使用，请提供get、set接口，请不要将全局变量随意暴露给外部。

跨文件、Cpp不能使用全局变量

2-5-2-3、\[ES] 结构体、类中的属性（成员变量）避免过多，当成员变量过多时，大概率违法职能单一原则，应该考虑从不同维度方向进行划分，分成多个不同的结构体。请不要将职能、含义等不相干的成员定义在同一个结构体、类中。

【建议】

2-5-2-4、\[DS] 当结构体中有位域类型的属性时，在保持相近的属性靠近条件下，还要考虑空间的合理利用，比如两个位域类型一样的字段尽量不要隔开，否则有可能增加结构体占用的字节数。

```
typedef struct {
    volatile uint32_t enable : 1; // 使能位
    volatile uint32_t mode : 4;   // 模式位
    volatile char version : 8;    // 版本 中间插入一个其他类型，使得结构体占用字节数增加
    volatile uint32_t status : 2; // 状态位
} ControlRegister;
```

【删除】

2-5-2-5、\[ES] 当项目中、模块中已经为某个数据类型起了别名，请统一使用类型的别名，且除非起别名能更有助于提高代码可读性，否则请不要滥给数据类型起别名。

【删除】

### 2-5-3 线程

2-5-3-1、\[ES] 使用原始的线程创建线程的接口时，应该为线程命名，命名规则为：模块名+线程作用。
说明：线程命名后，方便后续有问题可以快速定位对应线程。

【建议】

2-5-3-2、\[ES] 模块驻守类工作线程（循环执行任务）的创建，请集中在模块初始化中创建，线程间时序可以用多种手段做同步控制。
说明：线程的创建宜早不宜迟，集中创建线程一是方便管理线程、做线程间的同步控制；二是可以非常清晰的了解到这个模块的工作流程、有哪些线程；三是方便维护，释放线程与回收资源时不用去寻找散落到模块代码各处创建的线程。

2-5-3-3、\[DS] 非驻守类工作（非循环执行任务）线程，请不要使用原始的线程接口创建线程，而是应该将任务交给线程池、定时器，其中异步耗时任务交给线程池，与时间有关的任务交给定时器。
说明：频繁的创建与释放线程会增加不必要的性能消耗。

2-5-3-4、\[DS] 保证多线程访问的临界变量线程安全时，优先考虑无锁方式实现，如果用互斥锁实现，请尽可能减小锁对数据的封锁粒度。
说明：无锁方式保证线程安全，可以最大程度不影响线程的并非；同理，封锁粒度越小，对线程并发的影响越小。

【建议】

2-5-3-5、\[SC] 选择使用互斥锁保证线程安全，当需要持有多个互斥锁时完成业务工作时，请保证使用到相关互斥锁的所有地方持有锁、释放锁的顺序一致，避免产生死锁。

### 2-5-4 日志
说明：日志有两大作用，一是帮助定位问题，二是帮助自证清白，所以日志内容要谨慎且完整。

2-5-4-1、\[ES] 日志请用简洁的英文表述，请不要出现汉字、拼音。 
说明：日志可能不只是本公司的开发者阅读，在澄清问题、自证清白时，日志原文件可能会交给客户、第三方阅读，如果日志内容中出现汉字会显得不够专业，影响公司形象。

2-5-4-2、\[ES] 编码过程日志等级的选择，应该符合业界公认的日志等级对应处理事件规范（前提是日志系统、日志框架也应该符合规范），如：
trace:量产需要调试的信息
a.debug:开发过程的调试信息，目的是用于开发者开发过程调试使用，不会出现在release版本软件中（上线后的软件一般只开启info等级日志），如开发过程需要详细跟踪的流程、数据等；
b.info:需要release版本中保留的软件运行时的关键信息，目的是方便软件上线后定位问题，如某些关键参数、关键结果等；
c.warn:软件运行过程需要特别注意的信息，对软件系统不利的因素等，目的是引起软件维护者、开发的注意，如：外部不合法的输入、监控线程的关键数据、内存资源即将耗尽等；
d.error:系统运行过程中，自身的错误记录，目的是方便软件开发者、维护者快速定位问题，如引发系统崩溃、不能正常工作的信息。

2-5-4-3、 \[SC] 日志中请不要记录任何敏感信息、涉密数据，包括：密码、密钥、部件涉密数据、车辆VIN码、客户信息等。
说明：日志在用于自证清白时，可能外传给客户，甚至流入未知的第三方，如果保存有任何敏感信息、涉密数据，会对公司造成损失。（为了调试方便，可以本地代码打印调试，但不允许提交上库。）
