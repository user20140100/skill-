# 概述
## 1 说明

本文旨在通过制定统一的C语言、C++语言的编程规范，帮助开发者形成良好的、统一的编码风格，形成安全的编码意识，使得代码可读性更好、健壮性更高，从而在编码之初就能最大程度的避免可能产生的各种问题。通过该文的规则作为标准，我们可以统一且明确（没有歧义）的认定每行代码、每个字符（比如每一个空格）是否符合规范的要求。
本文中的各种规则，并非作者通过主观意愿制定的规则，而是参考了业界主流的规则定义，如《华为C语言编程规范5.0》（非公开文档）、《阿里巴巴Java开发手册1.4.0》（公开文档）、六环旧的《C/C++ 编码规范》等，或者是一些开源代码统一的良好的编码风格等等。参考这些规范，一是我们可以最大程度的学习到业界优秀企业的经验所得（他们在制定这些规则时肯定已经有了充分的考虑），二是可以让我们在学习第三方开源代码，或在业界技术交流时降低学习成本。
由于作者水平有限，本文可能存在诸多错误或遗漏的地方，欢迎各位读者指正、或参与到该文档的更新修订工作中，使得该文档更加完善。
最后再次阐明，本文严格的要求，并非是有意增加开发者学习成本、工作负担，而是为了让开发者能明确自己每一行代码、甚至每一个字符的意义，更好地写出高质量的代码。

## 2 核心原则

可读性(Readability)：代码虽然是给机器执行的，但在开发、维护过程需要人去阅读。清晰、一致的风格可以让开发者快速理解代码含义，减小维护与再开发成本。
简洁性 (Simplicity)：在保证算法效率、具备良好拓展性的前提下，尽可能用最简单、最直接的方式解决问题。避免过度设计和不必要的复杂性。
安全性 (Security)：始终优先考虑代码的健壮性和安全性，防止缓冲区溢出、内存泄漏、空指针、线程安全、死锁、隐式泄露等致命问题。
可维护性 (Maintainability)：代码应该易于维护和扩展，模块化、低耦合的设计是关键。
可移植性 (Portability)：代码应尽量避免依赖特定编译器、操作系统或硬件的特性，以保证在不同平台上的兼容性。

## 3 适用范围

a、本公司绝大部分的C、C++代码需遵循本文规则，因特殊情况而无法遵循本文规范（如工具产生的代码），可以通过附加说明与责任人审核的方式忽略对应规则。

b、引入独立成模块的第三方代码、linux内核代码等，可以保留源代码的编码风格，并在修改时也使用源代码的编码风格。（注意第三方代码定义，供应商提供的代码，已经属于公司需要维护的代码范畴，不属于第三方代码。）

## 4 规则考量分类

规则考量分类说明每一条规则考量的依据类型，在每一条规则的前面会标注考量类型的简写字母。

| 考量类型 | 英文全称                  | 英文简写 |
| -------- | ------------------------- | -------- |
| 编码风格 | Encoding Style        | ES   |
| 安全编码 | Secure Coding         | SC   |
| 设计规范 | Design Specifications | DS   |
| 可移植性 | Portability           | P    |

## 5 章节说明

本文主体部分分为三章，分别为：风格规约、实践规约、安全规约。每个章节描述的侧重点不同，其中风格规约主要描述命名、代码格式、注释等内容；实践规约主要描述语法点、关键字、库函数、工具在使用时的良好的方式；安全规约主要描述与安全编码相关的问题（包括程序健壮、信息安全等）。但也并非完全严格区分，比如实践规约中也可能含有排版相关的内容等（最显而易见的就是一条规则中可能会包含多条【考量类型】）。这些章节的重要程度也不分轻重，它们是相辅相成的，共同构成我们完整的编程规范。

每个章节中，有不同部分的分类，每个大类中又分小类，然后是每一条规则。其中每条规则包含【规则描述】，可能有【说明】、【正例】、【反例】内容，【规则描述】即规范准则的阐述，【说明】是对规则的补充或解释说明，【正例】是正确的做法，【反例】为错误的做法。


# 一. 风格规约

## 1-1 命名
说明：命名的总体原则是尽可能用简洁的词汇，表达当前对象的含义，做到见名知意的效果。

### 1-1-1 文件

1-1-1-1、\[ES] 文件命名统一使用大驼峰风格命名，在防止同名与表面含义前提下尽量简短。词语使用因为单词，避免出现非国际词语的拼音。
说明：C++类命名为大驼峰风格命名，文件名与类名同名方便查找文件。

正例：
```
DataAccess.h
DataAccess.c
DataAccess.cpp
```

反例：



```
dataAccess.h // 使用小驼峰
data_Access.c // 使用下划线
Data_Access.cpp // 使用了下划线
data$process.c // 使用了其他符号
shu_ju_fang_wen.cpp // 使用拼音
```



1-1-1-2、\[ES]\[P] 文件后缀要求，头文件后缀统一为.h，C语言源文件统一后缀为.c，C++语言源文件统一后缀为.cpp。

正例：
```
DataAccess.h
DataAccess.c
DataAccess.cpp
```

反例：
```
DataAccess.H // 使用大写字母H作为头文件后缀不符合规范
DataAccess.C // 使用大写字母C作为C文件后缀不符合规范
DataAccess.hxx // 使用hxx作为C++文件的后缀不符合规范
```

### 1-1-2 宏

1-1-2-1、\[ES] 定义宏常量以字母开头，所有字母都用大写，单词之间用下划线分隔。
说明：避免使用下划线开头定义宏，很多三方库的宏定义以单下划线开头，双下划线开头是Cpp标准库中定义的宏，如果定义宏使用下划线开头容易与之混淆。

正例：
```
#define BUFF_MAX_SIZE 1024
```

反例：
```
#define _BUFF_MAX_SIZE 1024 // 下划线开头
#define buff_max_size // 使用了小写字母
```


1-1-2-2、\[ES] 宏函数命名与宏常量基本一致，宏函数参数命名用小写字母，并且尽量用一个单词，如果有多个单词，用下划线分隔。

正例：
```
#define ARRAY_SIZE(x) (sizeof(x) / sizeof(x[0]))
#define UNUSED(x) (x)
#define LOG_DEBUG(format, args...) print("[DEBUG][FILE:%s][LINE:%d][%s]"\
            format "\n", __FILE__, __LINE__, __FUNCTION__, ##__VA__ARGS__)
```

1-1-2-3、\[ES] 条件选择编译类宏命名时，请不要使用带有否定类词语。
说明：一般一个条件选择编译宏，值为true时，表示是什么平台、是什么产品、有什么功能/特性等表肯定的含义，并编译相关代码，如果加否定类词语，表示的含义与习惯的思维相反，容易让人误解。

正例：
```
#define LOG_LEVEL_DEBUG
#define LOG_DEBUG(format, args...) print("[DEBUG][FILE:%s][LINE:%d][%s]"\
    format "\n", __FILE__, __LINE__, __FUNCTION__, ##__VA_ARGS__)
#else
#define LOG_DEBUG
#endif
```

反例：
```
#define NOT_LOG_LEVEL_DEBUG // 使用否定类词语
#define LOG_DEBUG
#else
#define LOG_DEBUG(format, args...) print("[DEBUG][FILE:%s][LINE:%d][%s]"\
    format "\n", __FILE__, __LINE__, __FUNCTION__, ##__VA_ARGS__)
#endif
```

### 1-1-3  变量

1-1-3-1、\[ES] 局部变量的命名使用小驼峰方式命名。

正例：
```
int32_t signalValue = 0;
bool isValid = false;
```

反例：
```
int32_t signal_value = 0; // 使用下划线
bool IsValid = false; // 使用了大驼峰方式命名
```

1-1-3-2、\[ES] 变量命名请不要使用美元符"$"、下划线"\_"。
说明：虽然命名中使用美元符、下划线符合语法，但这首先与小驼峰方式命名矛盾；双下划线开头的变量是C++标准库的命名风格，如果下划线开头命名方式容易与其混淆；下划线、美元符命名不统一，增加代码杂乱感。

反例：
```
int32_t battery$level = 0; // 变量名混用美元符
```

1-1-3-3、\[ES] 变量名请不要使用拼音，国际公认拼音词、特有名词除外。
说明：业界中几乎都使用英文单词进行变量命名，且大部分现有代码都是英文单词命名，混用拼音不优雅。

正例：
```
string liuhuanHardwareVersion; // liuhuan（六环）为特有名词，可以使用拼音
```

反例：
```
int32_t sudu = 0; // 使用拼音命名变量
```


1-1-3-4、\[ES] 变量命名应该根据用途、作用范围进行命名，其中作用范围越大的变量，命名应该详细一些（宁可命名长一些也不可丢弃变量重要的含义），作用范围小的变量，命名可以简洁一些。在保证变量名含义清晰条件下尽可能简洁，但不可滥用缩写（不被公认的单词缩写）。为保证变量名长度不能过长，变量名的字符数不能超过30个（含30个），命名不能完全表示含义的，用注释加以解释。

正例：
```
// app是公认的applicable缩写，msg是公认的message缩写，recv是公认的receiver的缩写
int32_t appMsgRecvCount = 0;

void func() {
    uint32_t count = 0; // 局部变量，命名可以简洁一些
    // do some thing
}

// 变量名长度接近30个字符还不能完全表示含义的，用注释补充说明其含义
bool isLongPressPrevKeyInRadioPage = false; // 是否在收音主页中长按方控的上一曲按钮
bool isLongPressNextKeyInRadioPage = false; // 是否在收音主页中长按方控的下一曲按钮
```

反例：
```
int32_t notiNum = 0; // noti并非notification标准缩写，可读性非常差

// 变量名长度超过了30个字符
bool isLongPressPrevKeyInRadioMainPage = false;
```

1-1-3-5、\[ES] 变量的命名请不要出现拼写错误的词汇、自创词汇、自创缩写等非标准英文单词，以及非公认名词。
说明：变量名出现错误词汇，会降低代码可读性，设置误导开发者对代码的理解。

反例：
```
bool hasConFinish = false; // con到底是config，还是connection的缩写？

// 可以猜测出是config错误拼写为confit,但对于有代码洁癖的同学看起来会很难受
int32_t confitId = 0; 
```

1-1-3-6、\[ES] 变量的命名请不要带有变量类型信息（如用变量类型首字母作为前缀）,但可以带有变量的逻辑结构信息。
说明：变量的命名应当聚焦变量的逻辑用途，而不是变量的类型。对于大部分不带类型信息前缀且规范的变量命名，开发者可以通过变量名字猜测出变量的类型，也可通过代码上下文很容易的获取到变量的类型。而变量名带上类型信息，当类型需要变更时就需要同步修改，且不适用泛化与抽象等。

正例：
```
float speed = 0.0f; // 根据命名、上下文就可获知变量类型

// 布尔类型变量使用类似isXxx或hasXxx命名，开发者很容易知道这是布尔类型变量
bool isValid = false; 

/* 带ptr后缀注重描述变量的逻辑形式是指向User的指针（不限定指针具体类型，可以是裸指针、智能指针） */
std::share_ptr<User> userPtr = std::make_share<User>(User()); 

// 带list后缀注重描述变量的逻辑结构是一个列表，底层类型可以是数组、链表等
std::vector<User> userList(); 
```

反例：
```
float fSpeed = 0.0; // 表明变量是float类型变量，如果后续改为doubel类型则变量名需要修改
User* pUser = NULL; // p前缀表示指针，放在前面，不符合注重变量逻辑用途规范

/* 补充说明：前缀统一不带变量基础类型的信息，实在要带基础类型信息，请加在后缀上（后缀也尽量不要带变量基础类型信息） */
```

1-1-3-6、\[ES] 全局变量命名时加上g字母作为前缀。
说明：前缀g意为global，这与变量命名请不要使用带有变量类型信息有区别，一是全局变量前缀g不表示数据类型，二是全局变量范围太大，带有g前缀意在提醒开发者务必注意该变量作用范围。

正例：
```
static bool gIsSystemInit = false;
```

1-1-3-7、\[ES] 定义指针变量、引用时，符号*、符号&应该靠近类型，强调类型一致性。
正例：
```
uint32_t* countPtr;
uint32* const array; // 常量指针
const char* const message = "Hello";

void ProcessData(uint32_t& data) {
    // do some thing
}
```

反例：
```
uin32_t *countPtr; // *符号应该靠近类型
uin32_t* data, size; // 请不要混合声明，可读性差，指针变量一行声明1个
```

### 1-1-4 常量

1-1-4-1、\[ES] 常量命名为小驼峰风格，带有k前缀。

正例：
```
static const int32_t kTimerTimeoutMs = 1000;

void HandleData(int32_t datas) {
    const uint32_t kTaskTimeoutMs = 100;
    // do some thing...
}
```

反例：
```
static const int32_t TIMER_TIMEOUT_MS = 1000; // 不带k前缀，且为大写字母、下划线分隔
```

### 1-1-5 枚举

1-1-5-1、\[ES] 枚举命名使用大驼峰方式命名，命名中尽可能表述清晰是什么类型的枚举，避免只用Type、State、Mode、Model等。

正例：
```
// 指明是Chip的Model,而不是简单的Model
enum RadioChipModel {
    RADIO_CHIP_MODEL_NXP47901 = 0,
    RADIO_CHIP_MODEL_SILICON47901,
    RADIO_CHIP_MODEL_SILICON47902,
}; 

// 指明是band的类型，而不是简单的type
enum RadioBandType {
    RADIO_BAND_TYPE_AM = 0, // 枚举成员都有RADIO_BAND_TYPE前缀
    RADIO_BAND_TYPE_FM,
};
```

反例：
```

## 1-2 格式
说明：格式的总体原则使代码工整美观，可以很大程度减少开发者阅读代码时的疲劳。

### 1-2-1 空格
说明：总体原则为遵循空格使用规定，任何情况下不多1个空格，也不少1个空格。

1-2-1-1、\[ES] 如果左大括号’{‘前不换行、左大括号’{’后不换行、右大括号’}’前不换行，则留1个空格。特殊情况，如果大括号内没有内容，则括号内不留空格。

正例：
```
// 左括号前不换行，留1个空格
class DataMgr {
    // members
};

std::vector<int> v { 1, 2, 3, 4, 5 }; // 左大括号后不换行、右大括号前不换行，留1个空格

virtual void Func(void) {} // 大括号内没有内容，不留空格
```

1-2-1-2、\[ES] 关键字if、for、while、do、switch与左小括号'('之间留1个空格。

正例：
```
// if关键字与小括号之间留1个空格
if (condition) {
    // do some thing...
}
```

1-2-1-3、\[ES] 除【1-2-1-1】、【1-2-1-2】外，其余情况下，小括号’()’前后都不留空格。

反例：
```
// 小括号中，前后不留空格
for ( int i = 0; i < size; ++i ) {
    // do some thing.
}
```

1-2-1-4、\[ES] 多元运算符前后留1个空格，包括'='、'\=='、'+'、'-'、'+'、'/'、'%'、' ?  :  '（三元条件选择运算符）等等，与操作数关系密切、从属关系的则不需要留空格，如自增、自减、指针符、域访问符等。

正例：
```
uint32_t CountLessThanNumber(const int32_t* arr, const uint32_t arrSize,
    const int32_t min) {
    if (arr == NULL) { // 双等号==前、后都留1个空格
        return 0;
    }
    int count = 0; // 等号=前、后都留1个空格
    for (uint_32_t i = 0; i < arrSize; ++i) {
        // +=号、<=号、条件选择运算符' ? : '前、后留1个空格
        count += (arr[i] <= min) ? 1 : 0;
    }
    return count;
}
```

反例：
```
++ i; // 一元运算符与变量间不需要加空格
userPtr -> name; // userPtr指针与其属性是从属关系，使用指针符->前后不需要留1个空格
```

1-2-1-5、\[ES] 在使用逗号、分号分隔并列关系的元素中，逗号、分号与后面的变量、表达式之间留1个空格。
正例：
```
// 分隔参数的逗号与后面的参数保留1个空格
uint32_t CountLessThanNumber(const int32_t* arr, const uint32_t arrSize,
    const int32_t min) {
    if (arr == NULL) {
        return 0;
    }
    int count = 0;
    for (uint_32_t i = 0; i < arrSize; ++i) { // for中分号";"与前面内容留有1个空格
        count += (arr[i] <= min) ? 1 : 0;
    }
    return count;
}
```

1-2-1-6、\[ES] 变量声明定义时，变量类型与变量之间有且仅有1个空格。

反例：
```
int32_t  count = 0; // 这里类型名与变量名是2个空格，不符合有且仅有1个空格
```

1-2-1-7、\[ES] 单行注释符，如果同一行前面有代码，注释符'//'与代码之间最少保留1个空格，与注释内容之间留1个空格；多行注释符，如果同一行前面有代码，注释符'/\*' 左侧与代码之间保留1个空格，与注释内容之间保留1个空格。

正例
```
// 单行注释符
int32_t value; // 单行注释符

/* 多行注释符 */
int32_t value; /* 多行注释符 */
```

1-2-1-8、\[ES] 空白行不能留有空格。

反例：
```
void Func(void* param) {
    if (param == NULL) {
        return;
    } // 下一行空白行留有空格，可能因为缩进而无意留下
    
    // do some thing...
}
```


1-2-1-9、\[ES] 换行前不能留有空格。

反例：
```
// 左大括号{换行前留了空格
void func() { 
    // do some thing...
}
```


1-2-1-10、\[ES] 静态表、宏、注释等行数较少需要对齐情况下允许多加空格。变量的声明不需要多加空格对齐。
说明：静态表、宏、注释等对齐会后代码工整美观，且每一列含义相同，有助于增加了可读性。变量每一列含义不一定相同，没有对齐的必要。

正例：
```
Static RadioStatusAndHandler radioStatusAndHandler[] = {
    { RADIO_STATUS_NO_READY, RadioInit(void* param, uint32_t paramSize)      },

#define NET_DIAGNOSE_PROTOCAL_BEGING_DIAGNOSE  901
#define NET_DIAGNOSE_PROTOCAL_PROCESS_DIAGNOSE 902
#define NET_DIAGNOSE_PROTOCAL_FINISH_DIAGNOSE  902
```


反例：
```
int32_t quality = 0;
int32_t price   = 0; // 变量声明为了对齐加多了2个空格
```

### 1-2-2 缩进与换行

1-2-2-1、\[ES] 一次缩进统一为4个空格，请不要使用tab符缩进（IDE可以打开显示制表符的选项，如果代码中存在制表符，则不符合规范）。
说明：tab符号在不同IDE中显示宽度不一致，混用空格和tab符做缩进，会导致代码参差不齐。

1-2-2-2、\[ES] 预编译指令任何时候都不缩进。
说明：预编译指令不属于代码逻辑，与代码一起缩进，混在代码中不能让开发者非常醒目的阅读到。

正例：
```
void DataProcess(int* data, bool condition) {
    if (data == NULL) {
        return;
    }
    if (condition) {
    // 预编译指令不和代码一起缩进，正确
#ifdef DEBUG
        DEBUG_LOG(“condition is true.”);
#endif // DEBUG
        // do some thing...
    }
}
```

反例：
```
void DataProcess(int* data, bool condition) {
    if (data == NULL) {
        return;
    }
    if (condition) {
        // 预编译指令和代码一起缩进，错误
        #ifdef DEBUG
        DEBUG_LOG(“condition is true.”);
        #endif // DENUG
        // do some thing...
    }
}
```

1-2-2-3、\[ES] 每个左大括号’{’后换行，括号内的代码增加1个缩进，大括号中内容为空则不换行，大括号内也不留空格。

1-2-2-4、\[ES] 每个右大括号'}'前换行，换行后的'}'比括号内的代码减少1个缩进（对齐左大括号所在列），大括号中内容为空的情况除外；右大括号后，如果是else、else if则与右大括号同行(之间留1个空格)，否则右大括号独立为一行。

1-2-2-5、\[ES] 以分号结束、或必须换行缩进的1行代码中，未超过120个字符不允许换行；相反超过120个字符的必须换行，换行细则：
（1）如果换行超过2行，则只在第1次换行时增加1个缩进，之后的换行与第2行对齐，不再增加缩进；
（2）运算符、成员访问符'.'、域访问符'::'、指针访问符'->'、参数分隔的逗号',' 保留在上一行;
（3）左括号前不换行。
（4）如果第1次换行为小括号中的内容，则换行开始位置可以是1个缩进，也可以在上一行左括号后1个字符的位置。
说明：统一行宽为120个字符，一是大部分屏幕的宽度一般足够看清行宽为120个字符代码。二是如果行宽不一致，会增加了代码参差不齐的杂乱感，且开发者阅读行宽超过屏幕宽度的代码时，需要反复的左右滚动，影响阅读效率。

1-2-2-6、\[ES]在代码中，为了让变量、代码块等对象的分类、逻辑、归属等更加清晰的，可以使用空行间隔开来，但有且只能加1个空行，请不要随意乱加空行、多加空行。

正例：

### 1-2-3 括号

1-2-3-1、\[ES] if、for、while、do、case、default后的代码中，就算只有1行代码，也必须加大括号。

正例：
```
if (!isValid) {
    return;
}
```

反例：只有缩进，没有大括号，可读性差，且容易出现逻辑错误。
```
for (uint32_t i = 0; i < size; ++i)
    if (condition)
        count++;
```

1-2-3-2、\[ES] 一次计算出现多个不同优先级的运算符时，通过加括号方式来控制我们需要的运算符执行优先级次序。
说明：开发者对运算符优先级的记忆可能会出错，通过括号控制计算的优先级，一是不容易出错，二是增加代码可读性。

1-2-3-3、\[ES] if、for、while、bool类型函数参数入参等的逻辑表达式中，如果有多个逻辑对象的计算，要恰当的使用小括号，使得逻辑运算的层级关系更清晰、可读性更好。

正例：
```
if ((a > c) || (b > c)) { // 给a>c与b>c这两个逻辑表达式都加一个括号，层级关系更清晰明显
    // do some thing...
}
```

1-2-3-4、\[ES] 除接口类函数空实现外，其他地方请不要留有空的大括号。

反例：

if (condition) {

    // do some thing...

} else {
} // 这里留一个空的else分支与空的大括号没有任何意义
```

### 1-3-2 细则

1-3-2-1、\[ES] 请不要加无意义的注释。

反例：
```
// 获取文件信息
int GetFileInfoById(const fileId, FileDate* date) {
    // do some thing...
}
// 这里函数命名已经足够让开发者理解函数的作用，注释内容多此一举，是无意义的注释。
```

1-3-2-2、\[ES] 注释语言统一使用中文（固定格式除外），内容要简洁准确，请不要使用含糊不清的词语，或表述的句子带有歧义。
说明：目前六环大部分开发者第一语言为中文，中文能更简洁准确描述代码含义，且更易于被阅读者理解。

1-3-2-3、\[ES] 自身命名不能够完全表达出含义的函数、变量、结构体、枚举等，建议加注释加以解释。

1-3-2-4、\[ES] 注释应该位于被解释代码的末尾或上方，请不要将注释插入到代码中。

反例
```
// 不符合注释规范，注释嵌入到了代码中
if (currentValue > FIRST_LEVEL_THRESHOLD) /* 开启恢复惩罚机制 */ {
    // do some thing
}
```

1-3-2-5、\[ES] 修改代码时，如果代码作用、含义变更，要同步修改注释；如果代码删除，对应注释也要删除。

1-3-2-6、\[ES]\[SC] 被注释的代码请不要提交上库。
说明：注释代码，开发者可以在本地调试时使用，但请不要提交上库。如果大家都将注释的代码提交上库，库上无用代码会越积越多，影响代码整洁、影响代码可读性、影响代码维护，如某个开发者在开发过程中不小心将注释的代码去掉注释符并提交上库，将会引入新的问题。

# 二. 实践规约

## 2-1 文件

### 2-1-1 通用规则

2-1-1-1、\[ES] 单个源文件代码行数不允许超过2000行（包含空行、注释在内），超过2000行的源文件很大可能是因为违反设计原则中的“职能单一原则”，要思考如何拆分文件。
说明：单个文件代码行数过多，可读性会降低，后期如果要维护、拓展都会很困难。

800line

2-1-1-2、 \[ES] 头文件必须自给自足。
说明：头文件如果有使用到非自身定义的宏、类型、变量等，都必须引用对应的头文件。检验方式为头文件可以单独编译通过，或被其他文件作为第1个头文件引用。

除了项目中公共、基础的头文件，其他必现满足

2-1-1-3、\[ES]\[P] 头文件必须使用宏来防止重复include。且应该使用#ifndef加头文件宏的方式解决，请不要使用#pragma once。
说明:预编译指令#pragma含义比较复杂，且不同平台、编译器支持度不同，为保证平台兼容性，#ifndef加头文件宏方式是所有编译器都兼容的做法。头文件宏，一般统一命名为文件名(全大写字母)加_H。

正例：头文件data_process.h
```
#ifndef DATA_PROCESS_H
#define DATA_PROCESS_H

// code...

#endif
```

2-1-1-4、\[ES] 请不要乱引入头文件，即不使用的头文件不引入。

2-1-1-5、\[ES]\[P]\[SC] 头文件顺序引入顺序，需严格按照如下顺序：
a.对应的头文件（.c/.cpp文件）
b.C标准库头文件
c.C++标准库头文件
d.系统/平台相关头文件（第二方库文件）
e.第三方库头文件
f.项目内其他头文件(第一方库文件)
说明：与.c/.cpp对应的头文件放在最开始位置，可以最早发现对应头文件自包含问题；然后是越稳定的头文件靠前，先引入可避免项目内头文件的宏意外污染它们；项目内头文件后引入，可明确依赖关系。

试行

2-1-1-6、\[ES] 源文件中同类元素要写在文件同一区域，各类元素定义顺序（分布位置）需按以下顺序：
a.文件首部注释（版权声明、简洁等）
b.预处理指令，头文件引入#include
c.宏常量定义
d.宏函数定义
e.结构体、别名定义
f.枚举定义
g.变量声明
h.函数声明
i.函数实现
j.C++命名空间，类，结构体定义
说明：自定义数据类型放在最前，方便下文使用。同类元素放在一起，且不同类元素顺序固定，可以让文件结构更加清晰，寻找某个具体元素非常方便；相反没有顺序，随意写在文件各个位置，会增加文件杂乱感，可读性降低、维护困难。

2-1-1-7、\[ES] .c文件、.cpp文件中同一类元素中各个元素相对位置要与.h文件保存一致。
说明：如在.h中声明函数的顺序为：
```
void Init(void);
void Process(void);
void Destroy(void);
```
那么在.c/.cpp文件中，函数实现也应该保持这个顺序。

2-1-1-8、\[ES] 源文件中同类元素(用途相似、处理某个业务流程等)，应该聚集到一起，不同类型的元素可以用一个空行分隔。
说明：好的头文件，相当于一个大纲目录，顺序、分类都非常有条理；.c/.cpp文件也同理。

正例：
```
// init
void InitOfStandard(void);
void InitOfSimple(void);

// process
void ProcessOfStandard(void);
void ProcessOfSimple(void);

// destroy
void DestroyOfStandard(void);
void DestroyOfSimple(void);
```

2-1-1-9、文件编码统一使用UTF-8。

### 2-1-2 C++规则

2-1-2-1、\[SC] C++文件使用C标准库时，请不要使用旧式的.h后缀的头文件。

正例：
```
// 使用不带.h后缀的C标准库头文件
#include <cstdint>
```
反例：
```
#include <stdint.h>
```

2-1-2-2、 \[ES] C++文件的命名空间内(包括匿名命名空间)各类元素、结构体中的各类元素定义顺序（分布位置），需遵循规则【2-1-1-6】。类中的元素定义与排布还需遵循：
访问权限声明顺序：
a.public
b.protected
c.private
每个访问权限区块只声明1次，同一区块内，各元素声明次序为：
a.内部类型（枚举/结构体/类）；
b.函数
c.变量
其中职能、归属一样变量（函数）应该聚集放在一个区域，职能不同的变量（函数）应该分隔，并适当加上注释；
其中函数的声明排版为：
a.构造函数/析构函数/初始化之类的函数
b.实现的接口函数
c.操作内部数据的函数(get、set)
d.业务函数

正例：
```
class NetDiagnosisHelper : public SystemEventListener, public EtherNetListener {
public:
    // inner typedef

    // constructor、destructor、init

2-1-2-3、\[SC] 头文件中请不要使用 using namespace xxx。

## 2-2 预处理与宏运用

### 2-2-1 条件编译宏

2-2-1-1、\[ES] 使用多分支的条件编译预处理指令，如：#if - \#elif - \#endif，后续关联的预处理指令都必须带上对应的条件控制分支中首个预处理分支关联的宏名作为注释。
说明：预处理指令缺少缩进，如果没有注释辅助体现预处理指令的关联关系，可读性非常差。

正例：
```
#if (QCM6125)

// code...

#elif (BCM2835) // (QCM6125)

// code...

#else // (QCM6125)

#error "Error: please check platform macro!"

#endif // (QCM6125)
```

2-2-1-2、 \[SC] 请不要在预处理指令中使用魔鬼数字起到注释代码段或选用代码段的作用。

反例：
```
#if 0

// code paragraph 1

#else

// code paragraph 2

#endif

```
如果不需要代码段 'code paragraph 1'请直接删除，并去掉预处理指令；如果确实有存在的必要，请使用具体的宏进行控制。


2-2-1-3、\[SC] 预处理指令 '\#else' 分支下不写默认被编入的项目代码，而是增加编译报错信息。
说明：如果 '#else' 分支中 写的是默认被编入项目的代码，当相关的宏值错误、或者新增加了对应的类型却没有增加分支的情况就不能被发现；相反增加编译报错信息，可以及时发现相关的宏值存在错误、或新增宏值没有对应的新分支。

正例：
```
#if (QCM6125)

// code...

#elif (BCM2835) // (QCM6125)

// code...

#else // (QCM6125)

#error "Error: please check platform macro!"  // 当平台宏定义错误时，可以及时发现问题

#endif // (QCM6125)
```

### 2-2-2 宏常量与宏函数

2-2-2-1、\[SC] 尽可能不使用宏常量，一般使用宏常量场景为跨设备间的协议、跨模块通用常量、汇编可能使用到的常量等。其他场景请使用常量const，或常量表达式constexprt。
说明：宏常量本质是文本替换，没有类型，在不同平台可能被解释为不同的类型，编译器不做类型检查，可能产生隐性问题。

2-2-2-2、\[SC] 宏常量定义时，常量值部分必须加上小括号。
说明：不加括号的宏常量值、常量表达式，可能在代码使用中产生隐形问题。

正例：
```
#define EXECUTE_ERROR (-1)
```

反例：
```
#define XXX_PER_DECREASE_NUMBER -100
// 如果在代码用，使用到这个宏常量用于计算，就可能出现问题。
```

2-2-2-3、\[SC] 尽量避免定义宏函数，宏函数一般为简单且重复的代码，如日志打印、数组长度计算、参数不使用声明、入参校验等。
说明：宏函数的弊端与宏常量类似，都可能产生隐形问题。
【建议】

2-2-2-4、\[SC] 宏表达式、宏函数存在多条语句时，必须用do {} while(0) 囊括。

正例：
```
#define POINTER_VERIFY(ptr) do {\
    if (prt == NULL) {\
        LOG_WARN(“null pointer.”);\
        return;\
    }\
} while(0)
```

2-2-2-5、\[SC] 定义宏表达式、宏函数末尾处不需要带有分号，在调用处添加分号。

反例：
```
#define ARRAY_SIZE(arr) ((sizeof(arr)) / (sizeof(arr[0])));
// 定义宏函数ARRAY_SIZE的末尾处不需要带有分号
```

## 2-3 条件控制语句

### 2-3-1 if/if-else/if-else if-else 与 bool表达式

2-3-1-1、\[ES]\[DS] if-else if-else条件分支语句中，分支数不允许超过5个(不包含5个)。
说明：分支数过多时，会让代码变的冗长、可读性差、更容易出错。当遇到超过5个分支业务场景时，可以使用设计模式中的策略模式（Strategy Pattern）转换、解决。复杂的多条件分支场景，通过策略模式、条件对像（谓词、lambda表达式）、条件对象<->策略对象映射表，最终都能转化为表的遍历。

2-3-1-2、\[SC] 条件判断中，请不要出现boolean常量，或boolean常量表达式。
说明：判断条件中为boolean常量，则代码是否被执行，在编译期就已经确定，条件判断没有任何意义。
反例：
```
if (true) {
    // do some thing
}

if (BUFF_SIZE > ARRAY_MAX_SIZE) { // 这里的BUFF_SIZE、ARRAY_MAX_SIZE都是常量
    // do some thing
}
```

2-3-1-3、\[ES] boolean类型变量不需要再与boolean常量进行比较，这样多此一举。

反例：
if (isValid == true) {
    // do some thing
}

2-3-1-4、\[ES] 数值类变量，请不要直接用于逻辑判断。
说明：C语言中，虽然语法定义0为假，非0为真，但数值直接用于逻辑判断（当成boolean值使用），代码可读性会降低。

正例：
```
if (dataPtr == nullptr) {
    return;
}

if (count != 0) {
    // do some thing
}
```

反例：
```
if (count) { // count为int类型变量
    // do some thing
}
```

2-3-1-5、\[ES] 带有比较运算符（'\=='、'>'、'<'等）的bool表达式中，待比较的变量应该放在左侧，被比较的变量或常量应该放在右侧，一般来说被比较的变量值相对固定或者是常量。

正例：
```
// currentStatus是待比较变量，应该放在左侧
if (currrentStatus == NET_DIAG_STATUS_IDLE) {
    // do some thing
}
```



2-3-1-6、\[ES] 过于复杂的判断条件，不要堆砌式的放在if的小括号中，可读性很差。可以声明为boolean变量，或封装为函数，并适当添加注释。
【建议】

### 2-3-2 switch-case

2-3-2-1、\[ES]\[DS] switch-case中的case分支不允许超过5个，超过5个的，转化为静态表+表遍历。
说明：case分支过多时，与if-else if-else分支过多的弊端一致。

2-3-2-2、\[ES] switch-case中，每一个case中的代码都必须使用大括号’{}’囊括，请不要在case大括号外出现代码。

2-3-2-3、\[ES] switch-case中，每一个case大括号中最后一条语句必须是break,不允许出现执行完一个case后，继续往后执行剩余case的代码。
说明：虽然在语法上switch-case允许执行完一个case不break可以往下执行剩余case，但业界默认将switch-case视作一次执行一个分支的条件控制语法关键字。如果允许往下执行剩余case会使得代码可读性降低，不利于后续维护扩展（如还需考虑case顺序等）。实在需要往下执行剩余case逻辑的，可以通过外层套一个while循环+case中修改控制while的变量来实现。

正例：
```
bool isContinue = true;
while (isContinue) {
    isContinue = false;
    switch (currentStatus) {
        case NET_DIAG_STATUS_IDLE : {
            // do some thing
            break;
        }
        
        case NET_DIAG_STATUS_WORK_END : {
            (GetFaultCode() != NET_DIAG_CODE_NORMAL) {
                // 要继续执行一次switch(或者说想继续走后面的case)
                currentStatus = NET_DIAG_STATUS_HEALING;
                isContinue = false;
            }
            break;
        }

        case NET_DIAG_STATUS_HEALING : {
            // do some thing
            break;
        }
        
        default : {
            LOG_ERROR("invalid net diag status.");
            break;
        }
    }
}

```


2-3-2-4、\[ES] switch-case中，最后必须有default分支作为结尾，并添加日志。
说明：方便统一处理未考虑的case值、无效case值。

## 2-4 循环

### 2-4-1 通用规则

2-4-1-1、\[ES] 循环体中应该遵循最少内容原则，不必要在循环中做的工作应该提到循环体外。

2-4-1-2、\[SC] 控制循环的逻辑条件中，应当遵守【2-3-1】中的规则。如：
控制循环的逻辑条件中，请不要使用boolean常量、boolean常量表达式。(宏函数中用于囊括多行代码的do {} while(0) 除外)。
说明：如果循环条件中使用boolean值为true的常量，循环变为死循环，后期扩展、维护非常不利（线程退出控制等）；如果循环条件中使用boolean值为false的常量，则这个循环体执行0次或1次，不需要使用循环控制。

反例：
```
while (1) {
    // do some thing
}
```
### 2-4-2 C++规则

2-4-2-1、\[DS] 当使用C++增强for循环遍历数组、容器中的元素时，应该使用引用类型，如果不涉及修改，还应该加上const关键字修饰。
说明：使用引用类型，可以减少不必要的对象拷贝，尤其对于大对象，多余拷贝增加性能损耗。

正例：
```
for (const auto& item : list) {
    // do some thing
}
```

## 2-5 函数

### 2-5-1 通用规则

2-5-1-1、\[ES] 函数的代码行数不允许超过60行（包括函数头、末行右大括号、空行、注释，但不包括函数首部注释），超过60行的函数需要进行拆分。
说明：函数超过60行时，大部分屏幕已经无法在不纵向滚动的条件下浏览整个函数的代码，不利于开发者理解函数上下文。函数行数越多，可读性越差。

2-5-1-2、\[ES]\[DS] 函数内，大括号嵌套层数不允许超过4层，其中循环嵌套层数不允许超过3层。
说明：对于if条件分支产生的嵌套，检查是否能使用“卫语句”减少嵌套层数；对于循环层数超过3层的代码，时间复杂度的次数高，可用性非常差，要思考用时间复杂度更好的算法。

改为圈复杂度

2-5-1-3、\[ES]\[SC] 对于条件判断中类似“不满足则不做任何事”的逻辑，应该使用“卫语句”提前返回。
说明：使用“卫语句”的好处，一是防御错误条件下执行了不该执行的代码，二是减少大括号嵌套层数，可读性更好。

正例：
```
void FilterData(Data* data) {
    if (data == nullptr) {
        return;
    }

    // do some thing
}
```

反例：
```
void FilterData(Data* data) {
    if (data != nullptr) {
        // do some thing
    }
}
```

2-5-1-4、\[ES] 在声明函数时，对于非指针类型参数、非引用类参数、或不允许修改的指针类型参数、不允许修改的引用类型参数，请加const修饰，移动语义除外。
说明：非指针类型参数、非引用类参数，是实参的拷贝，一般只用于读取（一般不做修改操作，如果需要修改，可以再定义一个局部变量，将入参赋值（拷贝）给这个局部变量，对这个局部变量进行修改），所以用const修饰；而不允许修改的指针、引用类型参数用const修饰能让编译器进行检查，防止错误的修改。

2-5-1-5、\[ES] 在定义函数时，无参数函数的括号中写上void关键字，函数实现处不需要。
说明：声明函数出，空参数用void关键字，可以非常醒目的表示该函数不需要入参。

2-5-1-6、\[ES] 声明函数时，输入类型参数应该放在输出类型参数前。

正例：
```
uint32_t GetValidData(const Data *src, const uint32_t srcSize,
    Data *des, uint32_t desSize);
// src、srcSize为输入型参数，放在前面；des、desSize为输出型参数，放在后面
```

2-5-1-7、\[SC] 提供给外部使用的函数（C语言非static函数，C++类非中private域下的函数），都必须进行入参校验，如指针非空校验，变量取值范围（如果有范围要求）校验等。

2-5-1-8、\[SC] 对于调用外部的函数，如果返回值非void的，需要进行返回值校验（执行结果值判断，指针非空校验等），确认不进行返回值校验的，加上void关键字标明。

正例：
```
// memset函数绝大概率不会有问题，忽略返回值校验，用void标明
(void)memset(arr, 0, sizeof(arr));
```

【建议】

2-5-1-9、 \[ES] 定义函数时，入参请不要超过5个。
说明：入参过多时，对调用者不友好，应该将参数封装为结构体或数据类。

2-5-1-10、\[ES] 函数中使用到的局部变量，应该在最接近使用的代码前定义，一是缩小局部变量作用范围，防止未初始化就使用问题，二是让局部变量的作用更清晰。

正例：
```
bool ProcessData(uint32_t* data, uint32_t size) {
    if ((data == NULL) || (size == 0)) {
        return false;
    }
    // do some thing

## 2-5 综合

### 2-5-1 禁用的关键字/禁用的编码方式

2-5-1-1、\[SC] 请不要使用assert断言。
说明：断言对错误的处理方式十分不友好，应该改为对应异常处理机制。

2-5-1-2、\[SC] 请不要使用goto。
说明：goto破坏程序执行的顺序结构，使得执行流程变得混乱，代码更容易出错，可读性降低等弊端，使用goto实现的流程可以用为break、continue代替。

2-5-1-3、\[SC] 请不要使用union联合体（共用体）。
说明：联合体中，多个字段共享一出内存，且某时使用哪个字段还需要熟悉业务、上下文条件下进行判断，误用则导致数据被覆写、读错数据等问题，不论是可读性、可维护性、安全性都造成不好的影响。

【业务层不要使用】

2-5-1-4、\[SC] 请不要使用魔鬼数字。部分常用且意义固定的字面量除外，如0、'\0'等。
说明：魔鬼数字是指直接出现在代码中的数字、字符、字符串（日志除外）字面量。魔数的存在，使得代码可读性、可维护性都降低，应该用规范命名的常量、宏替代。

2-5-2-2、\[ES] C语言文件内全局变量必须定义为static，如果有需要提供给外部文件使用，请提供get、set接口，请不要将全局变量随意暴露给外部。

跨文件、Cpp不能使用全局变量

### 2-5-3 线程

2-5-3-1、\[ES] 使用原始的线程创建线程的接口时，应该为线程命名，命名规则为：模块名+线程作用。
说明：线程命名后，方便后续有问题可以快速定位对应线程。

【建议】

2-5-3-2、\[ES] 模块驻守类工作线程（循环执行任务）的创建，请集中在模块初始化中创建，线程间时序可以用多种手段做同步控制。
说明：线程的创建宜早不宜迟，集中创建线程一是方便管理线程、做线程间的同步控制；二是可以非常清晰的了解到这个模块的工作流程、有哪些线程；三是方便维护，释放线程与回收资源时不用去寻找散落到模块代码各处创建的线程。

2-5-3-3、\[DS] 非驻守类工作（非循环执行任务）线程，请不要使用原始的线程接口创建线程，而是应该将任务交给线程池、定时器，其中异步耗时任务交给线程池，与时间有关的任务交给定时器。
说明：频繁的创建与释放线程会增加不必要的性能消耗。

2-5-3-4、\[DS] 保证多线程访问的临界变量线程安全时，优先考虑无锁方式实现，如果用互斥锁实现，请尽可能减小锁对数据的封锁粒度。
说明：无锁方式保证线程安全，可以最大程度不影响线程的并非；同理，封锁粒度越小，对线程并发的影响越小。

【建议】

2-5-3-5、\[SC] 选择使用互斥锁保证线程安全，当需要持有多个互斥锁时完成业务工作时，请保证使用到相关互斥锁的所有地方持有锁、释放锁的顺序一致，避免产生死锁。

【建议】

2-6-1-11、\[ES] 请不要定义运算符重载函数。
说明：运算符重载函数，一个符号很难让开发者理解其功能、作用，容易产生歧义，应该用普通函数代替运算符重载，比如'\=='可以用名为Equals的函数代替。

2-6-1-12、\[ES] 未被final修饰的类，其析构函数必须是public virtual或protected non virtual。其中当派生类对象在释放时需要表现出多态的特征（如需要基类指针指向派生类对象）、释放派生类对象时基类也存在需要释放的资源（需要调用到基类析构函数）时则声明为public virtual，否则声明为protected non virtual。

### 2-6-2 指针相关

2-5-2-1、\[SC] C++代码中，空指针统一使用nullptr表示，而不是使用NULL。
说明：C++中的NULL与C语言中的NULL含义是有区别的，在C++中NULL实际是int类型字面量0，在C语言中NULL实际是void\*(0)，做这个区别的原因是C++不允许隐式的将void\*转为其他类型指针，从而避免缺陷代码。虽然C++绝大部分场景中使用NULL的作用与nullptr一致，但为保持C++标准和代码一致性，统一使用nullptr表示空指针。

2-5-2-2、\[SC] C++代码中非特殊情况，如兼容原有代码、C语言接口等，优先使用智能指针（share_ptr、unique_ptr等），非必要情况下请不要使用裸指针。

### 2-6-5 其他

2-6-5-1、\[SC] C++代码中，设计类型转换时请不要使用C式的类型强转，而是使用C++标准库中提供的类型转换函数static_cast\<T>、const_cast\<T>。几个转换函数的作用、区别：
static_cast：用于基本类型之间转换、派生类对象（指针）转换为基类对象（指针）的上行转化，编译器会做安全检查；
const_cast：用于为变量添加或形式上去除const、volatile属性，不会改变变量的类型，注意形式上去除const属性的变量依然是不能修改的变量，只是在形式上让变量没有了const属性；
dynamic_cast：支持‌安全的下行转换‌（基类指针转派生类指针）和多态类型转换，依赖RTTI在运行时检查类型安全性，转换失败时返回空指针（指针）或抛出异常（引用）；
reinterpret_cast：执行‌低级别的位模式重新解释‌，如将指针转换为不同类型的指针或整数，不进行类型检查，因此‌风险高且不可移植。
其中：dynamic_cast、reinterpret_cast非必要情况下请不要使用，可能使程序产生未定义行为。

3-2-2-1、\[SC] 内存申请/释放（malloc、`calloc` 、realloc/free，new/delete，new\[]/delete\[]）函数必须成对出现，最好在同一个函数中（并且注意是否存在异常、提前返回等可能导致释放资源函数执行不到的情况），或成对的内存申请、内存释放函数中（构造/析构、初始化函数/销毁函数等）；如果内存申请/释放函数未在同一函数中成对出现，必须在【申请内存的代码】处用注释说明对应【释放内存的代码】在哪、在【释放内存的代码】处用注释说明对应【申请内存的代码】在哪。

3-2-2-2、\[SC] 使用不安全的内存字节操作类函数，如memcpy()、memset()、strcpy()、sprintf()等,务必检查【目标地址内存大小的字节数】、【操作参数中指定字节数】，保证【目标地址内存大小的字节数】>=【操作参数中指定字节数】。

### 3-3-1 随机数的使用/异步安全函数

【设计类问题】

3-3-1-1、\[SC] 在设计加密验证相关的随机数产生上，必须使用跨平台通用的专用密码学库，如OpenSSL、libsodium。​普通的随机数产生，C语言、C++推荐使用的API见用例，请不要使用随机数种子方式去产生随机数，因为这样产生的随机数序列是固定或可预测的。

正例：
```
// C语言
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

#define FAILED  (-1)
#define SUCCESS 0

int32_t GetRangeRandomNumber(uint32_t left, uint32_t right, uint32_t* r) {
    int randomData = open("/dev/urandom", O_RDONLY);
    if (randomData < 0) {
        /* /dev/urandom是 Linux 系统中的密码学安全随机数生成器 (CSPRNG)，
         适合生成密钥、令牌等 */
        perror("Failed to open /dev/urandom");
        return FAILED;
    }
    int32_t randomNumber;
    int32_t ret = read(randomData, &randomNumber, sizeof(randomNumber));
    close(randomData);
    if (ret != sizeof(randomNumber)) {
        fprintf(stderr, "Failed to read from /dev/urandom\n");
        return FAILED;
    }
    // 生成 [left, right] 范围的随机数（无偏差）
    *r = (randomNumber % (right - left)) + left;
    LOG_DEBUG("Secure random number: %d\n", *r);
    return SUCCESS;
}

```

#include <iostream>
#include <random>

void GetRandomNumberExample() {
    // 1. 随机数引擎：负责生成原始随机序列
    // std::random_device 用于获取非确定性随机数（如硬件熵）作为种子，是真随机数，无法预测
    std::random_device rd;
    // 使用梅森旋转算法引擎，用 random_device 的输出初始化
    std::mt19937 gen(rd());
    
    // 2. 分布器：控制随机数的范围和分布规律
    // 生成 [1, 100] 均匀分布的整数
    std::uniform_int_distribution<int> intDis(1, 100);
    
    // 生成 [0.0, 1.0) 均匀分布的浮点数
    std::uniform_real_distribution<double> doubleDis(0.0, 1.0);
    
    // 3. 生成随机数：将引擎实例传递给分布器
    std::cout << "Random Integer: " << intDis(gen) << std::endl;
    std::cout << "Random Double: " << doubleDis(gen) << std::endl;
    
    // 其他分布
    // 正态分布 (均值为 5.0，标准差为 2.0)
    std::normal_distribution<> normalDis(5.0, 2.0);

    // 伯努利分布 (返回 true 的概率为 0.3)
    std::bernoulli_distribution bernoulliDis(0.3);
    std::cout << "Bernoulli distribution (true with p=0.3): " <<
        std::boolalpha << bernoulliDis(gen) << std::endl;
}

说明：如果交付给客户的软件中使用了未向客户披露的端口，客户在测试过程抓取报文时发现，轻则做繁琐的澄清解释，重则丢失客户信任，甚至客户要求赔偿，对公司造成损失。反之亦然。

3-3-2-3、\[SC] release版本软件中，不允许留有任何客户未知的“后门”代码，如本地连接进入调试模式、远程连接root登录、未披露的开关类操作等。
