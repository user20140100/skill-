# 完整版逐 Feature Point PRD 契约

本契约迁移自 `prd-writer` 完整版，并针对代码反推场景增加 FP、源码追溯和验证约束。

## 文档级结构

1. **文档说明**：文档目的、产品定位、功能概览、术语表。
2. **功能模块与功能点**：按模块排列连续的 `FP-01`、`FP-02`……。
3. **功能关联与闭环关系**：串联所有 FP；complex PRD 每个 FP 使用独立且参与流转的 Mermaid 节点，所有节点连通，decision 展开带标签分支，并提供源码 token 级规则矩阵审计。
4. **行为覆盖与代码追溯**：Behavior → FP → 源码证据 → 可感知行为 → 章节。
5. **验证依据**：逐 Behavior 写真实测试或自动化验证缺口。
6. **已知缺口与待确认项**：集中记录 TODO、未实现策略和无证据的产品意图。

frontmatter 还必须携带结构化分类契约，以及连续的 `decomposition_candidates`。每个 FP 恰好映射一个 trigger/stage/decision/interaction/external_wait/terminal/lifecycle 锚点；cleanup 只能作为附加候选。standard/complex 的每个 FP 都必须分别映射主路径 Behavior 和限制/异常 Behavior。

## 每个 FP 的固定七章节

### 1. 功能描述

- “是什么”只定义该 FP，不把其他阶段塞进一句话。
- “为什么”分别说明用户痛点和业务价值；证据不足时明确待产品确认。

### 2. 交互逻辑

- 使用有序列表，从用户、调用方或系统事件视角描述。
- 每步包含一个具体动作和系统响应。
- 主路径之外还要写独立分支、取消、失败、恢复或清理。

### 3. 跳转逻辑

- 有页面/流程去向时使用 Markdown 表格，写触发、目标和说明。
- 非 UI 能力明确写“无页面跳转”，但仍说明状态或流程去向。

### 4. 跳转过程逻辑

展开权限校验、数据加载、拦截、订阅、异步等待、定位、恢复等中间行为。不能只重复起点和终点。

### 5. 正向限制

使用“项目 | 限制”表格，写允许角色、入口、范围、格式、数值、状态、生效时机和持续时间。代码存在具体值时保留具体值。

### 6. 反向限制

使用“项目 | 说明”表格，写不支持、不允许、隐藏、置灰、拒绝、幂等、重入和当前系统表现。

### 7. 异常/空态/错误提示

使用“场景 | 提示内容 | 展示方式 | 源码证据”表格。证据必须支持触发条件、结果和展示方式；展示方式必须具体。

五类异常在整篇文档中必须全部审计：空态、操作失败、网络异常、权限不足、边界超限。不得凭惯例补写超时、权限、Toast 或弹窗；不适用时同样绑定源码证据。

## 详细度判断

以下任一项具有独立产品规则时，应成为 FP 或进入已有 FP 的完整矩阵，而不是被概括：

- 不同入口或角色的准入规则；
- 多阶段状态转换；
- 枚举到行为/文案的映射；
- 优先级链或拦截器链；
- 确认弹窗、倒计时和按钮分支；
- 外部设备/系统协作和异步确认；
- 最终策略选择；
- 取消、失败、恢复、超时、重入和资源清理。

例如完整关机流程通常需要分别审计电源键入口、UDI 策略通知、关机拦截器、确认弹窗与倒计时、PC 联动、最终关机策略和 PC 状态反向触发；不能只写成一套全局七章节。
