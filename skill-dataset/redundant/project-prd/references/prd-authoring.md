# 逐功能 PRD 撰写规范

## 核心原则

- 每份 PRD 描述一个细分功能，文件位于 `.project-prd/<功能分类>/<细分功能>.md`。
- 采用 `prd-writer` 的“模块 → 功能点”结构。先拆 Feature Point，再为每个 FP 独立、完整地重复 7 个核心章节；不得只在整篇 PRD 级别写一套章节。
- 使用产品与用户视角描述可感知行为，不复制代码、私有函数或偶然实现细节。
- 仅记录有证据的已有基线。对产品原因或理想体验没有证据时，明确写“待产品确认”。

## 元数据与文档头

每份 PRD 必须包含：

- `prd_id`：全项目唯一，格式为 `PRD-...`。
- `product`、`baseline_version`、`date`、`author`。
- `category`、`feature`、`status`。
- `prd_schema: feature-points-v3`。
- `category_domain`、`category_goal`、`category_contract`：同一一级目录内必须完全一致；contract 至少包含两个结构化共同维度。
- `category_fit`：当前 PRD 对共同维度的源码证据，至少两项，且证据必须同时存在于 `source_entries`。多成员目录要求所有成员共同有证据的维度不少于两个。
- `complexity`、`complexity_reasons`、`decomposition_candidates`、`decomposition_basis`、`source_entries`。候选使用 `DC-##|kind|名称|证据|FP-##`，每个 FP 恰好有一个锚点候选。
- 标题 `# {产品} {功能} 产品需求文档`。
- 文档头 `> 版本：... | 日期：YYYY-MM-DD | 作者：...`，日期与 frontmatter 一致。

## 文档级结构

1. “文档说明”包含文档目的、产品定位、现有功能概览；complex PRD 还必须包含真实术语表。
2. “功能模块与功能点”先按模块列出 `FP-01`、`FP-02`……，每个 FP 完整套用下述七章节。
3. “功能关联与闭环关系”必须纳入每个 FP；complex PRD 的 Mermaid `flowchart` 要为每个 FP 建独立节点、保持连通并展开 decision 分支；规则矩阵的代码项使用证据范围中的真实 token/表达式。
4. “行为覆盖与代码追溯”将每个 Behavior 精确映射到 FP。
5. “验证依据”逐 Behavior 映射真实测试或明确缺少自动化验证。
6. “已知缺口与待确认项”集中记录源码中的 TODO、未实现策略和无法从基线证明的产品意图。TODO 不得混入已实现需求正文。

## 每个 Feature Point 的七章节

### 功能描述

- **是什么**：只用一句话，采用“用户在…通过…实现…”。无 UI 功能可将用户替换为调用方或系统事件。
- **为什么**：分开写“用户痛点”和“业务价值”。无证据时不臆造，保留待确认项。

### 交互逻辑

- 使用有序列表，每步只写一个角色动作和对应系统响应。
- 格式统一为“用户/调用方动作 → 系统响应”。
- 用 UI 控件的准确文案；非 UI 功能写出 API、硬件键、系统事件或回调名称。
- 主路径、独立分支、取消/失败、恢复/清理均需进入交互流。

### 跳转逻辑与跳转过程

- 跳转表使用“触发操作 | 目标页面 | 说明”。
- 过程单独描述权限校验、数据加载、拦截、定位和恢复。
- 无页面跳转时明确写“无页面跳转”；不得为 service/SDK 虚构页面。

### 正向限制

用“项目 | 限制”表格记录系统允许的范围：数量上限、格式、角色、入口、状态、生效时机和持续时间。数值必须具体。

### 反向限制

用“项目 | 说明”表格记录不支持或不允许的场景，并说明隐藏、置灰、拒绝、保持原状或返回错误等实际表现。

### 异常、空态和错误提示

表格使用“场景 | 提示内容 | 展示方式 | 源码证据”，必须包含空态、操作失败、网络异常、权限不足、边界超限。每行证据必须指向真正实现分支的 Symbol 或精确行范围；同文件无关函数和注释无效。不适用时也保留类别和已审计闭包证据。

五类异常按整篇 PRD 汇总覆盖，但每个 FP 的异常表都必须非空并只写与该 FP 相关的真实异常。不要机械复制五行相同内容。

## 关联、追溯与验证

- 在“功能关联与闭环关系”写出每个 FP 的上游入口、中间状态、关联功能和最终结果，并引用其他 PRD。
- 在“行为覆盖与代码追溯”为每个 Behavior 写 FP ID、源码证据、用户可感知行为和主要 PRD 章节；每个 FP 至少有一个 Behavior，standard/complex 的每个 FP 必须同时覆盖主路径与限制/异常。
- 在“验证依据”映射现有单元/集成测试。没有测试时写“缺少自动化验证”，不虚构测试路径。
- `source_entries` 和 Behavior 源码证据统一写成 `项目内相对路径:Symbol` 或 `项目内相对路径:行号`。Symbol 仅写单一定义名，不写 `Class.method` 等限定名；支持的语言会校验真实定义，不支持可靠解析的文件改用有效行号。一个 Behavior 有多项证据时，每项用反引号包裹并以 `<br>` 分隔。
- 每个 Behavior 必须单独写一条 `B### → 验证证据`。验证证据中的项目内相对路径必须真实存在并符合测试目录或测试文件命名约定；没有自动化测试时只能明确写 `缺少自动化验证`，不得使用生产源码、推测路径或合并 Behavior ID 范围。
- `source_entries` 必须等于 Behavior 源码证据去重后的完整集合。它不是只列几个代表文件的摘要。

## 防止“看起来完整、实际压缩”

- 章节齐全不等于内容完整。先完成行为清单、`decomposition_candidates` 和 `decomposition_basis`，再写 FP；每个 FP 只能承接一个独立锚点候选。
- 独立触发、状态阶段、策略矩阵、拦截链、确认交互、外部协作、取消/恢复/清理如果可以独立验证，就不得压入另一个 FP 的一句话。
- 每个 FP 的七章节必须按固定顺序恰好出现一次，不允许“同上”、共享一张限制表或把所有异常集中成空泛五行。
- 复杂度数量只是最低门槛。达到 `complex >= 2 FP / 5 交互 / 3 正向 / 3 反向 / 6 Behavior` 后，仍要对照行为清单逐项确认无遗漏。

## 证据等级

1. 已有自动化测试和公开契约。
2. 用户可达入口及其实际执行路径。
3. 数据模型、状态机、文案和错误处理。
4. 项目文档与注释。
5. 仅凭命名或不完整实现的推断。

第 5 类不能写成确定产品需求；继续寻找证据，仍无法确定时标为待确认或询问用户。
