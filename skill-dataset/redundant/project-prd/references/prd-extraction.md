# 从代码提炼逐功能 PRD

## 目标

先完整识别已实现行为，再把它们组织为产品视角的交互、限制、异常和闭环。不得通过函数名想象产品意图，也不得只记录一条主路径。

## 第一步：建立行为清单

沿入口、调用链、事件订阅和状态依赖阅读完整行为闭包，在 `.project-prd/.analysis/` 建立：

| Behavior ID | 角色/触发 | 前置状态 | 用户或调用方动作 | 系统响应 | 限制/异常 | 后续或清理 | 源码证据 |
|---|---|---|---|---|---|---|---|

必须检查：

1. **触发入口**：用户操作、系统事件、定时器、回调、通知、恢复流程。
2. **角色与输入**：用户角色、设备类型、来源、枚举值、模式和配置组合。
3. **状态与转换**：初态、中间态、终态、幂等、重入和并发。
4. **决策与优先级**：guard、if/switch、白名单、拦截器链、策略、回退顺序。
5. **可感知结果**：页面、弹层、提示、返回值、事件消费、持久化、硬件或外部系统副作用。
6. **失败与恢复**：空态、异常、超时、无效输入、依赖不可用、取消、重试、回滚和清理。
7. **闭环边界**：功能的上游入口、下游页面、跨模块回调、外部系统确认和终止状态。

入口函数只是起点。多阶段流程、三个及以上分支/枚举/拦截器、异步确认、外部副作用和成对资源清理都必须进入实现级代码。

## 第二步：评估复杂度

- `simple`：单一触发、少量直接判断，无复杂状态或异步协作。
- `standard`：存在一个明显状态转换、模式分支、外部协作或失败恢复维度。
- `complex`：满足以下任意两项，或单项已是核心业务复杂度：
  - 三个及以上阶段或状态转换。
  - 三个及以上角色、模式、来源或枚举分支。
  - 三层及以上优先级、拦截或决策链。
  - 异步通知、倒计时、超时、回调或跨进程确认。
  - 两个及以上外部系统/硬件副作用。
  - 存在取消、回滚、恢复、清理或重入防护。

所有等级都必须写 `complexity_reasons`；`complex` 至少两条独立证据。

## 第三步：先拆 Feature Point，再写 PRD

禁止把整条复杂流程直接塞进一套全局七章节。先把行为清单无损拆成 `FP-01`、`FP-02`……：

- 独立触发入口或角色具有不同准入规则时，形成独立 FP。
- 能独立描述输入、处理和输出的流程阶段，形成独立 FP。
- 枚举/文案矩阵、优先级链、拦截器链或最终策略具有独立产品规则时，形成独立 FP。
- 异步外部协作、确认弹窗、倒计时、取消恢复、资源清理或生命周期监听形成独立闭环时，形成独立 FP。
- 仅是同一动作的私有实现步骤，不单独成 FP。

源码中具有独立状态转换、输入输出且可单独验证的编号阶段必须形成候选；生命周期候选负责订阅/退订，监听到达后若具有不同准入或结果契约，再形成 trigger/decision 候选。同一 cleanup 服务多个 FP 时，为每个受影响 FP 分别写命名不同的 cleanup 候选，允许证据重叠。

先把所有候选写成 `DC-##|kind|名称|源码证据|FP-##`。`kind` 只允许 trigger、stage、decision、interaction、external_wait、terminal、lifecycle、cleanup。每个 FP 恰好承接一个非 cleanup 锚点；complex 流程的 trigger、external_wait 和 lifecycle 候选必须同时给出真实上游入口与核心/下游证据，避免只读到编排函数就漏掉硬件键、事件监听或回调入口。

将每个 FP 的拆解理由按顺序写成 `FP-01: ...` 并逐条放入 `decomposition_basis`，数量必须与实际 FP 完全一致。`simple/standard` 至少一个 FP，`complex` 至少两个；这只是最低防压缩线，不是数量目标。关机这类包含入口、UDI 策略、拦截器、确认弹窗、PC 联动、最终策略和 PC 反向触发的流程，应分别拆出相应 FP，不能因为满足最低数量就停止。

## 第四步：逐 FP 映射到 PRD 章节

将行为清单分配到：

- **功能描述**：该功能是什么；为什么只能使用可验证的项目文档、文案或用户流证据。
- **交互逻辑**：每个独立角色动作和系统响应；系统事件或 API 调用也作为一种交互入口。
- **跳转/过程**：页面、弹层、组件之间的去向，以及权限校验、加载、拦截、定位等中间行为。
- **正向限制**：允许的角色、入口、范围、格式、数值、状态和生效时机。
- **反向限制**：不支持、不允许、隐藏、置灰、拒绝、幂等和重入防护。
- **异常提示**：空态、操作失败、网络异常、权限不足、边界超限及其文案/系统表现和展示方式。
- **功能闭环**：入口 → 中间状态 → 协作功能 → 最终结果，以及取消、失败和恢复路径。

每个 FP 都必须按固定顺序完整重复上述 7 章节。一个行为可同时影响多个章节，但“行为覆盖与代码追溯”表需同时写明 FP ID 和最主要章节。

对 complex 流程，依据这些候选绘制 Mermaid `flowchart`：每个 FP 使用且只使用一个独立节点、每条边单独一行、全部 FP 节点参与同一连通闭环；decision 节点至少有两条带条件标签的出边。允许生命周期、外部事件使用多个入口节点，但不能把多个 FP 塞进同一节点。

## 第五步：五类异常完整性

`prd-writer` 要求覆盖五类异常。对代码反推 PRD 执行：

1. 有实现：写出真实触发条件、文案/结果与具体展示方式。
2. 无实现但概念适用：写明当前未处理的实际表现，不虚构理想行为。
3. 概念不适用：保留该行，写“不适用”和源码证据，例如“无网络依赖”。

禁止为了填满表格而虚构 Toast、弹窗、网络失败或权限流程。

每个异常行都要引用同一 FP 的源码证据。声明超时、权限不足、Toast 或弹窗前，必须在引用代码中找到对应计时、权限、Toast 或 dialog 信号。

## 第六步：规则矩阵覆盖审计

逐项枚举代码里的来源/模式映射、状态转换、优先级或拦截顺序、文案、策略和权限矩阵，写入 MX-## 表。`代码项` 使用证据 Symbol/行号范围中真实存在的 token 或表达式，映射可写 `条件 → 结果`；`PRD 覆盖项` 必须精确相等，状态、优先级和策略还必须保持顺序。校验会提取 enum、case 和命名规则集合以发现漏项；MX-NONE 也会扫描完整 `source_entries` 闭包。

## 第七步：行为覆盖审计

在 PRD 中写入：

| Behavior ID | 功能点 | 源码证据 | 用户可感知行为 | PRD 章节 |
|---|---|---|---|---|

完成前检查：

- 每个 Behavior ID 都精确归属一个已定义 FP，并有源码证据和 PRD 章节；每个 FP 至少一个 Behavior，standard/complex 的每个 FP 同时需要主路径 Behavior 与限制/异常 Behavior。
- `source_entries` 与 Behavior 源码证据去重后的集合必须完全一致，既不能漏登记也不能登记后不映射。
- 拆解候选、异常行和规则矩阵的证据必须由同一 FP 的 Behavior 覆盖。
- 每项源码证据使用 `相对路径:单一Symbol` 或 `相对路径:行号`，并验证文件、Symbol 定义或行号真实存在；无法可靠解析 Symbol 的文件必须使用行号，多项证据用反引号和 `<br>` 分隔。
- 触发、状态、分支、限制、异常、外部协作和清理没有未映射项。
- 每个 FP 至少 1 个交互步骤，正向/反向/异常表各至少 1 行，并完整包含 `prd-writer` 七章节。
- `simple` 整篇至少 1 个 FP、1 个交互步骤、1 条正向限制、1 条反向限制和 1 个 Behavior。
- `standard` 整篇至少 1 个 FP、3 个交互步骤、2 条正向限制、2 条反向限制和 3 个 Behavior。
- `complex` 整篇至少 2 个 FP、5 个交互步骤、3 条正向限制、3 条反向限制和 6 个 Behavior。

数量是防过度压缩门禁，不是写作目标。达到数量但行为清单仍有缺口时，PRD 仍不合格。
