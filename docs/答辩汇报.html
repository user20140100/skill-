Background

业务背景：为什么需要全链路审计

03

团队正在大规模引入第三方及内部开发者编写的 Agent 技能（用于 Claude Code、Codex、OpenCode 等）。技能文件夹不仅包含 Markdown 指令，还常附带执行脚本，安全团队提出三类合规担忧：

① 技能投毒与隐蔽风险

可能隐藏提示词注入、越权工具调用、敏感凭证外泄、后门命令。

② 语义冲突与冗余

不同技能的指引高度重叠，导致 Agent 触发逻辑混乱。

③ 行为增益不明确

缺乏沙盒隔离下的对照实验，无法证明技能确实提升了任务完成率，而非引入副作用。

对应交付 调研开源方案 → 本地 Mac 搭建原型 → 完成三层评估实战、冗余技能推荐、企业自定义安全规则、一键批处理审计与自动修复。
Design Philosophy

核心设计思路：五条原则

04

整条流水线围绕五条设计原则展开，后续所有环节都是它们的落地：

① 纵深防御

确定性静态扫描（权威、离线、零成本）打底 → 大模型语义审计补盲 → 沙盒实测验证行为，三层各司其职、互不替代。

② 宁多勿漏（fail-closed）

结论不确定时一律按「有风险」处理：宁可多报、不可漏报；大模型只能增量补充，不能删除或降级静态结论。

③ 检测与放行分离

规则只负责「发现风险」，白名单/抑制层负责「降误报」，二者不耦合，避免放行逻辑只对某一条规则生效。

④ 结论独立

安全、去重、效果三类结论性质不同，各自独立记录，不合并为单一分数。

⑤ 非侵入式扩展

自定义规则经外部参数挂载，不改动上游开源源码，便于跟随上游升级。

一句话「确定性打底 + 语义补盲 + 沙盒验证」，把不确定的推理外置为确定、可审计、可复现的工具。

静态 vs 大模型的分工

  • 静态规则（权威）：正则/代码结构/签名等确定性规则，可离线、零成本，精确定位到文件与行号
  • 大模型审计（补盲）：识别「换说法就绕过关键词」的语义风险，只能增量补充
  • 宁多勿漏：大模型判为误报也只打标签不删除；确定性规则大模型无权降级
  • 安全扫描不执行代码：纯静态分析，沙盒只用于第三层
分工一句话：静态兜底已知模式，大模型补语义盲区，沙盒做行为验证。

两类任务，回答两个不同问题

  • 特化任务（带 vs 不带）：技能「有没有用、在哪有用」——任务绑定被测技能
  • 公共任务（带 A vs 带 B）：两个技能「用哪个更划算」——任务不预设技能、纯结果断言

公平性保障

  • 同一组任务、同一评判标准、同一智能体与模型
  • 公共任务只取双方能力交集，不偏袒任一技能
  • 同一份任务喂给两个技能，差异只能来自技能自身成本
五维分解（关键）增益不只看「结果」，还拆成 正确率、有效性、安全、可发现性、效率——从而把「真实答案增量」从「工作流结构性增量」中剥离出来，避免得出「都很有用」的误导结论。

三个测试技能怎么设计

10

① 正向技能 · 专业计算套件

特化取向

在基础计算器上扩展统计 + 财务能力；多脚本模块化；针对大模型「心算易错」的精确数值任务（标准差、贷款月供、复利终值等）。

② 冗余技能 · 基础计算器

泛化取向

仅算术表达式 + 单位换算；单脚本精简指令；覆盖最通用、最基础的计算需求。

③ 安全靶场技能

含风险样本

刻意植入明文凭证正/负样本（改密码命令、带凭证请求、数据库连接串…）与白名单外发样本，用于验证自定义规则。

构建逻辑三者一一对应三层能力的验证：正向验证第三层增益、冗余验证第二层去重与推荐、靶场验证第一层拦截与自定义规则。正向与冗余技能在「基础算术 + 单位换算」上高度重叠，构成一对可复现的冗余冲突对。
Rule Selection

自定义规则：为什么选「白名单 + 敏感信息检测」

11

课题要求「≥2 条企业自定义规则」，举例是「非白名单域名外发」与「读取敏感路径」。但落地前先做实测基线，发现举例方向已被内置规则覆盖，真正的空白在别处：

候选方向实测结论最终定位
读取敏感文件（密钥/配置）已被内置「凭证文件访问」规则覆盖「敏感信息检测」改落到命令行明文凭证盲区
外发检测（上传/请求）内置「数据外发」规则已承担，但无法区分「合法内网上传」与「恶意外泄」规则一：域名白名单放行（降误报，不新增告警）
命令行明文凭证真实空白：改密码命令、带凭证请求、数据库连接串等 全部 0 检出规则二：明文凭证检测（补盲）

规则一 · 域名白名单放行（降误报）

发往企业可信域名的外发不再报警，不新增任何告警——「检测归检测、放行归放行」。

规则二 · 明文凭证检测（补盲）

检测明文写在命令/连接串里的密码，豁免占位符（<密码> / 环境变量 / 无值交互输入）。

选型逻辑不是「照抄课题举例」，而是先实测内置规则的覆盖边界：敏感文件读取已被覆盖、外发已有规则，唯独「凭证出现在命令行/连接串」这一泄露面是确定性盲区，且大模型只给间接信号、无法精确定位——故将「敏感信息检测」落为规则二补盲，「白名单」落为规则一降误报。

Recommendation

推荐功能设计：安全 + 增益双维度

13

当第二层检测到冗余冲突时，系统从安全与增益两个独立维度评估候选，输出双结论，最终「哪个更优」交给用户决策。

安全维度（能不能用）

完整安全审查：静态安全扫描 + 第一层安全校验，二者并列。

  • 安全：无高危告警
  • 不安全：存在高危告警
  • 三种情形：双方安全 / 一方不安全 / 双方不安全（给风险更低方）

增益维度（值不值得用）

同一公共任务集上，综合 5 个维度：

  • 结果 · 流程 · 输入/输出开销 · 执行耗时 · 执行轮数
  • 结果优先：结果差异大 → 明确更优；结果相当 → 比效率
  • 结果相当时某方领先 ≥3 项 → 效率更优，否则「两者均可」

核心原则：决策权交用户

报告输出安全结论与增益结论两个结论，不合成单一「最终推荐」；两条结论可能不一致（如「安全推荐 A + 增益推荐 B」），属正常现象，由用户结合场景自行权衡。

为什么分两个维度安全回答「能不能用」，增益回答「值不值得用」——二者正交、互不污染。这也是最终「更推荐冗余技能」结论的推导框架。

在泛用功能上，正向技能结果虽正确，但开销与耗时均高于冗余技能，增益不占优。

关键观察（五维分解的价值） 基础算术大模型本来就能算对，技能在泛用任务上没有「真实答案增量」，只有「工作流规范」和「成本差异」；而特化任务上正向技能带来了真实的正确率增量。若只看单一增益数字会误判「两个技能都有用」，拆开看才能分清「特化收益」与「泛化成本」。
Conclusion

分析结论：为什么更推荐冗余技能

16
核心结论 正向技能（专业计算套件）对财务审计等特化计算有明显增益，但在泛用功能上的增益相较冗余技能（基础计算器）并不占优；且两者均通过安全审查。因此，在面向通用场景时更推荐冗余技能（基础计算器）。

① 特化 vs 泛化

正向技能价值在「能力边界扩展」，冗余技能价值在「通用任务成本控制」，两者设计取向互补而非互斥。

② 安全维度打平

双方均通过完整安全审查，安全无差异，无法从安全角度二选一。

③ 泛用场景成本优先

泛用任务上结果等效，但冗余技能更省开销、耗时更短 → 增益维度效率更优。

推荐结论（双结论、交用户）

  • 安全结论：双方安全（打平）
  • 增益结论：泛用任务效率更优 → 冗余技能
  • 系统不合成单一 verdict，由用户按场景选

评测体系合理性

三层评估同时捕获「增益」（带 vs 不带）与「效率」（A vs B）两个正交维度，得以区分「特化收益」与「泛化成本」，得到符合设计意图的结论。

边界说明：本结论面向「通用场景」——若任务属于财务/统计等特化计算，正向技能仍是唯一选择（增益 +31.85pp）。「更推荐冗余技能」成立的前提是泛用功能 + 双方安全等价。
