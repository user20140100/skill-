# SDD与AI开发规格规范

> 仅在用户明确要求开发、SDD、测试、直接编码或 AI Agent 规格时读取。SDD 的目的不是增加章节，而是把已确认的 `FR-xxx` 转换为可定位、无阻断歧义的开发切片。

## 1. 基本原则

1. 规格先于代码；需求变化先修改 `FR-xxx` 对应规格，再同步任务、测试和代码。
2. `spec.md` 写可观察的 What，不写框架、类名、数据库设计和目录等 How。
3. 一条功能说明主体、触发、输入、处理、输出和失败行为；不使用“尽快、智能、友好、支持大量”等模糊词。
4. 未知项用 `Q-xxx` 标记，并判断是否阻断开发。
5. 图表帮助理解，但不能替代关键字段、规则和行为说明。
6. SDD-ready 不等于必须生成测试用例、追踪矩阵和多份文档；按交付需要裁剪。

## 2. 输出路由

| 用户意图 | 输出 |
|---|---|
| 只整理需求 | 保持一份业务需求文档，不拆 SDD 包 |
| 交给开发或 AI 编码 | 为选定 `FR` 生成精简 `spec.md` |
| 要求测试或正式验收 | 增加 `testcases.md`，按需使用 `AC/TC` |
| 要求全链路追踪 | 增加 `traceability.md` |
| AI Agent 功能 | 增加 `agent-spec.md`；需要发布评测时增加 `evals.md` |

推荐目录：

```text
specs/<###-feature-slug>/
├── spec.md
├── testcases.md       # 按需
├── traceability.md    # 按需
├── agent-spec.md      # AI Agent 场景按需
└── evals.md           # AI 发布评测按需
```

`requirement.md` 可以继续使用原业务需求文档，不必复制一份。

## 3. 功能编码与追踪

`FR-xxx` 是业务需求、SDD 和工程工作的主键：

```text
PAGE-001 / JOB-001
→ FR-001
→ specs/001-feature-name/spec.md
→ 开发任务 [FR-001]
→ 提交或 PR [FR-001]
→ 按需 AC-xxx / TC-xxx
```

规则：

- 一个开发切片可以包含一个或多个紧密相关的 `FR`，但必须说明主 `FR` 和依赖 `FR`。
- `PAGE-xxx` 只定位交互载体，不代替功能编号。
- 简单业务规则不编码；只有需要跨功能、代码、配置、测试或审计独立追踪时才使用 `BR-xxx`。
- `AC-xxx` 和 `TC-xxx` 按正式验收、风险和测试交付需要生成。
- 代码不要求到处写需求编号。开发任务、提交、PR 和测试报告应带 `FR-xxx`；非直观业务规则的代码注释可引用 `BR-xxx`。
- 编号废弃后保留并标 `Deprecated`，不得复用。

## 5. 字段规则与影响

### 5.1 字段

- 页面字段总体参考已确认的需求页面和原系统截图。
- 规格只补充新增、修改、删除、受影响不变和关键依赖字段。
- 页面未展示但后台需要保存、计算、审计、恢复或传递的信息，继续写在功能下。
- 需求规格不负责设计数据库表；工程侧结合源码在 `plan.md` 中设计数据结构。
- 用户提供现有表结构并明确要求兼容时，可以把表名、列名和类型作为批准约束保留。

### 5.2 业务规则

- 同一业务对象的规则集中说明，不拆成大量独立编码。
- 复杂计算写清单位、精度、舍入、空值、版本和生效范围。
- 优先级规则写清冲突裁决和无命中行为。
- 跨功能复用或需要独立版本、配置、审计和测试时才创建 `BR-xxx`。

### 5.3 接口与NFR

接口、权限和 NFR 只有在该开发切片确有变化或属于必要约束时才写。接口按需说明提供方、消费方、触发、关键输入输出、幂等、失败处理和兼容；NFR 必须可测，未知阈值写 `Q-xxx`。

## 6. 验证和测试

### 6.1 何时只写验证要点

普通低风险功能使用简短验证要点即可，例如：

- 主路径结果正确；
- 缺少必要数据时行为明确；
- 无权限用户不能执行；
- 明确不变功能通过回归关注。

验证要点不强制编号。

### 6.2 何时使用AC和TC

存在复杂规则、状态、异步、权限、历史兼容、高风险动作，或用户要求正式验收时，使用 `AC-xxx`。用户要求测试、直接编码、正式测试交付或高风险回归时，生成 `TC-xxx`。

`testcases.md` 按需包含：关联 `FR/AC`、前置数据、步骤、预期结果和清理恢复。测试层级和自动化建议按项目需要选择，不为每个简单功能强制生成。

### 6.3 追踪矩阵

只有正式 SDD 交付、跨多个 `FR` 或用户要求全链路追踪时生成：

| 功能 | 规则（按需） | 验收（按需） | 测试（按需） | 状态 |
|---|---|---|---|---|
| FR-001 | BR-001 | AC-001 | TC-001 | 已覆盖 |

## 7. 开发就绪检查

开发前只检查可能阻断实现的内容：

- [ ] 开发切片和关联 `FR-xxx` 明确。
- [ ] 原功能、本次功能、不变边界和影响清楚。
- [ ] 触发、输入、处理、输出和失败行为无阻断歧义。
- [ ] 页面字段和后台保存信息满足业务开发需要。
- [ ] 关键对象规则、状态、异步和接口结论明确或已标阻断 `Q-xxx`。
- [ ] 高风险功能具备必要验证或验收标准。
- [ ] 待确认项已区分阻断和非阻断。
- [ ] 技术实现细节留给结合代码仓库生成的 `plan.md`。

低风险功能不因为缺少 `AC`、`TC` 或追踪矩阵而自动判定未就绪。

## 8. AI-Agent扩展

只有普通规则或固定工作流不足时才使用 Agent。`agent-spec.md` 按需说明：目标和非目标、自主等级、触发与输入、上下文、输出结构、工具和权限、知识来源、人审、禁止动作、失败降级、审计和终止条件。

高风险动作必须提供人工确认、影响预览、最小权限、幂等、审计和恢复。非确定性能力需要发布评测时再生成 `EVAL-xxx` 和 `evals.md`，覆盖标准、边界、权限、知识冲突、工具失败和人工接管场景。

## 9. 工程侧移交

移交内容保持简短：

1. 规格目录、主 `FR`、依赖 `FR` 和当前状态；
2. 阻断和非阻断 `Q-xxx`；
3. 必须保留的业务规则、字段、接口或兼容约束；
4. 按需的验证要点、`AC`、测试和追踪关系。

工程侧结合项目宪法和代码仓库生成 `plan.md`、`tasks.md` 和代码。实现中发现需求歧义时回到对应 `FR` 修订，不得只在代码中固化新的业务规则。
