# 变更型需求文档结构

> 适用于已有系统的页面、字段、逻辑、权限、状态、审批、接口、通知或报表调整。先读取 [`doc-structure-common.md`](doc-structure-common.md)。

## 1. 默认目录

```markdown
# <需求名称>

## 1. 痛点与目标

## 2. 系统功能
### 2.1 功能范围

| 功能编码 | 功能说明 | 优先级 |
|---|---|---|
| FR-001 | <一句话说明本次功能> | P0/P1/P2 |

### PAGE-001 <页面名称>
#### FR-001｜【修改】【P0】<功能名称>
#### FR-002｜【新增】【P1】<功能名称>

### JOB-001 <后台任务名称>（存在时）
#### FR-003｜【新增】【P0】<功能名称>

## 3. 待确认项（存在时）

## 附录：术语与缩略语（按需）
```

普通变更不输出业务解决方案。只有存在跨页面流程、多个角色协作、对象关系或跨系统边界时，才在“系统功能”前增加必要图形。

## 2. 输入资料与存量事实

- 核对旧需求、页面截图、流程图、字段说明、Excel 和补充记录。
- 原系统截图放在对应 `PAGE-xxx` 附近，并用文字说明本次关注区域。
- 原流程图准确时保留；重绘时明确 As-Is 或 To-Be。
- 影响功能行为、字段、权限、接口、运行或历史兼容的原文事实不得遗漏。
- 材料冲突或结论不足时创建 `Q-xxx`。

## 3. 页面与功能

### 3.1 功能范围与页面

“系统功能”开头只建立一次功能范围表：

| 功能编码 | 功能说明 | 优先级 |
|---|---|---|

每个受影响页面默认只写入口、使用角色和必要的原系统截图，随后直接展开 `FR-xxx`。不重复页面说明、功能列表或功能对比表。无入口或角色信息时不编造。

### 3.2 修改功能

每个【修改】功能直接写要修改的描述和逻辑，通常使用 3～8 条短句。将相关字段、交互、后台保存与处理、异常、必要影响和不变边界自然合并到这些说明中，不强制设置“原功能、本次功能、明确不变、修改影响”等标题或表格。

只有不对比就容易误解、涉及删除或高风险兼容时，才补充必要的原行为或不变边界；不要为形式完整重复正文。

### 3.3 新增、删除和不变

- 【新增】：直接说明入口或触发、功能行为、字段或后台信息及主要影响，不必写“原系统无此能力”。
- 【删除】：说明原功能、删除范围、替代方式；历史数据、外围调用、权限和恢复仅按风险补充。
- 【不变】：只说明容易误改或需要回归关注的具体行为，不盘点全系统。
- 【待确认】：说明问题、可选方向、影响功能和是否阻断开发。

### 3.4 字段与规则

- 页面字段总体可写“参考原页面字段及以下补充说明”。
- 只列本次新增、修改、删除、受影响不变和关键依赖字段。
- 页面未显示但后台需要保存、处理、审计或恢复的信息，在本功能下补充。
- 同一业务对象的规则集中说明；简单规则不创建 `BR-xxx`。
- 多个 BU、角色、订单类型、状态或场景在相同维度上规则不同，优先用对比表；一行一个范围，一列一个稳定规则维度。顺序逻辑、少量规则和复杂例外继续用条目。

### 3.5 跨页面功能

同一功能跨多个页面时沿用同一 `FR-xxx`。每个页面写本页面的入口、字段、交互和影响，不重新创建一套功能或规则编号。

接口、批处理、定时任务和规则引擎使用真实运行载体，不创建虚假页面。

## 4. 按需扩展

- 简单局部改造不输出接口、权限、NFR、上线、运营、验收和测试独立章节。
- 公共约束确实覆盖多个功能或存在高风险时，才增加“跨功能公共要求”。
- 正式验收或规则复杂时增加验证要点或 `AC-xxx`。
- 用户要求测试、直接开发或正式 SDD 包时才生成 `TC-xxx` 和追踪矩阵。
