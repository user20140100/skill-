## 1. 输出原则

1. 完整分析，精简输出。检查到但无变化、无风险的内容不建立章节。
2. 零散和局部需求从“痛点与目标”直接进入“系统功能”。
3. 专项和项目型的“业务解决方案”只保留有评审价值的流程图、数据关系图和系统边界图。
4. 页面和运行载体是阅读聚合单元，`FR-xxx` 是功能和开发追踪单元。
5. 场景、规则、字段、后台信息、状态、异常、影响和验证点放在对应功能附近。
6. 不用一串编号代替正文，也不为简单内容创建独立编码。
7. 术语与缩略语放在附录；原始材料未明确提出且不存在理解歧义时不输出。
8. 用户要求精简时，默认每个功能保留 3～8 条关键行为；不复述流程图，不穷举材料未提及的所有边界，同类待确认项合并。

## 2. 编号与标签

### 2.1 编号

- `FR-xxx`：唯一必需的功能主编码。
- `PAGE-xxx`：多功能页面、复杂页面或跨页面链路时使用。
- `Q-xxx`：存在影响开发或评审的待确认问题时使用。
- `OBJ/SCN/BR/DATA/INT/NFR/AC/TC/AGT/TOOL/KNW/EVAL`：仅在需要独立追踪时使用。

不默认创建 `CHG-xxx`。新增、修改、删除、不变和待确认直接作为功能属性。

### 2.2 标签

| 标签 | 使用条件 | 最低说明要求 |
|---|---|---|
| 【新增】 | 原系统不存在，本次增加 | 新能力、入口或触发、影响 |
| 【修改】 | 存量能力行为发生变化 | 修改内容、修改逻辑及理解变化所需的必要边界 |
| 【删除】 | 本次确认下线 | 删除范围、替代、历史及外围影响，按风险说明恢复 |
| 【不变】 | 位于影响半径且容易误改 | 继续沿用的具体行为和边界 |
| 【待确认】 | 证据或决策不足 | `Q-xxx`、影响和确认责任 |

标签可以组合，如 `【修改】【待确认】`。标签前不得添加彩色圆点或其他小图标。

## 3. 痛点与目标

默认使用三列表格：

| 痛点 | 目标 | 备注 |
|---|---|---|
| 描述当前机制及其后果 | 描述本次希望达到的结果 | 写明不在本次范围、约束或待确认内容 |

规则：

- 不展开长篇背景、行业分析和企业全景。
- “缺少某按钮/字段”不是痛点，应说明它造成的业务后果。
- 目标不需要全部编号；跨功能衡量或需要独立追踪时才使用 `OBJ-xxx`。
- 基线和目标值未知时标【待确认】，不得补造数字。

## 4. 范围与优先级

项目型和专项在系统功能前列示本期范围与后置项：

| 功能编码 | 功能说明 | 优先级 | 版本 | 备注 |
|---|---|---|---|---|
| FR-001 | <一句话说明> | P0/P1/P2 | V1.0 | <核心闭环或配套关系> |

| 本期不做的功能 | 优先级 | 后置原因 | 计划版本 |
|---|---|---|---|
| <功能说明> | P1/P2 | <依赖、资源或决策原因> | V1.1/V2.0 |

MVP 原则上由全部 P0 和支撑 P0 闭环所必需的 P1 组成。变更型需求仅在功能范围表中标注优先级，不单独建立本章。

## 5. 业务解决方案

### 5.1 是否输出

| 情况 | 输出 |
|---|---|
| 零散、单页面或简单局部变更 | 默认不输出 |
| 存在跨页面、跨角色或明显业务分支 | 输出业务解决流程图 |
| 对象关系复杂或责任源不清 | 增加数据关系图 |
| 跨系统边界影响理解或评审 | 增加系统边界图 |

本章只保留必要图形和一两句图示说明。场景、规则、状态、字段、异常和验证不得在这里重复展开。

流程图已经能够表达步骤时，不再追加同内容的编号步骤列表。

### 5.2 流程分层

业务流程可按 L1～L6 分析：价值域、端到端价值流、主干流程、场景子流程、业务活动、执行任务。按需求复杂度选择展示层级，不要求每份文档都输出完整分层。

L1～L6 仅用于业务流程；系统功能按系统/模块、页面或运行载体和 `FR-xxx` 组织。

## 6. 页面与功能

### 6.1 页面概览

```markdown
### PAGE-001 <页面名称>

入口：<菜单或进入方式>

使用角色：<角色和数据范围>

原系统页面截图：<将截图放在此处，并说明本次关注区域>
```

零散变更在系统功能开头只使用“功能编码、功能说明、优先级”三列表做一次总览；页面下不重复功能列表。专项和项目型可按复杂度增加一句页面说明或简表，但不得重复功能正文。

### 6.2 功能块

```markdown
#### FR-001｜【修改】【P0】<功能名称>

- <直接说明要修改或新增的行为、字段、交互和处理逻辑。>
- <将必要的后台信息、失败处理、不变边界、影响或待确认项自然写入。>
```

零散变更不强制使用“功能目标、原功能、本次功能、明确不变、修改影响”等固定小节。只有复杂、高风险或对比本身能显著帮助评审时才拆分。删除功能仍需写清删除范围、替代和必要的历史或外围影响。

### 6.3 无页面能力

无页面的接口、任务、批处理、规则引擎和 Agent 使用真实运行载体，例如 `JOB-001` 或 `INT-001`。功能块将“页面交互/页面字段”替换为“触发方式、运行过程、输入输出和可观察结果”。不得创建虚假页面。

## 7. 字段、后台信息与规则

### 7.1 页面字段

- 不重新抄录原页面全部字段。
- 只列新增、修改、删除、受影响不变和本次功能依赖的关键原字段。
- 简要写字段用途、输入或展示方式、默认值、必填条件、枚举、校验和权限。
- 原系统截图可作为字段布局参考，但截图不能替代关键变化的文字说明。

### 7.2 后台保存与处理信息

页面未展示但后台需要保存、计算、审计、传递或用于恢复的信息，默认直接合并到功能调整说明中。只有信息较多、存在独立数据责任或表格明显更易读时，才单独列出业务名称、用途、来源或产生方式及处理要求。

需求阶段不默认描述数据库表、列、主键、外键、索引和技术类型。只有用户提供现有数据库结构并要求变更规格时，才保留相关技术约束。

### 7.3 业务规则

- 同一业务对象的取值、校验、优先级、有效期、覆盖、失效和历史处理尽量集中说明。
- 先判断规则是否共享同一比较维度。多个 BU、角色、订单类型、状态、产品类别或场景需要横向比较时，优先使用表格：一行一个业务对象或范围，一列一个稳定规则维度。
- 同维度规则超过 3 组、文字出现重复句式，或读者需要快速定位差异时，通常应使用表格；规则是顺序步骤、单一对象逻辑或只有 1～2 条时，使用条目更清晰。
- 表格只保留能帮助比较的维度；复杂例外、算法顺序和待确认项放在表格后简要说明，避免把长段落塞入单元格。
- 页面内简单校验、显示条件和单一对象规则使用无编号条目。
- 只有跨功能复用、复杂计算、配置化、独立版本、审计或测试需要独立追踪时才创建 `BR-xxx`。
- 一个规则跨页面时在主责位置完整定义，其他页面写该页面的具体表现，不只写编号引用。

## 8. 按需内容

### 8.1 状态、异步与异常

只有主对象存在状态机、多条状态转换或异步闭环时才输出。简单成功/失败提示直接写在功能说明或页面交互中。

### 8.2 接口、权限、NFR、上线与运营

功能特有内容留在功能块。只有公共约束跨多个功能、确有变化或存在风险时，才建立独立章节。无变化时不输出“沿用原机制”空章节。

### 8.3 验证和测试

- 普通低风险需求可不输出验证部分。
- 存在规则歧义、边界、权限、状态、异步、历史兼容或高风险动作时，增加简短“验证要点”。
- 正式验收、直接开发或 SDD 交付时按需使用 `AC-xxx`。
- 用户明确要求测试、正式测试交付或高风险开发时才生成 `TC-xxx` 和 `testcases.md`。

## 9. SDD衔接

`FR-xxx` 作为需求到开发的主键：

```text
需求功能 FR-001
→ specs/001-feature-name/spec.md
→ 开发任务 [FR-001]
→ 提交或 PR [FR-001]
→ 按需 AC/TC
```

业务文档不因 SDD 增加复杂度。只有进入开发时才加载 [`sdd-specification.md`](sdd-specification.md)，把已确认功能转换为开发切片。
