# 需求分析图表选型与表达规范

## 1. 核心原则

1. 先明确图表要回答的唯一评审问题，再选择图表类型和载体。
2. 需求类型不决定是否画图；关系复杂度、歧义风险和评审对象决定。
3. 一张图保持同一抽象层级。节点过多或同时表达不同问题时，拆成总览图和聚焦子图。
4. 图表与正文共用 `SCN/BR/FR/PAGE/DATA/INT/AGT` 编号和术语，不维护两套事实。
5. 简单事实、少量步骤、字段、规则、接口和验收优先使用段落或表格。
6. 材料不足时标「待确认」，不使用完整图形掩盖事实缺口。
7. 图后用 1～2 句说明控制点、关键变化、风险或结论，不复述所有节点。

## 2. 图表语义模型

绘图前先在内部形成以下模型；只有用户需要交接图形时才输出完整模型。

| 字段 | 要求 |
|---|---|
| 评审问题 | 图表需要回答的唯一问题 |
| 结论式标题 | 直接表达核心判断，不只写“流程图” |
| 范围 | 组织、系统、业务、时间和数据边界 |
| 抽象层级 | L1～L6、系统模块、功能、页面、对象或状态 |
| 图表类型 | 流程、泳道、架构、对比、ER、状态机等 |
| 阅读方向 | 左到右、上到下或中心向外 |
| 分区 | 阶段、泳道、层级、系统边界或对比栏 |
| 节点 | 编号、名称、类型、责任主体、必要规则 |
| 关系 | 起点、终点、方向、关系动词、条件和基数 |
| 异常与回路 | 失败、重试、补偿、驳回、降级和返回位置 |
| 图后结论 | 控制点、改变、风险或待决策事项 |

先校验范围、层级、节点和关系，再选择 Mermaid、ASCII、图片或其他载体。不同载体必须来自同一语义模型。

## 3. 问题到图表类型

| 要回答的问题 | 推荐图表 | 关键内容 |
|---|---|---|
| 项目未来如何运行 | 业务蓝图 | 目标、价值流、能力、系统与治理支撑 |
| 业务域和能力如何组成 | 业务架构图 | L1～L2 边界、能力分区、支撑关系 |
| 系统和模块如何分工 | 系统边界/功能架构图 | 范围内外、模块、公共能力、责任关系 |
| 数据从哪里来并服务什么 | 数据架构图 | 来源、集成、资产、治理、服务和消费 |
| 当前机制如何转为目标机制 | As-Is/To-Be 对比 | 对齐维度、变化动作、影响和结论 |
| 活动按什么顺序和条件执行 | 流程图 | 触发、活动、判断、异常和结果 |
| 谁负责、在哪里交接 | 泳道图 | 角色/系统、活动归属、真实交接和异常责任 |
| 对象如何关联 | ER/对象关系图 | 实体、关系动词、基数和主从方向 |
| 对象状态如何变化 | 状态机 | 状态、事件、守卫、动作、终态和失败态 |
| 哪些系统交换什么 | 集成关系图 | 系统、业务对象、方向、方式和责任方 |
| 两个方案如何取舍 | 对比图 | 相同维度、代价、风险和结论 |
| 三个以上方案如何评价 | 决策矩阵表 | 评价维度、权重依据和结论 |
| 如何分阶段落地 | 里程碑/路线图 | 阶段、交付、退出条件和价值 |
| Agent 如何感知、决策和行动 | Agent 架构图 | 触点、Agent、知识、工具、人审和治理 |
| Agent、工具和审批如何交互 | 时序图/状态机 | 请求、调用、审批、超时、补偿和终止 |
| 指标如何比较或变化 | 柱状/折线/漏斗 | 真实数值、口径、单位、时间和来源 |

### 3.1 L1～L6 图表选择

| 层级 | 推荐表达 | 注意事项 |
|---|---|---|
| L1 业务价值域 | 业务蓝图/价值域地图 | 不按部门组织划分价值链 |
| L2 端到端价值流 | 价值流图/业务关系图 | 标明起点、阶段、结果和关键对象 |
| L3 主干业务流程 | 端到端流程/泳道图 | 只放通用主线和关键控制点 |
| L4 业务场景子流程 | 场景流程/泳道图 | 依附 L3，表达业务模式和异常差异 |
| L5 业务活动 | 活动表/规则表 | 优先表格，关系复杂时绘图 |
| L6 执行任务 | 操作、配置、接口或任务表 | 不上升为业务蓝图 |

系统功能架构使用“系统/产品 → 模块 → 功能组”，不得套用 L1～L6。

## 4. 表达载体选择

| 条件 | 默认载体 |
|---|---|
| 关系简单、少于约 5 个连续步骤 | 列表或步骤表 |
| Markdown 环境支持 Mermaid | Mermaid，保持可编辑和可渲染 |
| 用户明确要求纯文本或环境不支持图形渲染 | ASCII 简化图 |
| 用户明确要求专业视觉图或图片 | 读取 [`visual-style.md`](visual-style.md) 后生成视觉图 |
| 图过于复杂 | 总览图 + 聚焦子图 + 结构化规格表 |

载体选择规则：

- Mermaid 或视觉图不是默认要求；只有图形确实降低理解成本时使用。
- ASCII 是兼容性降级方案，不是全局强制；只保留必要节点、方向、分支和异常。
- 正式图形交付不能只给绘图说明；若当前环境无法生成图形，提供语义模型并明确限制。
- 图表不能替代字段、规则、接口、权限、验收和 JSON Schema 等可检索内容。

## 5. 专业构图规则

### 5.1 通用规则

1. **确定锚点**：蓝图锚定目标，架构锚定边界，流程锚定主路径，对比锚定变化，状态机锚定合法状态。
2. **先骨架后节点**：先确定层级、阶段、泳道、边界或对比维度，再放节点。
3. **主线连续**：主路径方向统一；支撑能力放下层或侧栏，异常靠近触发点。
4. **关系有语义**：箭头写业务对象、动作、条件或基数；依赖、流转、数据交换和反馈不得使用同一种无标签连线。
5. **层级一致**：同层节点粒度一致；页面操作不与业务价值域并列。
6. **控制复杂度**：出现大量交叉线、长回路或多个生命周期时拆图。

### 5.2 流程与泳道

- 主流程优先左到右；页面较窄或阶段较深时上到下。
- 从触发开始，依次表达活动、判断和结果；判断分支写完整条件。
- 异常、驳回、重试、补偿和人工接管注明返回位置或结束状态。
- 泳道按责任主体划分，业务角色和系统动作可分道；系统自动动作不放在人工泳道。
- 数据或消息关系注明对象，不与业务控制流混淆。

### 5.3 ER、状态和集成

- ER 图按业务聚合分区，实体使用业务名词，关系标动词和 `1`、`0..1`、`1..N`、`N..M`。
- 状态机先定义合法状态，转移写 `事件 [守卫] / 动作`，标明终态、失败态和回退。
- 集成关系图先画系统边界，再画业务对象、方向和 API/事件/批量方式；减少无语义交叉线。

### 5.4 Agent 图表

- Agent 架构图说明运行组件和治理边界，不替代工具、输出和评测 Schema。
- 时序图只用于关键工具调用、人工审批、异步恢复或 Handoff。
- 多 Agent 图注明最终控制方、移交条件、共享状态、最大轮次和终止条件。
- 图中只保留影响理解的关键分支；正常、拒绝、转人工、工具失败、超时和回滚必须在正文规格中有结论。

## 6. 制造业常用图组

| 场景 | 推荐图组 |
|---|---|
| ERP、SCM、MES 一体化项目 | 业务蓝图 + L3 主干流程 + 系统边界 + 数据架构 |
| 订单承诺与供应协同 | L2 价值流 + L4 场景泳道 + 订单/计划状态机 |
| 物料齐套与缺料处置 | L4 流程 + 物料/BOM/工单对象关系 + 异常闭环 |
| 生产工单执行与报工 | MES 泳道图 + 工单状态机 + ERP/MES 集成关系 |
| 批次与序列号追溯 | 追溯链路图 + 对象关系图 + 状态/事件表 |
| 质量不合格闭环 | 跨质量/生产/供应链泳道 + 不合格状态机 |
| 智能排产或异常 Agent | Agent 架构 + 工具调用时序 + 人工审批/执行状态机 |

图组只在每张图回答不同问题时使用，禁止为了形式丰富重复表达同一内容。

## 7. 需求类型裁剪

| 类型 | 优先检查 | 裁剪原则 |
|---|---|---|
| 项目型 | 业务蓝图、L3 主流程、系统边界、数据架构、路线图 | 只覆盖项目范围；每张图回答一个项目级问题 |
| 专项 | As-Is/To-Be、L4 流程/泳道、状态、对象或集成关系 | 围绕一个业务结果形成闭环 |
| 变更型 | 局部流程、状态、页面变化或最小对象关系 | 只有表格不足以表达时绘图 |

“优先检查”不等于固定出图清单。未入选图表无需解释；入选图表要说明评审问题和结论。

## 8. 出图前检查

- [ ] 图的范围、层级和阅读方向清楚。
- [ ] 节点、关系、条件和编号与正文一致。
- [ ] 图形可读，没有用图替代必要的文字规格。
