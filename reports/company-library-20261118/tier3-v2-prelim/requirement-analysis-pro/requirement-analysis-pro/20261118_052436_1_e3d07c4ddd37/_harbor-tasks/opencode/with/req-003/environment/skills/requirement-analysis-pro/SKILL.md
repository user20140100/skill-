# requirement-analysis-pro

> 把业务需求整理成业务看得懂、产品说得清、研发找得到、AI 可以继续开发的规格。完整分析不等于完整输出；默认只写对评审、开发和确认有用的内容。

## 1. 定位与默认交付

本 Skill 的首要任务是将用户提供的原始需求、业务资料、会议纪要、旧需求文档、截图、流程、表格及零散说明进行梳理、去重、整合和校验，在不改变事实含义的前提下形成可评审、可确认、可继续开发的需求文档。

默认交付一份精简 Markdown 需求文档。按用户意图扩展：

| 意图 | 输出 |
|---|---|
| 需求分析 | 项目型、专项或变更型需求文档 |
| 沿用已有格式 | 保留目标文档的章节、编号、表格和表达方式，完成内容整合、一致性检查、待确认标记及跨文档验证 |
| 页面与原型 | 正文中的 `PAGE-xxx`；明确要求时增加原型包 |
| 开发或 SDD | 在业务文档确认后增加 `spec.md`；测试和追踪文件按需生成 |
| AI Agent 开发 | 按需增加 `agent-spec.md`、`evals.md` |
| 转飞书 | Markdown 校验后交给 `lark-doc-studio` |
| 仅审查 | 只给问题、风险和修改建议，不修改原文或远端内容 |

## 2. 核心原则

1. **默认精简**：后台可以完整检查，正文只输出本次有用、发生变化或需要确认的内容。不得用空章节、全量检查表和重复背景制造“专业感”。
2. **来源整合**：先识别各材料的来源、时间、版本和适用范围，再合并重复内容；保留关键事实和决策依据，不把不同语境的表述强行拼接为单一结论。
3. **格式继承优先**：用户明确要求按已有需求文档格式或已有内容输出时，以目标文档为结构和表达基线，不强制套用本 Skill 的章节、编号、标签或表格模板。本 Skill 的方法论仅用于后台检查和内容补强。
4. **痛点直达功能**：零散和局部变更需求默认使用“痛点与目标 → 系统功能 → 待确认项”。
5. **页面聚合阅读**：页面是功能的交互载体。页面下集中说明功能、字段、后台信息、对象规则、交互、影响和验证点，不拆成多个重复章节。
6. **功能驱动开发**：标准结构模式以 `FR-xxx` 作为功能主编码和需求、SDD、任务、提交及测试的追踪键；格式继承模式沿用目标文档既有编码，除非用户要求转换。
7. **存量改造直接写变化**：修改功能直接说明要改什么及修改逻辑。原功能、不变边界和影响只在理解变化或控制风险所必需时自然写入，不强制使用“四段式”标题或对比表。
8. **状态标签无图标**：标准结构模式只使用【新增】【修改】【删除】【不变】【待确认】，不得在标签前添加彩色圆点或其他小图标；格式继承模式沿用目标文档既有标记规则。
9. **字段就地说明**：不默认建立数据对象或数据库表章节。页面字段、未展示但后台需要保存或处理的信息均在对应页面或功能下说明。
10. **规则归并并选择合适载体**：同一业务对象或同一判断维度的规则集中说明。多个 BU、角色、订单类型、状态或场景在相同维度上存在差异时，优先用对比表；顺序、计算或少量简单规则用条目。简单规则不编号；跨功能复用、复杂计算、配置化、审计或独立版本管理时才使用 `BR-xxx`。
11. **按需验证**：验证要点、`AC-xxx`、`TC-xxx` 和追踪矩阵按风险、交付和用户要求生成，不是所有需求的必备内容。
12. **业务与实现分层**：需求和 `spec.md` 写 Why/What；技术方案、代码和任务写 How/When。没有仓库上下文时不虚构类名、表名、目录和技术方案。
13. **事实与方案分离**：缺失信息标【待确认】，不得补造规则、指标、接口、阈值或系统能力。
14. **确定性优先、运行闭环优先**：稳定规则优先用配置或固定工作流；持续运行或高风险能力按需说明监控、接管、审计、降级和恢复。自动化程度按“人工操作 → 系统辅助 → 半自动（人工确认）→ 全自动”逐级选择，高风险场景不得跳过人工确认直接全自动运行。
15. **篇幅服从任务**：用户要求精简时，每个功能只保留关键行为和直接影响；不把流程图再逐步复述，不主动穷举原始材料未提及的全部可能规则，同类待确认项合并且不在正文和汇总表重复出现。
16. **范围与优先级显性化**：标准结构模式下，每个功能标注 P0、P1 或 P2。资源受限时优先保证 P0 业务闭环，P1/P2 可后置或简化。

## 3. 文件路由

先判定交付模式，再决定是否进入类型路由。不得为了“完整”预读全部资料。

### 3.1 格式继承模式

当用户明确要求“按现有格式”“沿用原需求文档结构”“在已有内容基础上整理或续写”时，本模式优先于项目型、专项和变更型路由：

1. 以目标文档的章节顺序、标题层级、编号体系、表格结构、术语和表达粒度为准，不主动重构为本 Skill 的标准目录。
2. 不强制新增 `FR-xxx`、`PAGE-xxx`、痛点与目标、系统功能、验收等章节；目标文档已有对应结构时在原位置补充，用户要求转换时才采用标准结构。
3. 将原始需求、会议纪要和补充资料去重后归入目标文档的对应位置；无法确定归属或存在冲突时标【待确认】，不得自行选择一种说法覆盖其他来源。
4. 检查范围、目标、流程、功能、字段、规则、状态、角色、接口、权限、验收之间的因果和引用关系，验证术语、对象、数量、单位、比例、时间、版本、枚举和状态前后一致。
5. 用户提供或要求参考其他需求文档时，按系统边界、功能、字段、规则、状态、接口、版本和术语进行交叉验证；记录冲突来源、影响和待确认结论，不将其他文档内容无依据地并入目标文档。
6. 默认直接输出沿用原格式的完整文档。若用户要求仅审查，则只输出逻辑矛盾、数量差异、遗漏引用、跨文档冲突和不确定事项清单。
7. 目标格式缺少高风险业务所需信息时，优先在最接近的既有章节补充；确需新增章节时先说明原因并征得用户同意。

格式继承模式默认不加载 `doc-structure-common.md` 及项目型、专项、变更型结构文件。只有用户要求转换为标准结构时，才继续执行下方类型路由。

### 3.2 标准结构模式

新建需求文档、用户未指定已有格式，或用户明确要求按本 Skill 标准结构输出时，先判定类型，再读取共用规范和一种类型文件。

| 文件 | 读取条件 |
|---|---|
| [`references/doc-structure-common.md`](references/doc-structure-common.md) | 标准结构模式的所有需求任务 |
| [`references/doc-structure-project.md`](references/doc-structure-project.md) | 新平台、跨业务域、多核心系统或分阶段项目 |
| [`references/doc-structure-special.md`](references/doc-structure-special.md) | 围绕一个业务结果的跨模块专项或高风险改造 |
| [`references/doc-structure-ad-hoc.md`](references/doc-structure-ad-hoc.md) | 已有系统的页面、字段、规则、权限、报表或局部逻辑变更 |
| [`references/chart-selection.md`](references/chart-selection.md) | 确实需要流程、关系、边界、状态或架构图时 |
| [`references/visual-style.md`](references/visual-style.md) | 用户要求专业视觉成图时；普通 Markdown 不加载 |
| [`references/prototype-spec.md`](references/prototype-spec.md) | 页面复杂或用户要求原型输入时 |
| [`references/sdd-specification.md`](references/sdd-specification.md) | 用户要求开发、SDD、测试、直接编码或 AI Agent 规格时 |

## 4. 类型与深度

本节用于标准结构模式。格式继承模式只在后台识别需求复杂度和业务风险，不因分类结果调整目标文档目录。

| 类型 | 判定信号 | 默认输出 |
|---|---|---|
| 项目型 | 新平台、跨业务域、多核心系统、端到端变革、迁移或分阶段推广 | 痛点与目标、必要业务图、系统功能、按需公共要求 |
| 专项 | 围绕一个业务结果，涉及多个模块或系统，需要专题闭环 | 痛点与目标、必要业务图、系统功能、按需公共要求 |
| 变更型 | 已有系统的局部页面、字段、校验、权限、报表、通知或逻辑调整 | 痛点与目标、系统功能、待确认项 |

以下情况即使改动点少，也升级为专项深度：跨系统数据责任变化；库存、生产、质量、财务、合同、权限或删除等高风险动作；复杂状态机；较大历史回填；自动执行会改变订单、计划、库存、产能或财务结果。

## 5. 编号与标签

本节用于标准结构模式。格式继承模式沿用目标文档现有编号和标签；目标文档未使用编码时，不主动引入本节编码。

### 5.1 必需编号

| 对象 | 编号 | 使用规则 |
|---|---|---|
| 功能 | `FR-xxx` | 唯一必需的功能主编码；一个编号对应一个可定位的功能行为 |
| 页面 | `PAGE-xxx` | 多功能页面、复杂页面或跨页面链路时使用 |
| 待确认项 | `Q-xxx` | 仅用于影响范围、行为、字段、规则、接口或开发决策的未决问题 |

### 5.2 按需编号

| 对象 | 编号 | 仅在何时使用 |
|---|---|---|
| 业务目标 | `OBJ-xxx` | 需要独立衡量或跨功能追踪 |
| 业务场景 | `SCN-xxx` | 跨功能复用或需要独立演示 |
| 业务规则 | `BR-xxx` | 跨功能复用、复杂计算、配置化、审计或独立版本管理 |
| 数据对象 | `DATA-xxx` | 对象关系复杂、责任源争议或需要跨功能治理 |
| 接口/事件 | `INT-xxx` | 确有跨系统契约变化 |
| 非功能要求 | `NFR-xxx` | 有明确且可测的性能、安全、可用性等要求 |
| 验收条件 | `AC-xxx` | 风险较高、需要正式验收或进入 SDD 开发 |
| 测试用例 | `TC-xxx` | 用户要求测试、直接开发或正式测试交付 |
| Agent 能力 | `AGT-xxx` | AI Agent 场景 |
| Agent 工具 | `TOOL-xxx` | Agent 工具需要独立授权或追踪 |
| 知识源 | `KNW-xxx` | Agent 或检索场景 |
| AI 评测 | `EVAL-xxx` | 非确定性能力发布评测 |

编号创建后不得因排序而重排或复用。废弃功能保留编号并标 `Deprecated`。默认追踪主线为：

```text
PAGE-xxx → FR-xxx → 按需 BR/INT/NFR/AC/Q → 按需 TC/EVAL
```

不默认创建 `CHG-xxx`。变更类型直接作为 `FR-xxx` 的属性。

### 5.3 变更标签

- 【新增】：原系统不存在，本次增加。
- 【修改】：沿用存量能力但改变行为、字段、交互、规则、权限、状态或运行方式。
- 【删除】：本次确认下线；需按风险说明替代、历史、外围调用和恢复。
- 【不变】：只用于影响半径内、容易误改或需要回归关注的能力。
- 【待确认】：结论不足；与 `Q-xxx` 关联。可与【新增】或【修改】组合。

### 5.4 优先级标签

| 标签 | 定义 | 判断标准 |
|---|---|---|
| 【P0】 | 核心业务闭环必需 | 缺少会阻断核心流程、违反合规或风控要求，或导致主要场景无法完成 |
| 【P1】 | 重要但不阻断主流程 | 显著提升效率或体验，或属于 P0 的必要配套能力 |
| 【P2】 | 可后置的增强能力 | 低频、边缘场景或无明确效率收益的体验优化 |

标准功能标题格式：`#### FR-001｜【新增】【P0】<功能名称>`。格式继承模式沿用目标文档的优先级体系；目标文档未定义时，在功能概览中补充“优先级”。依据不足时给出建议优先级并标【待确认】，不得虚构版本计划。

## 6. 工作流

### Step 1：识别交付和来源

识别需求对象、业务范围、系统范围、原始材料、期望交付和已知约束。先判断用户是否明确要求沿用已有文档格式；若是，锁定目标文档、参考文档、版本和允许修改的范围，再进入格式继承模式。信息不足时只追问会改变范围、功能行为、字段、规则、接口或开发结论的问题。

### Step 2：萃取事实并分类

区分事实、痛点、诉求、约束、已确认决定和待确认项。记录各项来源、时间、版本及适用范围。标准结构模式判定项目型、专项或变更型并执行风险升级；格式继承模式只在后台判断复杂度和风险，不据此改写目标文档结构。

### Step 3：分析存量和影响

检查业务、页面、字段、后台保存信息、规则、权限、接口、任务、报表、历史数据和运行影响。检查不等于全部输出；无变化且无风险的维度不建立章节。

整理已有系统资料时：

- 保留影响功能理解的原文事实；
- 原系统截图放在对应 `PAGE-xxx` 附近；
- 原流程图准确时保留，需要说明目标方案时再重绘；
- 标准结构模式将冲突或缺口写为 `Q-xxx`；格式继承模式沿用目标文档的待确认标记，未定义时使用【待确认】。不得静默删除或擅自补齐。

格式继承模式还应检查：

- 同一对象在不同章节中的名称、数量、单位、时间范围、状态和版本是否一致；
- 目标、流程、功能、规则、字段、接口和验收之间是否存在遗漏、断链或相互矛盾；
- 章节、表格、图示、附件和编号引用是否准确，是否存在无来源结论或失效引用；
- 相关需求文档之间的系统边界、功能归属、字段定义、业务规则、接口契约和版本关系是否一致。

格式继承模式完成材料整合和上述检查后即可按原格式交付；只有用户同时要求补充方案设计、原型、SDD 或测试规格时，才继续执行后续对应步骤。

### Step 4：按需设计业务方案

零散和普通变更需求默认跳过业务解决方案。专项或项目型仅按需输出：业务解决流程图、数据关系图、系统边界图。图后只保留必要说明；场景、规则、字段、状态和异常下沉到系统功能。

业务流程可使用 L1～L6 分析，但按复杂度选择需要展示的层级。L1～L6 仅用于业务流程；系统功能使用系统/模块、页面或运行载体和 `FR-xxx` 组织。

### Step 4.5：界定范围与优先级

在展开功能前确定本期范围和实施顺序：

1. 汇总功能并按 P0/P1/P2 标注优先级；
2. MVP 原则上由全部 P0 和支撑 P0 闭环所必需的 P1 组成；
3. 将 P2 及因资源或依赖后置的 P1 列入“本期不做”，说明原因和计划版本。

项目型和专项在“系统功能”前输出“范围与优先级”，分别列示本期范围与后置项。变更型仅在功能范围表中增加优先级，不单独建章。

### Step 5：定义页面与功能

本步骤适用于标准结构模式。格式继承模式沿用目标文档的页面、功能组织方式和既有编号，仅做内容整合与一致性修订。

零散变更先在“功能范围”用“功能编码、功能说明、优先级”三列表概览。每个页面默认只写入口、使用角色和必要的原系统截图，随后直接展开 `FR-xxx`，不在页面下重复功能列表。专项和项目型页面可按复杂度补充一句页面说明或精简功能列表，但不得与功能正文重复。

每个功能块直接写调整说明，按需包含：

1. 要修改或新增的行为及逻辑；
2. 必要的触发、输入、处理、输出和失败行为；
3. 本次相关的字段、交互和后台处理信息；
4. 按业务对象或判断维度归并的规则；
5. 理解变化或控制风险所必需的原功能、不变边界和影响；
6. 状态、异步、异常、验证和待确认项，仅在确实涉及时。
7. 优先级标签，直接标注在功能块标题中。

精简约束：普通功能通常控制在 3～8 条；字段、后台信息、影响和不变边界默认合并到调整说明，不另设小节或表格。只有内容较多且独立阅读更清晰时才分组。同一决策主题只建立一个 `Q-xxx`。信息不足时先保持方案骨架，不把所有可能性展开成正文。

一个功能跨页面时沿用同一 `FR-xxx`，并在各页面说明该页面的具体表现。无页面的接口、任务、规则引擎和 Agent 使用真实运行载体，不创建虚假页面。

### Step 6：字段、后台信息与规则

- 页面字段总体可写“参考原页面字段及以下补充说明”，只列新增、修改、删除、受影响不变和关键原字段。
- 页面未显示但后台需要保存、计算、审计或传递的信息，直接写入对应功能的调整说明；信息较多或存在独立数据责任时才单独列表。
- 需求阶段描述业务信息、来源、用途、产生方式和是否展示；不默认写数据库表名、列名、主键、外键和技术类型。
- 同一对象的校验、取值、优先级、有效期、覆盖和历史处理规则集中说明。若多个业务单元在同一组维度上存在差异，优先使用“对象/范围 × 规则维度”的表格，表头采用可直接比较的稳定维度；不要把同构规则拆成重复段落。简单规则不拆成多个编码。
- 对象关系复杂或责任源不清时才绘制数据关系图或使用 `DATA-xxx`。

### Step 7：按需补充公共要求

接口、权限、NFR、迁移、上线、运营、监控和回滚只有在跨多个功能、确有变化或存在风险时才建立公共章节；功能特有内容仍留在功能块内。

涉及库存、财务、质量、权限等高风险业务动作时，在业务解决方案或跨功能公共要求中简要说明主要风险及应对措施，不单独建立风险模板。

选择自动化或 Agent 时遵循：

```text
人工操作 → 系统功能 → 配置/规则 → 固定工作流
→ 模型能力节点 → 单 Agent → 多 Agent
```

### Step 8：按需生成 SDD 和验证

普通需求只需功能清晰、边界明确和待确认项可见。用户要求开发、测试、SDD 或 AI 编码时读取 `sdd-specification.md`，以 `FR-xxx` 建立开发切片；测试用例和追踪矩阵按风险及交付要求生成。

## 7. 交付前常规自检

只做一次快速自检，默认不在需求文档中输出检查表或质量报告：

- [ ] 范围和结构精简，没有空章节、重复背景或无关内容。
- [ ] 用户要求沿用已有格式时，章节、编号、表格和表达方式已保持一致，未强制套用标准结构。
- [ ] 原始需求、资料、会议纪要和旧文档已完成去重整合，关键结论可追溯到来源。
- [ ] 标准结构模式下，页面与 `FR-xxx` 能直接看出要修改什么和修改逻辑；必要的原功能、不变边界及影响已就地说明。
- [ ] 内容来自已知材料；不确定结论已标【待确认】，没有补造规则或实现。
- [ ] 术语、对象、数量、单位、比例、时间、版本、枚举和状态前后一致；矛盾或差异已明确标出。
- [ ] 用户要求参考其他需求文档时，已完成跨文档验证，并标明冲突来源、影响和待确认结论。
- [ ] 相关字段、后台信息、规则和原系统图片放在对应页面或功能附近。
- [ ] 编号和标签一致；测试、接口、NFR、图表等扩展内容只在确有需要时出现。
- [ ] 标准结构模式下，每个功能已标注优先级，并明确本期不做的内容及原因。
- [ ] 痛点描述说明了业务后果，而非仅陈述缺少某个按钮、字段或页面。

只有用户明确要求正式评审、SDD、测试交付或需求涉及高风险业务动作时，才加载相应参考文件执行专项检查；不要把专项检查扩展到普通需求。
