# 模块级需求：阶段 0 模块拆解

> 被 `SKILL.md` 的入口分流引用。当输入是一个**模块 / 子系统**（包含多个页面或功能）时，**先做本节的模块拆解，再对清单里的每个功能走主流程的 4 阶段**。单功能不走本节。

## 为什么要先拆

一个模块直接套"8 大维度"会爆炸：维度 × 功能数 = 海量问题，小白扛不住，也理不清功能之间的关系。所以先在模块层把"骨架"搭好（有哪些功能、功能之间什么关系、哪些规则是共用的），再逐个功能填"肉"。

## 阶段 0：模块拆解（5 步，全用大白话）

### 1. 模块边界（一句话）
这个模块整体是干什么的？给谁用？解决什么大麻烦？

### 2. 功能 / 页面清单
把模块里**每一个页面、每一个功能**列出来，每个一句话说清是干嘛的。
- 问法："这个模块里，你数数看大概分几块？每块是干啥的？"
- 产物：一张清单（功能名 + 一句话 + 是"页面"还是"操作"）

### 3. 页面地图（谁连到谁）
这些页面/功能之间，从哪个进、能跳到哪、哪个是入口？
- 问法："打开这个模块，第一眼落在哪？从这能点去哪几页？"
- 产物：一张简单的导航关系图（文字描述即可，不用画图）

### 4. 共性上浮（重点，避免重复问）
找出**所有功能都共用**的规则，在模块层统一问一次，各功能文档引用，不再重复：
- **角色清单**：整个模块涉及哪些人（角色）？把人先定下来。
- **权限体系**：这些角色分别能看/改什么，是不是模块统一一套规则？
- **状态口径**：整个模块的"状态"怎么算、怎么看？
- **共用基础资料**：有没有几个清单（如项目、部门、币种）是所有功能都要用的？建议在模块层做成共享基础资料。
- **共用字段**：创建人、创建时间这类是不是所有功能都该有？

### 5. 依赖与建设顺序
哪个功能得先做（别的依赖它）？哪个可以后做？
- 问法："这几个功能里，有没有哪个是地基，别的都得靠它？"

写到 `<项目根>/docs/requirements/<模块名>/00-模块概览.md`：

```

## 1. 模块边界

- 给谁用：
- 解决什么麻烦：

## 2. 功能 / 页面清单
| 序号 | 名称 | 一句话说明 | 类型(页面/操作) | 对应需求文档 |
|---|---|---|---|---|
| 1 | | | | <功能名>.md |

## 3. 页面地图
- 入口：
- 导航关系：（文字描述）

## 4. 共性规则（各功能文档引用本节，不重复）
- 角色清单：
- 权限体系：
- 状态口径：
- 共用基础资料：

```

## 然后逐个功能

清单里**每一个功能**，都走 `SKILL.md` 的阶段 1-4，产出 `<项目根>/docs/requirements/<模块名>/<功能名>.md`。
- 共性维度（角色/权限/状态/基础资料）直接引用模块概览的 §4，**不要重复问**。
- 只问这个功能**特有**的东西。

## 模块级进度落盘

在 `<项目根>/docs/requirements/.progress/<模块名>.md` 建模块进度文件：

```
# <模块名> 模块拆解进度

| 步骤 | 状态 |

```

## 模块结束条件

阶段 0 ✅ + 清单里每个功能各自走完 `SKILL.md` 的结束条件 + 用户确认模块概览。任何一条不满足都不算结束（同主流程铁律 1）。
